我本来准备装两天就卸载 DeepSeek Harness

系列第 01 篇 ｜ 版本 v1.1 ｜ 2026-11-08 ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）

先说人话：这东西是一个住在我电脑里、能自己动手的程序。我给它一句话，它会去翻文件、敲命令、写东西，做完再回来跟我讲。我以前不觉得这种东西靠得住，现在每天都在用。这篇记的是我怎么从不信走到用上，以及哪几件事我到现在也不让它碰。

读完你能做到

  • 用三个数字判断一个 agent 运行时值不值得试，而不是看宣传
  • 列出你手里"该交"和"不该交"的活，各三条
  • 把一件 30 分钟的重复小事，改成一条可验收的交接

凌晨两点，我关掉最后一个终端，顺手数了一下 ~/.dsh/storages/session_projcache/sessions 这个目录里有多少文件。屏幕回了一个数字：186。

几天前我对它的判断还停在"又一个把模型包了层壳的命令行工具"。现在我的长文流水线、知识库检索、还有几个每天都要跑的小活，都在这台机器的同一个运行时里。

这篇不教你怎么装。它是一份复盘：我原来怎么判断它、什么东西把我拽了回来、哪一次我自己搞砸了、以及哪三件事我到今天也不打算交给它。

我原来的判断

我原来的判断：又一个套壳 CLI，装两天，发一条"试了，一般"，然后卸载。

现在的判断：它是我工作流的底座，但有三件事我不会交给它。

原来的判断不是随口说的。这半年我见过的"套壳"太多了，光是社区里给同类工具套的桌面壳，我随口就能数出三个，2026 年 8 月之后就并存着。所以第一次听说又一个 harness 时，我的默认反应是把它归类，而不是打开它。

归类很省事，也很省时间。代价是，我差点错过一个我后来每天都在用的东西。

转折：我先数了三个数字

三个数字把我的判断顶回来了。

第一个数字是版本号。我这台机器上，dsh --version 回的是 0.2.2-rc.1。我去翻了官方的 release 记录：37 个版本（GitHub release 口径；npm 上另有 42 个发布版本，两个数不是一回事），全部标着 prerelease，从 2026 年 8 月 17 日到 11 月 4 日，79 天里发了 37 个，平均 2.19 天一个。

这个数字让我不舒服。因为"装两天就卸载"这个判断有一个隐含前提：这东西装完就定型了，两天足够我看清它。事实是它变得比我的判断还快。

第二个数字是配置树。我跑 dsh --profile paseo --dump-config，打出来 2390 行，其中以 - id: 开头的插件行有 197 行。把官方默认那一层剥掉（--dump-default-config）是 1243 行，两者之差，就是我自己叠上去的那一层。

197 这个数字，第一眼没让我觉得"功能多"，而是让我换了个问题。我原来问的是"它能干什么"，看到 197 之后我改问"它是怎么被拼出来的"。

顺带说一个我这几天才发现的真实限制：桌面版 profile 不允许命令行 dump。你敲 dsh --profile desktop --dump-config，它回一句 error: profile "desktop" is managed exclusively by the Electron application。所以上面那 197 行来自同源的另一个 profile，不是桌面版本身。这个区别我后面还会再提一次。

第三个数字是我自己的使用量。我把存储目录里的 186 个会话文件全读了一遍（截至 2026-11-08 02:41），累计 1968 轮、28770 步，模型侧耗时约 92.6 小时，工具侧耗时约 117.8 小时，最长的一个会话走了 2312 步。

117 比 90 更扎眼，因为这个比例暴露了我真实的工作形态：我大部分时间都在等 bash 把活干完，等模型说话的时间很少。这条如果反过来（模型时间远大于工具时间），说明我只是在跟它聊天；而 117 比 90，说明我真的把活交给它了。

这里有个方法上的细节值得说一句：我读的不是界面上的统计，是存储目录里每个会话的统计行——那一行里记着轮数、步数、模型耗时、工具耗时。界面只给你会话标题，能拿来对比的东西在原始行里。所以我敢在这篇里给具体数字，是因为它能被重新数一遍。

它替掉的第一件事：在四个窗口之间搬东西

我原来的流程是四个窗口：浏览器查资料、终端跑脚本、编辑器改稿、笔记软件归档。每一步都不难，难的是每次都要人肉搬上下文。

搬进同一个运行时之后，我数了一下会话记录：bash 出现两万八千多次，读文件一千九百多次，写文件一千八百多次，抓网页一千六百多次。这些数字是我的实际动作分布，不是功能列表。

这个分布说明一件事：我不是在"用 AI 写作"，我是在用模型替我做一台机器该做的事——读、跑、写、归档，然后把需要判断的那一小段留给我。

知识库那一侧也一样。我的 Obsidian 里有 5397 篇笔记、26 个专题目录，以前要在里面找"上次那篇东西写在哪"，得靠我记得。现在这件事变成了一次检索。

它替掉的第二件事：写完就忘的一次性脚本

我工作区里有一个 tools 目录，里面躺着一堆我自己写的脚本。其中一条是长文流水线：一条命令跑完质检、备份、图文版、建草稿。

这些脚本一直都能用，问题是它们需要我记得。我记得它叫什么、记得参数、记得先跑哪个。以前每次要跑一遍，我得先 ls 一下 tools 目录，确认名字，再确认顺序是质检、备份、图文版、建草稿。一旦隔两周没动，我就得重新读一遍自己的脚本。

搬进运行时之后，变的是"谁来记得它"。脚本本身一个字没改，还是那个脚本，但说明书现在摆在模型面前，我只要说"这篇按流水线走一遍"。

这是我认为最被低估的一次替换：它换掉的是"记住工具怎么用"这件事，工具本身没换。

它替掉的第三件事：我自己当调度员

第三件事更小，但对我意义更大。

我做过一个外链工作台，每天要跑复检。以前的做法是：我记着，到点去终端敲命令。忘一天，就断一天。

后来我给它写了个插件，111 行，注册成一个叫 linkdesk 的工具，参数主要就一个 action，值是我自己定的几个固定动作——看状态、列今天该跑的、真跑一遍。装进 profile 之后，我在对话里说"看看今天该复检哪些"，它自己挑 action 去跑。

111 行不多，但它改变了我和这件事的关系：从"我要记得"变成"它在清单里"。

这三件事合起来，就是一个很朴素的结论：能被写成"输入清楚、输出清楚、错了也兜得住"的活，搬进去是划算的。

第一件我不会交给它的事：需要我当场做价值判断的活

写文章这件事，我能让它写三版开头，三版都通顺。但没有一版知道我那 5397 篇笔记里，哪一篇是写给谁看的。

问题出在我没把判断写出来，不在模型能力。而我之所以没写出来，是因为我自己也常常是写到一半才知道自己要说什么。

这类活的特点：输入本身要靠我边做边定。交给它，我只能得到一份"看起来像我的东西"，然后花更多时间把它改回我。

第二件：碰真钱和真线上的活

发帖、部署、删数据、跑付费接口，这四件事我不交。

原因不在信不信它，在出错的代价不对称：它做对一百次，我省下一点时间；它做错一次，我要花一整天收拾。而且收拾的时候，我还得先搞清楚它到底动了什么。

我自己定的规矩是：它可以把草稿建好、把检查跑完、把命令写好，最后一个回车我来按。

第三件：我的判断标准本身

这条最难解释，但我确实感觉到了。

它会顺着我的话往下写。我说"这个方向值得做"，它就能给我五条理由；我说"这个方向有问题"，它也能给我五条理由。两种都很像样。

用久了会有个副作用：我分不清哪句话是我原本的想法，哪句话是我在对话里被喂出来的。所以我给自己留了一条笨办法——凡是涉及"要不要做"的结论，我先自己写一段，再让它看。顺序反了，我就容易认不出自己。

我翻过的一次车

上面那个 111 行的插件，我是按印象写的。

我没有先去读官方工具包的契约，凭手感写了一个定义：返回值给了一个内容块（content 数组加 isError），报错靠返回里的 isError 字段，参数用了手写的一套风格。

后来我把官方工具包翻出来逐条对，四条里错了三条：

返回值——官方要的是一个可以直接被 schema 校验的值，不是内容块；报错方式——官方靠 throw，isError 是注册表根据结果判的，不是工具自己填的；output 声明——官方要求必填，还要配 render，我压根没写。

最丢人的是第四处：我不确定宿主的注册函数签名是 execute、run 还是 handler，于是写了个循环，三种签名挨个 try，哪个不报错用哪个。

这不算试错，是没读文档就动手。官方工具包里有 defineTool，类型是完整的，参数 schema 能推出参数类型，一个 import 就能把签名这一层猜测整个消掉，返回值那三处也有类型兜着。

而我自己插件的 README 里，当时还老老实实写着一句"宿主内注册尚未验证"。也就是说，我心里知道它没验过，但我先把它当成"能跑"了。

还有一个更小的错，我顺手也记下来：我一开始把 197 这个数字理解成"197 个插件"。后来读配置 schema 的输出才发现，这些行里还混着 group 行——静态投影分不清某一行到底是插件还是分组，工具给出的诊断里就记着 4 条辨认不出的报错。所以我数的 197 是"行数"，不是"插件数"。这两个数我以后不会再混。

我的判断清单

试了这些天，我给自己留了五条，写下来给以后的我用。

一、这件事的输入和输出，我能不能用一句话说清。能说清，可以搬。

二、这件事上一次做到哪，是不是只有我记得。只有我记得，可以搬。

三、这件事出错之后，我能不能用一句话兜住。兜得住，可以搬。

四、这件事的核心是"选哪个"，还是"做完哪个"。如果是前者，别搬。

五、这件事将来要不要有人签字。要签字，别搬。

第五条是我最晚加进来的一条。有些活我做得动，它也能做，但只要将来会有人拿着这件事问一句"这是谁定的"，我就会自己动手。原因不在追责，在我认这句话比它快。

这五条不保证对。它们只是我踩过一次坑之后，暂时愿意相信的东西。

这套东西的边界

第一，它是 rc 版本。79 天 37 个版本，平均 2.19 天一个，意味着契约会变。我今天写对的插件，过一个月可能又不对了。它不算缺点，但对我来说是成本。

第二，它不会替读文档。安装包里有 28 个以 dsh-tool- 开头的工具包，每一个都有自己的契约。上面那次翻车，本质是我把"能跑"当成了"符合契约"。

第三，桌面版和命令行版不是一回事。桌面版 profile 不让 dump，那句 error 我贴在上面了。我现在看到任何配置树截图，都会先问一句：这是哪个 profile 打出来的。

第四，我要诚实说一件事：我数不清自己用了多少天。我能给你的只有三个可查的日期——vault 里最早一份 DSH 相关文件写于 2026-11-01，磁盘上桌面 App 包的日期是 2026-11-04，而 0.2.2-rc.1 这个版本的发布日是 2026-11-04。

所以这篇如果要挂一个"30 天复盘"的名头，在我这里对不上。我能确认的只有它已经进了日常：具体哪天第一次装、这期间花了多少钱，我手头没有可信记录，就不编了。能查的我都放上来了，查不到的我留着空。

第五，这篇里所有数字都是我自己在这台机器上数出来的，不是引用谁的评测。所以我只敢说"在我的机器上是这样"，不敢说"DSH 就是这样"。这两句话的区别，我最近才开始在乎。

落地案例：把"每天抄竞品"交出去

场景：你每天要打开 3 个竞品站，把新标题和日期抄进表格，大约 25 分钟。

做法：写一个 urls.txt，每行一个网址；让它读这个文件，抓每页的标题、更新日期、第一条新内容，输出一张三列的 Markdown 表；你只核对标题对不对。

验收：表里恰好 3 行，每行有链接和日期；日期比昨天新，才算过。错一行就重跑，不改表。

耗时：第一次 40 分钟（含调通），之后每次 3 分钟。

读完这一篇，你应该能把"重复但简单"的活，改成一次交接 + 一次验收。

下一篇

下一篇我要拆那个 197。因为把树拆开之后，我看到一个很别扭的事实：这 197 行里，没有一行是"主程序"。

根配置是一个空数组。所谓产品，是一层层 bundle 按 id 覆盖出来的。

术语小抄

  • harness（运行时）：夹在模型和我的电脑中间的那层程序，负责把模型想好的动作真的做出来
  • profile（配置档）：一套插件清单，桌面版、命令行版各用各的一套
  • 插件 row（配置行）：配置树里的一行，一行就是一个挂上去的零件
  • 会话（session）：我和它一次连着干活的完整记录，落成一个文件
  • dump-config：让它把实际拼出来的配置树打印出来，看看到底装了什么

我还没搞懂

  • 197 个 row 里，哪些是真插件、哪些只是分组？我按行数数的，没逐条核过类型。
  • 会话里那些耗时是它自己算的，还是系统给的？我拿来算了比例，没验过口径。
  • 桌面版为什么不让命令行 dump 配置？我接受了这个限制，但还没找到原因说明。
