一个没有核心的 Agent 运行时

版本 v1.1 ｜ 2026-11-08 02:41 (Asia/Shanghai) ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）
学习笔记 ｜ 第 2 站 ｜ 我带着的问题：一个能换模型的工具，为什么还敢说"什么都能换"？
读之前我以为：插件最多改改界面，真正管事的核心一定写死在程序里。
读完我的一句话答案：这里没有那个核心，产品是配置里一行行拼出来的。
读完我能答出来的三个问题：1 为什么它的主配置文件里只有一对空方括号？ 2 为什么说它是"两个半边加一个注册面"，不是三个半？ 3 "一切皆插件"的代价，最后落在谁身上？（答不出就说明我没学会，这篇先不发）
系列第 02 篇 ｜ 版本 v1.1 ｜ 2026-11-08 ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）

先说人话：一般软件都有个"主程序"，插件只能挂在边上改点皮毛。这个东西不是——它连"怎么跟模型说话""怎么记聊天记录"都是一个个零件，能拆能换。我第一次打开它的配置文件，里面只有一对空的方括号。这篇就是我搞明白这件事的过程。

刚装完那会儿，我想改一下它接哪个模型。打开配置文件，准备找那一行。

整份文件读完了，一共四行：三行注释，最后一行是一对方括号。

没有端口，没有模型名，没有密钥字段。一个能开界面、能跑多轮任务的产品，主配置文件是空的。

我盯着那对方括号看了很久。这篇就讲它为什么可以这样。

一、我原来的判断

我原来的判断：这又是一个把模型接口包了一层的命令行工具。所谓插件，是给主题、快捷键、小挂件留的口子；真正决定它怎么想、怎么调工具、怎么记会话的那部分，一定写死在核心里，谁也动不了。

这个判断有它的道理。我用过的东西基本都长这样：编辑器的插件改不了编辑器的内核，浏览器的扩展改不了渲染引擎，规则文件也只能影响到提示词那一层。插件是长在边上的，边上是有限度的。

现在的判断：它没有那个"边上"。模型适配器、工具注册表、会话日志、agent loop，这四样我以为一定在内核里的东西，全都是可以从配置里换掉的插件。官方文档的原话是"不存在需要打补丁的特权内核"。

这句话我一开始当成宣传语。后来我数了它的配置行数，才承认它是字面意思。

二、它到底是什么：harness 不是模型，也不是 IDE

先把词说清楚，因为它现在被用得很松。

模型是发动机。同一个模型，放进不同的 harness，表现出来的能力差得很远：会不会自己拆任务、工具调错了会不会重试、上下文满了怎么压、一次任务花多少钱，这些都不是模型单方面决定的。

harness 是发动机之外的那一整套：怎么把对话变成一次请求、怎么把工具声明塞进系统提示词、怎么执行、怎么记账、出错时怎么重来。

它也不是 IDE。编辑器是一个应用，agent 是应用里的一个功能；终端里的 agent 也一样，是某个工具里的能力。DSH 比这两者都低一层，它不自称编辑器，它自称 agent harness。官方 README 第一句就是这个定位：由 DeepSeek AI 开发的开源 agent harness（智能体框架）。

我给朋友的三句话版本是这样。

第一，它是一个运行时，不是一个应用。你装它，得到的是一套把模型接到工具、文件、会话、审批上的机制。

第二，它的每一部分都能换，包括你以为不能换的那些。

第三，换的账由换的人付。这一条我留到后面单独讲。

官方产品页上的定位句也是同一个意思："以可自由组合的插件，拓展 Agent 能力"。注意它没说强大的编程助手，它说的是插件和组合。

和 Claude Code 的结构差异，我用一句话说：Claude Code 是一个产品，里面带一套扩展机制；DSH 是一份组合清单，产品是清单跑出来的结果。

这个差异带来的手感完全不同。Claude Code 装完就能用，你能做的事被产品边界框住；DSH 装完是一份能跑的默认组合，你能做的事被清单框住，而清单是你自己的。

顺手说一个我翻安装目录时看到的东西，它解释了我开头为什么找不到主程序。

命令行入口 dsh 是一个十四行的 shell 脚本，它只干一件事：把自己换成 Electron 的 node 模式，去跑一份 CLI。也就是说，你敲的那个命令背后没有一层层调用到一个"总入口"，它进的是一个组合器，组合器再去把配置里的条目一个个挂起来。

三、第一层：根配置是空的

回到那对方括号。

它的正式名字是 cordis.yml，放在每个 profile 目录下。全文就是我开头看到的那样：三行注释，一个空数组。

注释是三句话，我抄下来：这个 profile 的根是一个空的条目列表；树是由 patch 组出来的，顺序是 package.json 里的 bundle 列表、然后 cordis.patch.yml、然后命令行传进来的 overlay；要改就改 cordis.patch.yml，别改这个文件。

空配置文件我见过不少：空的 nginx 配置、空的 compose 文件，那些都意味着"这里还没配"。在 DSH 里，空的意思是"这里不该有东西"。产品不在这个文件里，它在被叠进来的层里。

这个设计不难，但它提前定死了一件很关键的事：没有主配置这个东西，也就没有主配置里的主子。

四、第二层：2390 行、197 个条目、29 处来源标注

既然根是空的，产品就得从别处来。我把它整个打印出来看。

命令是 dsh --profile paseo --dump-config，输出管进 wc -l，出来 2390 行。

再数条目，grep 数开头是 - id: 的行，197 个。官方术语把这一个条目叫 row，下面我一律说条目。所以一个能开浏览器界面、能跑多轮任务、能挂子代理的产品，是 197 个条目拼出来的。

第三个数最有信息量：grep 数开头是 # == 的行，29 处。

每切换一个来源，输出就插一行这种注释，写明这一段来自哪个包，或者被谁改过。整棵树只有六种来源组合，我逐段数了一遍：

dsh-base 原样给的，74 个条目；
dsh-base 给的但被 dsh-web-app 改过的，22 个；
dsh-base 给的但被我自己的 patch 改过的，1 个；
dsh-web-app 原样给的，98 个；
dsh-web-app 给的但被我的 patch 改过的，1 个；
我的 patch 新插进去的，1 个。

加起来正好 197。

那 22 个是我这次读配置最意外的地方：上层 bundle 改了 22 个下层 bundle 插进来的条目。所以这套层栈的动作是"按 id 后写覆盖"，不是把几层排在一起。后面那一层想改哪一行，就照 id 把整块配置重述一遍。

顺带一个会咬人的细节：配置是整块替换，不做深合并。官方给的原话就是"替换整块配置"。这意味着你只想改一个字段，也得把这一整块重写一遍，漏掉的字段就按默认值走。我一开始以为是字段级合并，差点按这个理解去改，后来才养成动配置之前先 dump 一遍对照的习惯。

还有一处我当时看不明白的写法：有一行的禁用字段，值不是 true 或 false，而是一段脚本表达式，判断"当前有没有 profile 上下文"。意思是同一个包在真 profile 里要挂，在被当作 SDK 用的时候不挂。行的顺序不管加载，但这一行的开关是运行期算出来的。

还有一条命令能把自己那层剥掉：加 --dump-default-config，输出 1243 行。2390 减 1243，多出来的 1147 行全是我自己叠上去的。想审计我到底改了什么，这一条命令就够了，不用记。

有个诚实的补充：桌面版 profile 不允许从命令行 dump。我试过，它直接回一句 error: profile "desktop" is managed exclusively by the Electron application。所以上面这些数字来自另一个只装了两个基础 bundle 的 profile，层栈机制一样，层数少一些。

五、第三层：两个半边，加一个注册面

这一段我要先认个错。

我最初的笔记里写的是"host / client / tool 三半"，还挺得意，觉得这个框架好讲。

后来为了引用原话，我把安装包里三百多个官方包的 README 全搜了一遍，专门找 half 这个词。

结果是：host half、Node half、browser half 到处都有；三半、three halves，零命中。官方根本没有这个说法。

再去读开发文档就清楚了：仓库把代码切成 Host 和 Client 两个独立的编译单元，一个包只能进其中一个。为什么必须切两半，文档给的理由很硬——两边都在同一个 Context 接口上做声明合并，但塞进去的是不同的服务；一个编译程序同时看到两套，就会报冲突。

而 tool 不在这套切分里。工具只存在于 host 侧，它注册进 ctx.tools 这个服务，注册之后它的 schema 会自动流进系统提示词的组装。它是运行期的注册面，和编译期的两个半边不是一个层级的东西。

第三方包里有一个文件把两半讲得最清楚：整份 patch 只有六行，三行注释三行内容。注释说，这一行把包的主入口当作宿主半边加载，而 package.json 里的客户端声明，让 Web 应用把它的 client 目录当作浏览器半边加载。

一个 npm 包，一行条目，两半齐了。这是"一切都是插件"的最小完整形态。

所以准确的说法是：两个半边，加一个面向模型的注册面。如果还想把提示词段、会话投影也算上，那是三个面，但它仍然不是三个半。

这个错不大，但我不打算悄悄改掉。因为"三半"很好听，好听到我差点在没核对的情况下写出去。一个读起来顺的框架，往往就是这种错最不容易被自己发现。

六、为什么能这么设计：注册是 effect

到这儿问题变成：凭什么每一样都能换？换掉之后不会留下一个半死的东西吗？

答案在它用的框架里。Cordis 那套东西，官方入门文档列了五条，我认为只有第五条是真正的机关。

前面四条不新鲜：插件是一个实现了服务的对象；context 是一个服务仓库，每个服务占一个固定的键，别的插件按键找，不 import 具体实现；依赖用 inject 声明；插件之间用类型化事件通信。

第五条是：所有注册都是可撤销的 effect。

这一条把"卸载"变成了默认行为。工具、提示词段、模型适配器、事件监听器，全部走 ctx.effect() 或者 ctx.on() 注册，插件被卸载时自动撤销。所以热插拔能成立，原因不在打包工具做得好，在于每一个注册都自带撤销。

它还顺手取消了一个我们习以为常的概念：启动顺序。

我一直以为 YAML 里写在前面就先加载。dsh-base 的 patch 文件里有一句注释直接否掉了这个想法：行的顺序不携带加载语义，激活由服务可用性驱动。官方入门文档说得更清楚：加载顺序由服务依赖表达，而不是手工编排启动序列。

所以你没法用"调整先后"来解决依赖问题，只能老实声明 inject。反过来说，依赖关系就是启动图。

最能说明"换实现"能换到什么程度的，是它自己架构文档里的那个例子：文件系统和进程的提供方共用同一个执行世界，把这两个提供方指向远程沙箱，Bash、PTY、LSP 会跟着一起搬家，而不用 fork 任何一个工具。

这句我读了三遍。它说的不是"你可以写一个插件替代 bash"，它说的是：你把底下的执行世界换掉，上面所有依赖它的工具跟着变，一行工具代码都不用改。

模型适配器也一样：ctx.llm 这个服务本身没有配置、没有 provider 的线上代码，具体翻译留给各自的适配器插件。会话日志是一个服务，agent loop 是另一个服务。这些名字都出现在那 197 个条目里。

自由度这么大，还有没有刹车？有，而且是一条硬约束：会话日志是唯一真相源。

官方把它写成一句话规则——模型能看到的东西，必须能从日志里重建。插件随便换，但"这个模型当时到底看到了什么"永远要能重建出来。已提交的日志不许重命名、替换、删除，要升级就在旁边发一个新版本的孩子。

一边放开换，一边把可追溯钉死。这两件事是配套的，少了后一件，前一件就只是乱。

七、代价：25 个下游 commit，0 个新插件

现在讲那个我觉得官方文档不会讲的部分。

Hacker News 上有个用户 wren6991，2026 年 10 月 2 日的评论，原句我抄下来：

"the problem with Everything Is A Plugin is that when this includes core functionality, you still have to maintain downstream patches for those core plugins if you want to tweak existing behaviour. I currently have ~25 downstream commits and 0 new plugins."

译过来是：一切皆插件的问题在于，当核心功能也算插件时，你想微调现有行为，还是得自己维护针对这些核心插件的下游补丁。他手上有大约 25 个下游 commit，零个新插件。

这条评论比任何夸奖都更有信息量，因为它讲的是账落在谁身上。

"不存在需要打补丁的特权内核"这句话，正面读是自由，反面读是：没有一处改动是官方会替你维护的。你想改的那一行恰好来自 dsh-base，那你的改动就得跟着 dsh-base 的版本走。

官方自己也把这条边界写在明处。插件加载前有一道版本闸门，查的是声明的兼容范围；README 紧跟着一句免责：这些检查不是防恶意代码的沙箱。

再往上，README 开头就写着这是开发者预览，未来会出现破坏兼容性的变更。安全声明更直接：尚未接受安全审计，不得视为可用于生产环境。

所以灵活和稳定在这里是反比，官方明确站在灵活那一边。这里没有对错，只有一个已经做过的取舍，只是账要由用的人来付。

八、我现在的用法

三条，按我自己用下来的顺序。它们只是我的用法，不是标准答案。

第一，判断一个 harness 能不能改，我现在不问有没有插件 API，先问这个能力有没有一个 ctx 键。

有键就有替换点，键就是那道缝。我想换模型选择策略、换存储、换沙箱后端，先去找那个键，再去官方包列表里找提供方。找不到键的地方，才是真正写死的边界。

第二，想改核心行为之前，我先算维护账。

只加一个新工具、加一个界面面板，是在旁边挂一个，成本一次性。要改已有的核心行为，我就进入了 wren6991 那种状态：每个上游版本跟一次。这不是某一家的坑，是这套架构的定价方式。

第三，读别人的配置，我先看来源标注。

29 处 # == 就是一张归属表，能回答三个问题：这一行是谁给的、被谁改过、我自己的改动落在哪一层。想给别人复现问题，我会先贴这张表，比贴一整段配置有用。

官方在 2026-10-31 的《Super-agent 设计探索》里把这件事又往前推了一步：不只是"没有核心"，连会话本身也不该是核心。Router 只负责接人和分派，Worker 才执行，用户面对的始终是同一个 Agent。这篇后面我会专门写（第 25 篇）。

术语小抄

  • harness（运行时）：夹在模型和电脑之间的那层程序，把模型想好的动作真的做出来
  • profile（配置档）：一套插件清单，网页版、命令行版各有一套
  • bundle（包）：可以整块插进配置树的一堆行，插完还能被上层改
  • row（配置行）：树里的一行，一行就是一个挂上去的零件
  • 两半（host / client）：编译期被切成两半，一半跑在宿主，一半跑在浏览器
  • effect（可撤销的注册）：注册的时候，就把"怎么撤"一起写好了

我还没搞懂

  • 一个插件同时有 host 半边和 client 半边时，谁先起、失败了怎么办？我在文档里没找到顺序。
  • 那 25 个下游 commit 的讨论我只读了一条评论，没跟后续，不知道最后怎么收场。
  • 热重载时是先撤后挂，还是反过来？我没做实验，只读懂了"注册即 effect"这一句。
