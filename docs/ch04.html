装 DSH 有三条路，选错那条会浪费你一周

系列第 04 篇 ｜ 版本 v1.2 ｜ 2026-11-08 02:41 ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读） ｜ 修订：改为学习笔记体

先说人话版。这是同一个程序的三张脸：一张在浏览器里打开，一张是装在电脑上的应用，一张是黑窗口里敲完就走的命令。三张脸长得不一样，底子是同一份。我一开始以为是三个东西，装到一半才发现，选错脸比装错版本更麻烦。

我在本机把 DeepSeek Harness 的三种装法各走了一遍。走完发现最费时间的不是安装本身，是装之前没想清楚自己要哪一种。

同一套代码，官方给了三条入口：命令行一行跑起来的 Web 版、下载即用的桌面 App、不打开任何端口的一次性命令行。三条路的门槛、能做的事、踩的坑都不一样。这篇把我查到的官方原话和我机子上真实看到的输出摆在一起，我是拿它来对号的，你也可以照这个法子对。

读完你能做到

  • 在 30 分钟内装好一种形态，并跑出一条屏幕上能看见结果的命令
  • 按三个问题选形态：平时在哪儿用、要不要给别人看、要不要退出码
  • 出问题时先分清是环境、形态还是版本漂移，而不是删了重装

一、我原来的判断

我原来的判断：装 DSH 就是装一个 App。下载、拖进应用程序文件夹、双击，跟装 Cursor 差不多。

现在的判断：DSH 没有"一个装法"。它是同一套代码的三种交付形态，选形态比选安装包重要；形态选错，后面一周都在补。

第二层判断也变了。我原以为三条路是三个成熟度不同的产品——命令行版可能是给开发者试水的半成品。实测不是。官方架构文档写得很直白：web、headless、sdk、sdk-minimal、acp 这几个名字，是"作为模板随发行版交付"的 profile，共用同一层底座。它们是同一栋楼的不同门，不是三栋楼。

所以这篇不按"哪个更好"写，按"哪种人走哪道门"写。

二、先把三种形态摆清楚

第一种，npm 一行跑。官方 README 的原话是：安装 Node.js，然后运行「npx @deepseek-ai/dsh web」。默认在「http://127.0.0.1:3080」起 Web UI，本机启动时还会用默认浏览器把页面打开。通过 SSH 启动时只打印宿主机 URL，因为本地转发地址在 SSH 客户端或编辑器手里。加「--no-open」就只跑服务器、不开浏览器。

第二种，桌面 App。官方产品页给的下载地址就是两个安装包：macOS arm64 的 dmg 和 Windows x64 的 exe。它自带运行时，不需要你先有 Node。

第三种，headless。命令是「dsh --profile headless "run the tests"」，跑完一个任务、打印最终答案、直接退出。没有界面，没有服务器，不开端口。

补一个容易混淆的等价关系：「dsh web」和「dsh --profile web」是同一条命令的两种写法。官方 CLI 的 help 里就是把它当别名举的例子。所以在网上看到别人写「dsh --profile web --port 8080」，跟自己写「dsh web --port 8080」，启动的是同一棵树。

还有一个家族要提一句：sdk、acp、sdk-minimal。官方 CLI 文档说得很清楚，SDK 和 ACP 都是 profile，不是独立的公开可执行命令。sdk 走 JSON-RPC stdio 给 SDK 客户端用，acp 走 ACP stdio 给自动化客户端用，sdk-minimal 是"刻意保留的例外"，一套完整的显式 SDK 配置树，不叠 dsh-base。像我这样不写插件、不做集成的，这三个名字可以一辈子不碰。

三、npm 那行命令：最快，也最挑环境

这行命令的前提只有一句：机器上得先有 Node.js，而且不能太旧。npm 上这个包的 engines 写的是 24.9 以上，官方 release note 里也明写 0.2.2-rc.1 把最低 Node 版本提到了 24.9。我本机默认的 Node 是 v23.11.0——不够。我实际是在桌面 App 自带的运行时上跑的，那个版本是 24.21.0。所以"装个 Node 就能跑"这句话，取决于装的是哪个 Node。

有两处细节官方文档写了，但很容易被当成小事划过去。

一是启动会打印一个带 token 的 URL。这个 token 不是装饰，后面对 API 的每个请求和 WebSocket 流都要用它换会话 cookie。所以那行 URL 我从来不敢随手贴进群里。

二是新装完的界面里没有工作区。官方快速开始的原话是：dsh 进程会把启动时所在的目录作为默认文件系统位置，而全新的 Web UI 不会选中任何工作区，你得自己添加一个；选中工作区之前，会话输入框是不可用的。我第一次遇到时以为是页面没加载完，其实是它故意不替你决定。

这条路的另一个特点，是"版本不由你定"。npx 拿的是 npm 上当前的最新发布版，官方在 npm 上一共发过 42 个版本（GitHub release 是 37 个，两个口径不同），全部是预览版。同一行命令，我这周跑和下个月跑，可能不是同一个东西。想固定，就得自己在项目里装一份、锁版本，这就从"一行命令"变成"一个小工程"了。我本机这套是 0.2.2-rc.1。

想换端口就加「--port 8080」。想绑具体网卡用「--host」，它只接受一个具体的本机 IPv4 或 IPv6 地址，通配地址会被拒。默认只监听 loopback，只接受本机连接。

真正的坑在"3080 是哪儿的默认值"这个问题上——我在下一节讲，因为我第一次也答错了。

四、桌面 App：官方那句"不需要另装 Node"

官方 release note 里有一条，日期是 2026-09-29，版本 dsh-v0.2.0-rc.2，原文是：macOS／Windows 桌面端可在菜单栏中管理和安装 dsh 命令，支持管理插件，无需另装 Node 或 pnpm。

英文版还多一句关键信息：这个命令需要用 "Manage dsh command" 那个菜单项装一次，不是自带就有的。

桌面端 README 把位置写得更细：应用菜单里的「管理 dsh 命令…」就排在「检查更新…」下面，显示当前命令，提供安装、修复、移除三个操作；命令复用桌面端已装的运行时和普通 dsh CLI，桌面应用关掉以后也能用；装完打开一个新终端，跑「dsh --version」。

我本机的实况和这段对得上。应用在「/Applications/DeepSeek Harness.app」，跑「dsh --version」输出 0.2.2-rc.1；「which dsh」指到的是「/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh」，不是任何 nvm 或 homebrew 路径。

我还打开那个 dsh 脚本看了一眼，它最后一行是拿 Electron 自身当 Node 用，带「ELECTRON_RUN_AS_NODE=1」和「--expose-internals」，然后去跑 app.asar 里的 CLI 入口。所以"不需要另装 Node"不是营销话术，是它真的借 Electron 的 V8 跑命令行。桌面端还自带独立的 Python、Node.js 和 pnpm 分发包，机器上没有系统 Python 也能跑 Office 那类任务——按 README 的说法，第一次用到工作区依赖时它会把这套产物离线展开到本机，之后才复用。

代价的一面也得说清楚：桌面端是整包更新。官方文档的说法是，Electron 壳、匹配的 dsh 运行时和 pnpm 组成一个"已签名更新单元"，运行时版本的选择绝不脱离桌面端发布。换成我的话说：想只升 dsh 不升桌面壳，做不到。想踩某个特定版本，桌面这条路给不了我这个自由度。

顺手说一个能对上号的差别：桌面端默认用系统分配的端口。这条是 dsh-v0.2.1-alpha.1 的 release note，理由写得很实——避开 Windows 保留端口范围导致应用起不来。我此刻这个界面跑在 127.0.0.1:50003，用「lsof -iTCP -sTCP:LISTEN」能看到是 DeepSeek 进程占着，不是 3080。官方文档里"默认 3080"说的是 npm 那条路。

五、headless：不打开端口的那种装法

headless 的官方描述，一句话就够了：从命令行跑一个 dsh 任务、打印最终答案、然后退出——没有 GUI、没有服务器、没有浏览器。

它的特点是干净。进程不打开任何端口，也不留任何后台在跑的东西。退出码就是结果：任务完成是 0，中止或出错是 1。要接脚本可以加「--json」拿按行输出的 JSON 事件流，再用事件流里的「--session-id」在同一段对话上继续唤醒。

边界也在同一页里写着，我觉得比卖点重要：每次调用只运行一个任务，没有交互式后续。想追问一句"那第二个文件呢"，得重新来一次。所以它适合 CI、批处理、一次性任务，不适合探索。

凭据这块有个很容易栽的点。dsh-v0.2.1-rc.1 的 release note 原文是：Web 端／桌面端优先采用已保存的凭据；headless 默认改用环境变量和 .env，不读取已保存的密钥。headless 的包文档补充了读取顺序：启动环境、运行目录下的 .env、然后是「$DSH_HOME/.env」。所以你在图形界面里登录得好好的，换 headless 跑同一台机器，会突然提示没有 key。这不是 bug，是它有意隔离。

我本机为了看它的默认配置跑了一次「dsh --profile headless --dump-config」，输出第一段就是 @deepseek-ai/dsh-base 的条目列表。跑之前我数过「~/.dsh/profiles/」里只有两个目录：desktop 和 paseo。跑完之后多了一个 headless——官方说的"首次使用时从随附模板自动初始化"，就是这么发生的，不是我先建好目录。

六、三条判据，你对着选

我要是只想天天用、不想跟命令行纠缠，会走桌面 App。代价是它把运行时、更新、插件都收进自己手里，我能改的边界比 npm 那条路窄。

要在服务器上跑、要给同事演示、或者只是想看看源码版本长什么样，我走 npm 那条路。代价是 Node 版本自己管，升级也自己管。

要进 CI、要写批处理、要一个能返回退出码的命令，headless。代价是没有交互，凭据还要另外配。

我要是冲着写插件来，会先绕开 headless。插件开发的反馈回路靠热重载和界面上的插件页，headless 这两样都没有。

还有一件很多人会问的事：能不能两个都装，会不会打架。官方架构文档的回答是比较克制的：桌面端与 npm CLI 共享产品数据，但包、启用选择和锁文件保持独立。也就是说它们不抢同一份插件清单，但"共享产品数据"这几个字意味着你会在两边看到同一批会话记录之类的东西。我自己没把两边同时开着跑同一个任务，这一条我只敢照抄文档，不算实测。

我给自己留的经验只有一条：按"大部分时间在哪儿用"选，不按"哪个听起来更专业"选。装完发现不对再换，成本比你想的低——因为三种形态共用同一层底座，你在 web 里配过的模型，在桌面端里配的是同一套字段。

七、三个坑，都是真的

第一个坑，抓 deepseek.com 会被 UA 拦。这不是装的时候踩的坑，是查资料时踩的，但我还是留着——因为它决定你读到的是哪一版官方文档。我们采集资料那天（2026-11-08）记录的是：默认 curl UA 访问 deepseek.com 返回 HTTP 429「Request Blocked」，必须伪装成桌面浏览器 UA 才能拿到内容。但我这次复测同一个地址，默认 UA 拿到的是 200。两个结果我都不删：说明这个拦截不是稳定规则，按 IP、频次、时段都会变；我给自己记的教训是：随手带一条浏览器 UA 的退路，200 不能当永远。

第二个坑，desktop 那个 profile 命令行碰不了。我跑「dsh --profile desktop --dump-config」，输出一行「error: profile "desktop" is managed exclusively by the Electron application」，退出码 1。直接「dsh --profile desktop」启动，也是退出码 1。官方 CLI 文档解释了原因：desktop 这个名字保留给 Electron 持有的 profile，CLI 会拒绝针对它的启动和配置 dump 请求。所以你想看桌面端到底装了什么，得换个办法——我是直接读「~/.dsh/profiles/desktop/package.json」，里面列了 12 层组合包，还挂着 dshmarket 和 dsh-context 两个第三方插件。

顺带一句：文档说 npm 装的 dsh 不能修改桌面 profile 的插件。我拿「dsh plugin --profile desktop list」试了一下，读是能读的。所以那个"不能"，针对的是装和改，不是读。

第三个坑，预览版真的会变。README 中文版原话：DeepSeek Harness 处于开发者预览阶段，正在快速迭代，未来将出现破坏兼容性的变更。这不是免责声明套话，是能被数据验证的：GitHub 上 37 个 release 全是 prerelease，stable 是 0 个，平均 2.19 天发一版。我今天装的东西，两周后可能配置项就改名了。安全声明那句更硬：它尚未接受安全审计，不得视为安全或可用于生产环境的软件。

八、我错在哪

我错的第一处，是把桌面版想成"给网页加个壳"。壳是真的有，但更关键的是它把运行时也搬进了自己的包里，连命令行都借 Electron 跑。这意味着桌面版比 npm 那条路更"重"，也更能对付没有开发环境的机器。

我错的第二处，是把"默认 3080"当成通用常识。3080 只是 npm 启动时的默认监听端口，桌面端从 0.2.1-alpha.1 起改用系统分配端口，我眼前是 50003。同一个官方文档，两处说的都对，混在一起就错。

还有一处我选择不写：这篇标题里有"30 分钟"，但我不报"我花了 X 分钟装好"。官方没给过安装耗时，我也没掐表，编一个数字出来最省事也最没用。能确认的只有两件：官方快速开始一页读完就能跑起来，产品页的原话是"现在，开箱即用"。至于花多久，取决于网络和机器上已经有的东西。

最后是适用边界：以上判断只在 0.2.2-rc.1 这个时点成立。版本一换，端口、菜单项、profile 名单都可能动，这也是我在每一处都标版本号的原因。

九、下一步

装完只是开始，第一件让我懵的事通常不是模型，是它一直问我"用哪个工作目录"。下一篇写这个：会话、工作目录、项目身份三者到底什么关系，为什么换个目录它就像换了个人。

落地案例：30 分钟装好，跑通第一条命令

场景：一台没装过任何 agent 工具的电脑，你要在今天之内让它跑起来一条命令，并且知道换机器时该走哪条路。

做法：先花三分钟回答三个问题——平时是不是只在浏览器里用、要不要跑在别人的服务器上、要不要一个能进脚本的退出码。只在浏览器用就下桌面 App；后两个占一个就走命令行。装完先敲 dsh --version 和 node -v，把两个版本号写在纸上。然后跑一条只读命令：让它读当前目录的说明文件，列出其中三个小标题。

验收：dsh --version 有输出，且版本号已经写在纸上；那条只读命令返回三个小标题，你能在屏幕上指着它们念出来。两条都过才算装好。缺一条就停在原地查，不要接着装插件——装插件会把问题搅在一起。

耗时：选形态 3 分钟；桌面 App 预计 10 分钟（含下载），命令行预计 20 分钟（含 Node 版本对齐）。

读完这一篇，你应该能在一个午休的时间里装好一种形态，并跑出一条看得见结果的命令。

术语小抄

profile：一套预先配好的启动组合。官方给了几种模板，选一个模板，就是选一种形态。

bundle：往启动树里叠的一层配置，一叠就是一批插件，可以叠好几层。

自带运行时：桌面 App 里自己带了一份 Node，外面不用再装。

loopback：只允许本机连接的地址，外网进不来。

headless：没有界面、跑完一个任务就退出的一次性跑法。

我还没搞懂

sdk 和 acp 那两条 stdio 通道，跟 web 形态共用同一份会话日志吗？我只看到"共享产品数据"这一句，没实测。

桌面端和 npm CLI 同时开着跑同一个任务会怎样？官方说包和锁文件独立，但共享产品数据，冲突点在哪我没找到。

headless 的凭据隔离管不管插件？文档只写了 API key 的读取顺序。

npm 上 42 个版本、GitHub 上 37 个 release，差的 5 个是什么情况，我没查到。
