我烧了 93 亿 token，只有 0.3% 是它生成的

版本 v1.1 ｜ 时间待补 (Asia/Shanghai) ｜ 依据：官方仓库 docs + 本机 dsh 实测
学习笔记 ｜ 第 6 站 ｜ 我带着的问题：同一套活交给不同的模型和档位，账单能差多少？
读之前我以为：接模型就是填个 key、选个名字，贵一点便宜一点差不到哪去。
读完我的一句话答案：钱几乎都花在反复读上下文上，不在生成上；档位之间能差 10.8 倍。
读完我能答出来的三个问题：1 这 93 亿 token 里，缓存读、未命中、输出各占多少？ 2 同样这组 token，最贵最便宜差几倍、差在哪两个变量？ 3 apiKeyEnv 里该填什么？（答不出就说明我没学会，这篇先不发）
系列第 06 篇 ｜ 版本 v1.1 ｜ 2026-11-08 ｜ 依据：本机实测 + 系列资料 ｜ 修订：改为学习笔记体

先说人话版。我把自己机器上所有聊天记录翻出来，把每次对话用了多少字加了个总。加完发现：模型自己写出来的字只占千分之三，剩下全是在反复读同一堆材料。所以想省钱，第一件事不是让它少写，是让它少读。

我把自己这台机器上 182 个会话的日志全解压了，一条一条把 token 用量加起来。

加完的总数是 93.69 亿。

我本来以为接下来要算的是"花了多少钱"。结果拆开一看，先被另一个比例卡住了：这 93 亿里，真正由模型生成出来的，只有 3000 万，占 0.32%。

这篇讲这个比例是怎么来的，以及它为什么决定了该盯价目表上哪一行。

一、我原来的判断

我原来的判断：接模型是配置环节里最不重要的一步。填个 key，选个模型名，能跑起来就行；反正同一家的模型，贵一点便宜一点，差别不会大到哪去。

现在的判断：选模型等于同时选了两样东西——一条成本曲线，和一条能力边界。而 harness 在这个环节里唯一能替你做的，是把账单记清楚。它记不清楚，我连自己贵在哪都不知道。

这两句话的差距，是一个数量级。

二、我怎么把这笔账算出来的

先说数据在哪。

DSH 的会话日志是只追加的事件流，每条模型回复落成一条 assistant/message 事件，事件里带一个 usage 字段，五个数：输入 token、输出 token、缓存读 token、缓存写 token、总计。

这五个数是适配器从模型返回里取出来的，不是 harness 自己估的。官方给适配器的契约里写得很硬：usage 必须在 finish 之前发出来，finish 之后不许再发任何东西。所以只要日志在，账就在。

我把 182 个会话的日志全部流式解压，扫了 239,762 条事件，其中 28,902 条带 usage。加起来是这样：

输入未命中，1.50 亿。缓存读，91.89 亿。输出，3007 万。缓存写，0。合计 93.69 亿。

三个比例我算了一下：缓存读占总量的 98.1%，未命中输入占 1.60%，输出占 0.32%。

也就是说，我这一整套工作流跑下来，模型真正"想"出来的字只有三千万 token，剩下九十二亿都是它在反复读同一批上下文。

分布还很不均匀。最大的一个会话单独就占了 10.53 亿 token，而中位数只有 578 万——也就是说我一半的会话其实很轻，真正吃钱的是少数几个跑得特别长的任务。

为什么会这样，机制上不难理解。每一步模型都要把完整上下文重新读一遍——系统提示词、全部工具的说明书、之前所有轮次、每一次工具返回的结果。一个任务走三十步，同一段上下文就被读了三十遍。缓存命中省的就是这笔重复读的钱；而没命中的那部分，在 flash 上单价是命中价的五十倍。

这个比例我第一次看到时是有点懵的。因为我的直觉里，"贵"应该贵在生成——生成慢、生成是模型在干活。但账不是这么记的。

三、同一个工作量，价目表上能差 10.8 倍

有了这组 token 数，就可以做一件更有意思的事：把它按官方价目表折算一遍。

我把 2026 年 11 月 8 日抓的官方价格页抄在这里，单位是元每百万 token。两个模型：deepseek-flash 和 deepseek-v4-pro。价格分峰谷两档，空闲时段是高峰的一半；高峰时段是北京时间周一到周五的上午九点到十二点、下午两点到六点。

缓存命中的输入：flash 空闲 0.02，高峰 0.04；pro 空闲 0.15，高峰 0.30。

缓存未命中的输入：flash 空闲 1，高峰 2；pro 空闲 4.5，高峰 9。

输出：flash 空闲 4，高峰 8；pro 空闲 13.5，高峰 27。

现在把我那 93.69 亿 token 按四组价格分别折一遍。

全部走 flash、全在空闲时段：454 元。

全部走 flash、全在高峰：908 元。

全部走 pro、全在空闲：2460 元。

全部走 pro、全在高峰：4920 元。

同样的 token 量，最便宜和最贵差 10.8 倍。等效到每百万 token，从 0.048 元到 0.525 元。

这里我得说清楚一件事：这不是我的账单。我的流量走的是本机一个 OpenAI 兼容网关，不是官方直连，实际扣费和这张表不是一回事。上面四个数是我把同一组 token 量按官方价目折算出来的结果，用途是回答"同样干这些活，价目表上能差多少"，不是"我花了多少"。

但即便只是折算，这个 10.8 倍也够说明问题了：选模型这件事，不是选一个"更好的"，是选一个"我打算为哪种 token 付钱"。

四、所以"接哪个模型"到底是几个决定

我把自己机器上那份模型配置打开数了一遍。配置文件顶层只有一个键，就是这个模型接入插件。它下面挂三个 provider，每个对应一种协议：openai-completions、openai-responses、anthropic-messages。三个加起来 97 个模型条目。

这 97 个条目由网关的模型目录同步进来，我没手写。但每个条目里那几个字段，是实打实决定我花多少钱的：

上下文窗口。我这台机器上最小的一个填 131,072，最大的填 1,048,576。差八倍。窗口越大，单次请求能塞的东西越多，也就越容易把"未命中输入"这一项推高——而这一项的价格是缓存命中的五十倍。

最大输出。我这份配置里从 32,768 到 458,752 都有。它不直接等于实际生成多少，但它决定了单次回复的上限，也决定了你估算成本时的天花板。

输入模态。有的条目写着 text 和 image，有的只有 text。带图的请求贵不贵，取决于走哪个模型。

思考档位。每个模型下面列了 low、high、max 三档，映射到 provider 那边的具体参数。同一个问题用 high 和 max，输出 token 不是一个量级——这一条是社区里关于成本骂得最多的地方。

关键点在于：这些数字不是 DSH 内置的。它们来自我写的 provider 块。官方把这件事交给配置，好处是换一个端点就能换一套目录；代价是没有人替我校验这些数字对不对——我填错了上下文窗口，它也不会拦。

五、凭据是怎么被藏起来的

这一节我犹豫了很久要不要写，因为它的边界很窄。最后决定写，但只写结构。

我那份配置里，provider 块长这样：一个显示名，一个 apiKeyEnv，一个协议名，一个 baseURL，然后一串模型。

注意 apiKeyEnv 这个字段。它填的不是 key 本身，是一个环境变量的名字。真正的密钥在环境变量里，配置文件里只有一个指针。

这个设计有多重要？它决定了这个文件能不能进版本库、能不能备份、能不能截图给别人看。如果 key 是明文写在这里的，上面三件事一件都不能做。

官方的适配器开发文档把这套做法写成了硬规矩：密钥走配置模式的 schema 加环境变量兜底，从配置文件里用 process.env 注入；并且明确写了一句，不要在代码里临时去读密钥文件。

翻译成日常话：密钥只有一个合法入口，就是环境变量。任何"顺手读一下那个文件"的做法，都是自己给自己挖坑。

我自己踩过的坑不在这里，在更蠢的地方——我一开始以为 apiKeyEnv 是填 key 的，把 key 贴进去，然后奇怪为什么认证一直失败。它要的是变量名。这个字段名其实已经写得很清楚了，是我没看。

六、社区那笔账，为什么对不上

讲成本不能不提社区。但社区这几笔账我没法直接拿来用，得先标清楚。

四个流传最广的数字：有人四个任务实测总花费不到 5 块钱，缓存命中率 99% 以上；有人两天半花了快五十块，两个多小时就要充值十块；有人在 Hacker News 上说重度用大概每周 20 美元；还有一篇汇编文章说涨价后总费用是涨价前的约 2.2 倍。

这四个数字全部是自述，没有独立验证。我引用它们，是因为它们能反映体感；我不能用它们，是因为它们缺了最关键的分母。

第一个数"不到 5 块"，前提是缓存命中率 99% 以上。第二个数"两天半五十块"，用的是 pro。第三个"每周 20 美元"，没说是哪个模型。第四个"2.2 倍"，是涨价前后比，但没说是哪个档位。

缺了模型档位、缓存命中率、峰谷时段这三样，任何成本数字都没法横向比。这也正是我上面那组折算想补上的东西：把分母说清楚。

顺带说一个我觉得被低估的事实：官方价格表里，空闲时段的价格是高峰时段的一半。而高峰时段只覆盖工作日的两个时间段。也就是说，同一个任务，半夜跑和上午十点跑，价目表上是两倍。这个差别比大多数人换模型的差别还大。

社区里已经有人做了对应的插件：设一个暂停和恢复的时间窗，高峰时段自动暂停长任务，窗口结束再恢复。这个思路很朴素——拿时间换钱。

七、我错在哪，以及这篇的边界

我错在把"接模型"当成了一个开关。它其实是一个三选一的组合：选协议、选目录、选凭据放哪。三个都选错，它照样跑得起来，然后在一个月后给我一张看不懂的账单。

边界有四条，我一条一条说。

第一，我没做过严格的同任务多模型对比。这篇里所有的成本数字，都是把我已有的 token 量按价目表折算，不是"同一个任务用 A 模型和 B 模型各跑一遍然后比"。后者我确实没做，也不敢拿折算冒充实验。

第二，价格会变。上面所有单价都是 2026 年 11 月 8 日抓的，官方页面自己写着保留调价的权利。这篇文章里的绝对数字，过两个月就不该再引用了，但"缓存读占九成八"这个结构性的比例，短期内不会变。

第三，缓存写那一项，我扫了 182 个会话，全是 0。我不确定是网关没上报，还是这个字段在当前链路里就没被填。所以我的折算里，缓存写这一项按 0 处理——如果真实计费里有这一项，我的数会偏低。

第四，也是最要紧的一条：折算不等于账单。我走的是本机网关，实际计价可能包含网关自己的加价、路由策略、或者压根不走官方价目。任何"我一个月花了多少钱"的结论，只能看账单，不能看折算。

八、下一篇

成本讲完，接下来该讲那个真正决定账单的东西：工具。

一个任务为什么会烧掉几亿 token？因为模型每一步都在决定调哪个工具、等结果、再决定下一步。工具的数量、每个工具的说明书有多长、结果怎么回灌——这些才是账单的第一推动力。

下一篇讲工具系统：它凭什么能读文件、跑命令，以及工具越多为什么首包越贵。

术语小抄

token：模型读写的最小计费单位，可以粗略理解成"字的一部分"。

缓存命中的输入：这段上下文之前已经读过，再读一遍便宜很多。

未命中输入：这段上下文第一次进请求，按全价算。

provider：一个模型接入点，要写清协议、地址、密钥从哪来。

apiKeyEnv：配置文件里只写"密钥放在哪个环境变量"，不写密钥本身。

我还没搞懂

缓存命中率能到 98%，我猜是因为上下文几乎不变，但什么样的任务会打破这个比例，我没有测。

97 个模型条目的上下文窗口是网关同步进来的，网关那边按什么填，我不知道。

峰谷价差两倍，可空闲时段到底按哪个时区算，我没在官方页面找到明确说法。

pro 和 flash 的能力差多少？这篇只算了钱、没算效果，我还没找到靠谱的对比口径。

最后想问你一句：你算过自己的 token 账单吗？

不是"这个月充了多少钱"，是拆开看：缓存命中多少、未命中多少、输出多少。如果你算过，那个比例是多少？如果没算过，你猜你生成的部分占几成？

留言说说。我猜多数人会高估。
