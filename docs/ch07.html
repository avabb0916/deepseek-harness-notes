它没有变强，是有人给了它一张清单

版本 v1.3 ｜ 时间待补 (Asia/Shanghai) ｜ 依据：官方仓库 docs + 本机 dsh 实测
系列第 07 篇 ｜ 版本 v1.3 ｜ 2026-11-08 ｜ 依据：本机实测 + 系列资料
学习笔记 ｜ 第 7 站 ｜ 我带着的问题：模型到底怎么知道该调哪个工具？
读之前我以为：工具就是一个函数，多挂几个就更强。
读完我的一句话答案：它每开一次口，面前都摊着一张五十四到六十四个名字的清单；加工具其实是改它的世界观。
读完我能答出来的三个问题：1 一次请求里它面前摊着多少个工具名？2 注册成功了就等于能跑吗？3 这张清单要不要每次付 token？（答不出就说明我没学会，这篇先不发）

这篇是我自己弄明白的一个小问题：为什么同一个模型，装在这儿显得会干活，换个地方就显笨。答案跟一张单子有关——它每回答一次，手里都摊着一份“我可以做什么”的目录，目录的长短和写法都会影响它。我确实是这么一步步才看懂的。

上周我让 agent 帮我改一个页面。它先读了三个文件，跑了一次类型检查，报错之后又回头读了一遍那个我改过的文件，然后再改。

整个过程我没有教它任何一步。它没有变聪明——它只是在每一步之前，看了一眼手里的清单。

读完你能做到

  • 打开一份自己的会话日志，数出这次请求实际带了多少个工具名
  • 指出一个工具从注册到跑起来要过的关卡，并说出其中任意一关的名字
  • 用一份日志算出你最常用的三个工具，以及它们占全部调用的比例

一、我原来的判断

这一节回答：我原来以为工具就是个函数，错在哪？

我原来的判断：工具就是一个函数。模型想用哪个，就按名字调一下，传参数，拿返回。

按这个判断，工具是"能力"，多一个工具就多一分本事，所以工具越多越好，清单越长越强。

现在的判断：工具是两件事的合并体。它既是模型的能力边界（没注册的工具，模型连它存在都不知道），也是权限边界（注册了不等于能执行，中间还有五道关）。

这两句差得很远。前一句让我以为"加工具"是纯加分；后一句让我知道，加工具的同时我也在给模型改世界观，而且改的是它的注意力预算。

二、转折：我在请求头里数出了 54 个工具

这一节回答：一次请求里，它面前摊着多少个工具名？

真正说服我的是一份自己的会话日志，一次误打误撞。

我在翻自己一份会话日志的时候，撞见了一条请求头记录。它记的是"这一次请求到底发了什么"。里面还有：用的哪个 provider、哪个模型、上下文窗口多大，以及一个我没预料到的字段：工具清单（模型能看见的工具名）。

我把里面的名字打印出来，一共 54 个。bash、read、write、edit、grep、glob、web_fetch、web_search、todo_write、job_output、spawn_teammate、team_task_create……

再翻另一份开了团队那套的会话，是 64 个。

我盯着这两串名字看了很久。因为我平时用的时候，"它会做什么"是凭感觉的；而这条日志告诉我，它每一次开口之前，面前摊着的是一张写着 54 到 64 个工具名的单子。

顺手我又算了一笔账。把那 64 个工具的名字、描述、参数结构序列化成文本，是 55,519 字节。按四字节一个 token 粗估，光这张单子就占了一万四千个 token 左右。

这个数字比任何"工具越多越强"的说法都更有说服力：清单不是免费的，它在每一次请求里都要重新付一遍。

这个字节数我复算过两遍，一开始不信一张清单能有五十多 KB——但它就在那条记录里躺着。

三、工具不是函数，是"名字 + 依赖 + 副作用"

这一节回答：一个工具由哪几块拼成？

我去翻了官方的工具目录。它有一张表，把每个模型可见的工具名，连到三样东西上：它属于哪个插件包、它需要哪些服务、它会写出哪些事件。

右边两列特别说明问题。

一个工具先要"需要"一堆东西。比如 bash 这个工具，需要工作目录、需要工具注册表、需要 shell 执行器、需要系统提示词组装、需要环境变量。少一个，它根本注册不上。

它还要"写出"东西。比如文件系统的工具，写操作会发出写入意图事件；todo_write 会写一条待办事件；job 相关的工具会写后台任务事件。

所以工具的形状其实是个三元组：一个模型看得见的名字，一组它依赖的服务，一串它产生的副作用。

这解释了我以前的一个困惑：为什么有些工具"看起来该有"却没有。答案通常是它的依赖服务没挂上，所以它连注册这一步都过不去。

官方那份目录里，35 个插件包一共贡献了 72 个模型可见工具。而我这台机器的请求头里是 54 或 64 个——差额来自我装了哪些 bundle（一叠插件）、开了哪个预设、挂了哪些外部工具。同一份官方代码，不同的人装出来，模型看到的清单长度是不同的。

四、一次调用要过五道关

这一节回答：从模型开口到结果回来，中间过了几道手？

第二件让我改判的事，是"注册成功"和"能用"根本不是一回事。

我把一次真实调用的记录从头翻到尾。它只有两个事件：调用和结果。中间发生的事，日志不记——但官方那张流水线图记着。

一条调用从模型说出口，到结果回到模型，中间是这样走的。

第一道，记录。调用一发生，先落一条调用事件。也就是说，不管后面成不成，"它想调什么"已经写进日志了。

第二道是策略瀑布（一串关卡）。钩子（外部挂进来的检查）、权限、沙箱都在这里插一脚，各自可以回三个答案：放行、拒绝、或者"问一下"。这条瀑布是协作式的，每一个处理者都可以选择继续往下传，也可以直接截断。

第三道，单调守卫。这是一批"只许否决、不许放行"的检查。它们排在策略之后，作用是给一道兜底的闸——前面所有的放行都可以被它推翻，但没有任何东西能推翻它。

第四道才是真正执行。工具的函数体在这里跑。跑的过程中，文件系统那一层还有自己的关卡，比如写入意图要先过一遍。

第五道是事后处理。结果可以被接受、被替换、被追加上下文，甚至被改成错误——然后才变成那条"结果事件"，回到模型的上下文里。

我原来以为权限是一道门，卡在工具门口。实际上它分布在三个位置：策略瀑布里可以拒绝，守卫里可以否决，文件系统那一层还可以再拦一次。

有一个细节我很喜欢：模型能看到的工具描述，是注册表从定义里"白名单投影"出来的。执行的函数、超时设置、界面渲染回调，这些都不会进入模型请求——只留名字、描述、参数结构。

所以模型看到的永远只是"说明书"，看不到实现。

五、被守卫咬过一次

我遇到的现象是：一次编辑被系统退回。

讲了这么多机制，不如一次真实的事故。

我那个下午在改一个 TypeScript 文件。agent 读完文件、动手改的时候，返回了一条错误。原文我抄在这里：

cannot edit "<路径>/rapworks/lib/site.ts": file changed since it was read — re-read the file, then retry。

意思是我在它读完之后又动过那个文件，所以它的编辑被拒绝了。

这条错误不是权限拒绝，也不是沙箱拦截。它是文件系统那一层的"先读后写"检查：它手里那份内容已经过期了，先去重读。

我当时的反应是有点恼火——它明明已经把文件内容打给我看了。但换个角度想，这条规则救的正是"agent 拿着旧内容覆盖掉我新改动"这种最难发现的事故。

有意思的是，官方工具目录里说，这条策略是由一个独立插件提供的，而随发行版交付的组合默认把它关着。也就是说，产品默认不拦，是我这套装法把它打开了。这件事我没有深究，只记下来：同一份代码，不同组合，安全等级是不一样的。

那一份日志里，2351 次配对成功的调用，只有 17 次以错误收场，占 0.7%。这 17 次里，我印象最深的就是这条。

六、工具多，会稀释注意力

这一节回答：工具越多，注意力为什么会被摊薄？

第三件事是我自己数出来的，也是这篇我最想记住的。

同一份会话日志里，2351 次调用的分布是这样的。bash 1821 次，后台任务输出 200 次，读图 145 次，写文件 43 次，抓网页 27 次，搜索 15 次。

bash 一个人占了 77%。

再往下拆一层会更清楚：那 200 次后台任务输出、145 次读图、43 次写文件，绝大部分是我并行跑几个 agent 时留下的痕迹。真正"写代码"的动作只占很小一块，剩下全是跑命令、等输出、看结果。

这个分布说明一件事：它做的事绝大部分是"跑命令",不是"思考"。而清单里另外 50 多个工具，在这个会话里的出场率接近于零。它们一直在每次请求的 token 账上占着位置，却几乎没被用到。

所以"工具太多会稀释注意力"这句话，在我这里不是感觉，是一个能算出来的账。清单越短，留给正事的上下文越多；清单越长，模型在选工具这件事上要做的判断越多。

官方的极简模式就是这个道理的实验版。我打开它的配置看过：它只挂了一个文件工具的配置行，而且把读、写、改三个开关全关了，只留一个读图；再加一个持久 bash。模型面前就两个工具。

我拿它和标准预设对比过。标准预设里挂着 18 个工具配置行，展开成模型看到的工具名，是五十多个。

这里我要老实说一句：我看到有第三方实测写"极简模式 2 个工具、标准模式 26 个工具"，但我自己机器上标准是五十多个，对不上。我猜是版本不同、或者他数的是另一个预设。所以我这篇里用我自己数出来的数，不引用那个 26。

七、我错在哪，以及这篇的边界

这一节回答：这篇哪里我还没验完？

我错在两处。

第一处是把"工具"当成能力单位。工具其实是"能力 + 依赖 + 副作用"的打包，我加一个工具，同时也加了它的依赖负担和它的越权可能。

第二处更具体：我以为"注册成功"就等于"能用"。查过流水线之后我才明白，注册只是让它进了清单；能不能真的跑，还要过策略、守卫、审批、文件系统四道关。任何一道关都可以让它失败，而失败的原因会写在结果里，不会写在注册里。

边界我也列一下，四条，都是我暂时回答不了的。

第一，模型什么时候选择不调工具，我没有做过系统实验。我能看到"它调了什么"，看不到"它考虑过什么又放弃了"。清单的长度对选择准确率的影响，我只能给出上面那个 token 账，给不出准确率曲线。

第二，我统计的是我自己这一台机器上的一份会话。工具集、预设、挂的 bundle 都和别人不同，所以 54、64、2351、77% 这些数，都只对这台机器成立。

第三，时间中位数是一千四百毫秒，平均却是一万九千毫秒。这两个数差十三倍，因为我这里有一次等后台任务等了六百秒。平均数在这种长尾分布里几乎没有意义，我以后会只报中位数和最长值。

第四，那个"一万四千 token"是用四字节一个 token 粗估出来的，我没有用真实分词器算过。所以它只能当量级看，不能当精确值——这一条我自己标出来，免得被人当账本引用。

落地案例：先让它报清单，再看它照不照做

场景：我想让它今天只干读文件这一类活，不想它顺手联网或者写盘。口头说一句"别乱来"没有用，我要一张能对的清单。

做法：新开一个会话，第一句就让它把此刻能看见的工具名全列出来，按字母序，一个不漏。然后我去配置里删掉三个不该出现的名字对应的行，重开会话，让它再列一遍。最后给它一个小任务：说出 tools 目录下有几个文件。我去日志里的请求头核对数量。

验收：两次清单的数量差，正好等于我删掉的行数；那个小任务只调了清单里的名字；日志里的工具数，和它自己报的一致。三条里有一条对不上，说明清单不是它真正看见的那张。

耗时：第一次 30 分钟（大半花在找那三行配置），之后每次 6 分钟。

读完这一篇，你应该能自己数出一张工具清单，并验证它是不是照着这张清单在调。

八、下一篇

下一篇往下拆一层。既然工具是靠"注册"进清单的，那注册这件事本身是怎么被撤销的？为什么它能做到中途卸掉一个插件，而界面和历史都不乱。

最后想问你一句：你有没有翻过自己的请求头，看它一次摊开了多少个工具？如果里面有哪个工具你从来没见过它用，你会留着自己安心，还是删掉省 token？留言告诉我，我想知道自己是不是装多了。

术语小抄

工具清单：这次请求里模型能看见的工具名，随请求发出去，每次都要重新付 token。

工具注册表：所有工具的登记处；注册进去才进清单，能不能跑另说。

策略瀑布：调用前的一串关卡，每个都能放行、拒绝或问一句。

单调守卫：只会否决、不会放行的兜底检查，排在策略后。

白名单投影：只把名字、描述、参数投给模型，实现细节留在后面。

我还没搞懂

一，模型什么时候选择不调工具，我完全没有观测手段。我能看到它调了什么，看不到它放弃过什么。

二，五十四和六十四这两个数的差额，到底由哪几层配置决定，我没有逐层拆开验过。

三，那张清单一万四千 token 是我按四字节一个 token 粗估的，没用真实分词器算过。

四，第三方实测说极简模式两个工具、标准模式二十六个，和我数出来的五十多个对不上，我猜是版本或预设不同，没去核实。
