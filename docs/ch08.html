上下文不是聊天记录：我拆开了自己的会话日志

版本 v1.3 ｜ 2026-11-08 02:43 (Asia/Shanghai) ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）
系列第 08 篇 ｜ 版本 v1.3 ｜ 2026-11-08 02:43 ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）
学习笔记 ｜ 第 8 站 ｜ 我带着的问题：它把我俩的对话存在哪儿了，存成了什么样？
读之前我以为：一次聊天就是一个文件，压缩就是把旧内容删掉换个摘要。
读完我的一句话答案：它只往一本账上追加，压缩只是在上面盖一张“这段看不见”的条，界面是另外折出来的。
读完我能答出来的三个问题：1 被压缩掉的那段，原文还在吗？2 界面上“上下文用了多少”是谁算的？3 已提交的日志能不能改名或覆盖？（答不出就说明我没学会，这篇先不发）

起因特别小：我想知道它到底记不记得我昨天说过的话。结果打开文件夹，看见一堆名字很长的二进制文件，只能硬着头皮学怎么解。下面这些是我学会的，不是教程，是我自己的笔记，顺序就照我当时的困惑排。

我解压了一份自己的会话日志，本来只想看看它多大。

zstd 一解，3638 条事件（一行一条记录）。我往下翻，找到序号 2604 的那条压缩记录。它排在这份日志的第 2606 位，后面还有 1032 条，前面那两千多条也一条没少。

我盯着那两条数字看了很久。因为在那之前，我一直以为"压缩"就是聊天记录被摘要顶掉了。

读完你能做到

  • 找到本机的会话日志目录，解压任意一份，数出它有多少条事件
  • 说清"压缩"在这套系统里改了什么、没改什么
  • 从一次请求的 token（模型计字数的单位）账里，指认出占比最大的那一类

我原来的判断

我原来的判断：上下文管理就是压缩摘要。聊得太长，总结一下，接着聊。

现在的判断：上下文管理是两件工程活——日志怎么记，投影怎么折。压缩只是日志里多出来的一条事件（就是序号 2604 那条），不是机制本身。

这两个判断的差别，不在措辞上。前者让我以为旧内容"没了"，后者让我知道旧内容一直在，只是被标成"看不见"。

一条官方的硬规则

这一节回答：日志凭什么算唯一真相？

官方架构文档里有一句话，我第一遍读的时候没在意：

The session log is the source of the context the model sees.

后面紧跟一句更硬的：Model-visible means logged。仓库里的 AGENTS.md 把它写成了双向的：Model-visible ⟺ logged。意思是凡进入模型请求的东西，都必须能从会话日志重建。反过来，没能落成日志的新输入，不许进请求。

我的翻译是：日志不是"顺便存的聊天记录"，它是唯一的真相源。模型此刻看见的上下文，是从日志里算出来的，不是另外存了一份。

这条规则解释了很多我以前看不懂的设计。比如为什么界面的增量要靠实时事件推，而历史永远从日志派生。原因很简单：如果界面自己存了一份状态，那它就变成第二个真相源了。

我打开一份日志，看见的不是聊天记录

这一节回答：日志里到底存了什么？

先给量级。这台机器上，按会话分的日志目录，主工作区 182 个（另有 4 个在 bot 工作区，合计 186）。投影缓存那边合并计数也是 186，两个数都对，口径不同。这些目录占了 236MB 上下（我写这句的时候它还在长），全部是压缩过的。文件名统一是 session.v4.jsonl.zstd，最大的一个 16.4MB。

把它们全解压、按事件类型数一遍，总共 233,532 条事件。排在前面的类型长这样：

工具调用和工具结果各三万多条。步骤开始和结束各两万八千多条，助手消息两万八千条。后台任务注册与结算各两万一千条，用户消息五千五百多条，轮次开始一千九百多条。

还有几个我没想到会存在的：沙箱模式、审批策略、模型选择、标题、请求头、请求上下文、压缩开始、压缩结束、压缩摘要、压缩剪枝。

两个细节值得单独说。

第一，用户消息和助手消息的比例大约是 1 比 5。也就是说，我每说一句话，它平均要动五步。这个比例说明我看到的界面不是"对话"，是一段有起点、有步骤、有终点的执行记录。

第二，工具调用和工具结果都在日志里，成对出现。所以"它到底动过什么"是可以查的，不用从我的记忆里还原。

请求上下文这一条，我一开始完全没看懂。它里面写着这次用的哪个 provider（模型供应商）、哪个模型、上下文窗口多大。也就是说，"它这次是在多大的窗口里干活"这件事，历史上是有记录可查的。

压缩不是删除，是遮蔽

这一节回答：压缩到底动了什么？

回到开头那份日志。

序号 2604 的那条压缩摘要，字段里写着三样东西：被遮蔽的事件编号、被遮蔽的区间、被遮蔽的 token 数。具体数字是 446 条事件、217,168 个 token。区间从第 8 条到第 1518 条。

关键词是"遮蔽"（标成看不见，不删）。摘要事件记的是"这段我看不见了"，而不是"这段没了"。所以那条摘要之后，日志还能继续长到 3638 条，被遮蔽的那些事件也还在原地躺着。

我把 182 份日志里所有压缩相关的事件都数了一遍：压缩开始 39 次、压缩结束 39 次、压缩摘要 38 次、压缩剪枝 438 次。

这个分布很有意思。开始和结束几乎总是成对，摘要有 38 次——有一次开始没留下摘要，可能是被打断了。而剪枝有 438 次，比摘要多十倍，说明大部分压缩动作是"一条一条地遮蔽"，不是每次都写一份大摘要。

官方 changelog 里也能对上：2026 年 10 月 14 日那个版本加了长对话自动压缩，同时给了手动压缩命令。也就是说，压缩在它这里是一个有事件、有开始、有结束的操作，不是后台默默改写文件。

为什么必须是只追加

这一节回答：为什么它宁可只追加？

把这两件事放一起看，只追加（只往后写，不改旧行）这个设计就不难理解了。

如果日志可以被改写，那"模型当时看见了什么"就永远说不清——我只能相信最后那一版。而只追加的日志，任何一个时刻的上下文都能重新算出来，出了问题能对比、能回放、能追到具体哪一步。

代价也很实在，我踩过三个。

第一，文件只长不缩。182 个目录 228MB，压缩管的是"模型看不见哪一段"，不是管磁盘。所以我用的时间越长，这个目录越沉。

第二，它会拒绝我的一些本能操作。想"清理一下日志"这种想法，在它的世界观里不存在——我能做的只有旁边发布一个新版本，然后让旧版本继续躺着。

第三，读它需要工具，也需要挑版本。我第一次打开时不知道要解压，也不知道有一到四代格式的区别，拿到的是一堆二进制。

我看到的界面，是投影，不是真相

这一节回答：界面上的数字是谁算的？

会话之外还有一层东西，叫投影（从日志折出来的视图）。

第一次看到这个词我以为是什么花活。直到我发现，存储目录里每个会话对应一个缓存文件，里面是 32 个键。键名包括标题、待办、计划、子代理目录、模型选择、权限状态、沙箱模式、上下文压力、上下文分解、上下文时间线、上下文活动……

每行都是三段：版本号、事件序号、值。

我盯着"上下文时间线"那一行看了半天。它的版本号是 38。然后我去翻了 dsh-context 这个包的源码，里面声明的正是 stateVersion 38。

两个 38 对上了。这意味着第三方插件声明一个版本号，落在这台机器的磁盘上就是那个数字——插件不是"外挂功能"，它参与了产品内部的数据模型。

再看那一行里的内容：每一次模型请求的总 token、提示 token、属于第几步、耗时；按类别拆开的 token 账（用户、注入、技能、助手、工具）；甚至有每次注入的名字，比如 AGENTS.md、运行环境快照、技能目录、时间上下文。

所以界面上那个"上下文用了多少"的显示，不是模型自己报的，是从日志里折出来的。

官方包 README 里有一句话把这个关系讲得很清楚：域插件注册单元，承载方读快照并订阅变更流，两边互相不认识。

我的理解是：日志是原料，投影是加工出来的视图。我想多一个视图，就多注册一个投影，原日志一个字都不用改。

代价在版本号上。折叠逻辑一改就得升版本号，升错了，客户端拿到的旧快照跟新事件就对不上。这种问题不会报错，只会在界面上显示一个奇怪的数字，让我怀疑自己看错了。

分叉和续接，复制的是血缘

这一节回答：分叉到底复制了什么？

日志的第一行不是消息，是一条会话声明。里面除了编号、创建时间、工作目录，还有三样我第一次见时愣了一下：父会话、来源、委派深度。

我随手翻到的那份，来源写着子代理，委派深度 1，父会话指向另一份日志。也就是说，这份日志从出生起就声明"我是谁生的"。

另一个字段更有意思：继承的事件数，值是 0。

所以分叉（从旧会话分出一支）不是"把聊天记录复制一份给我"，而是"新日志声明自己的父亲是谁，并记下继承了多少条事件"。日志之间靠血缘连起来，不靠复制粘贴。

本机 182 个目录里，有 36 个是带 session 前缀命名的。我没有去逐个确认这 36 个是不是都是派生出来的——这一点我不确定，先记在这里。

版本：已提交的文件不重命名

这一节回答：升级会不会弄丢历史？

本机这 182 份日志，全部是第四版格式。没有一份还叫 session.jsonl 的旧名字。

官方的升级路径是这样的。最早的明文 session.jsonl 是 v0，之后是 session.vN.jsonl，可选 zstd 压缩。已经提交的某一代日志，绝不被重命名、替换、删除。迁移的做法是在旁边发布一个新的版本命名的后继。每个相邻的迁移包只负责一步，从 vN 到 vN+1。

这条约束比"一切皆插件"更硬。插件随便换，但"模型看到过什么"必须永远可重建。

对我这种把活长期挂在上面的人来说，这句话的实际意思是：升级不会让我丢历史，但会让我多出一堆版本号。回头读的时候得挑对版本，不然会读到半截。

所以什么时候该开新会话

这一节回答：什么时候该换会话？

我把上面这些揉成四条判据，现在每次动手前会过一遍。

一、看上下文压力。压力是投影里的一行（32 个键里那个叫上下文压力的），看得见。到线之前换会话，比到了线之后被压缩一次要省事。

二、看任务换没换。一个会话里干两件事，日志会变成两段互相污染的上下文，读回来的时候分不清哪句是给哪件事说的。

这条是我吃过的教训。我本机最长的一份日志走了 2312 步，后来我自己都不愿意打开它。不是因为它坏了，是因为它太长了，长到我读不动，模型每次也只能看见其中一段。

三、看要不要复现。要复现就给它一段干净的日志和一个明确的起点，别让它在一万条事件里找今天这一句。

四、看要不要留证据。要给人看过程，就得确认压缩事件在哪一段、遮蔽了多少；不然我拿出来的"完整过程"其实是打过折的。

还有一条不上台面的土办法：动手前先决定"这段历史归谁"。归我的，开新会话；归任务的，接着往里写。

反过来也成立：我也提醒自己别为了干净就随便开新会话。新会话有成本——它不认识这个项目，也不记得上一轮为什么改了那一行，得重新读文件、重新听我讲一遍。同一件事没做完就换，我把这叫自找的返工。

我错在哪

第一处错，是我以为摘要顶掉了旧对话。基于这个错判，我以前有个很浪费的习惯：觉得早前的细节"已经没了"，就让模型重新做一遍。实际它还在日志里，只是被遮蔽了。我本可以去查，而不是重做。

第二处错，是我把投影当缓存，觉得是可以随手删的性能优化。它不是缓存，它是恢复的依据。删掉之后重建不出来，界面上的历史就断片了。

第三处是边界，不是错。日志可回放，不等于可读。二十三万条事件我并没有通读，真正认真读的是三份日志的开头，和一份小会话的全篇。三千多条那份，我读到三百条就开始靠检索了。所以这篇里关于压缩的描述，是从事件字段推的，不是我逐条读出来的。

第四处也是边界。投影是插件提供的，插件写错，恢复出来的状态就错，而日志本身还是对的。这种 bug 最难查：证据是对的，结论是错的。我自己写插件的时候就犯过同类毛病——没读契约就按印象写，返回值形状都不对。

官方在 Super-agent 文章里还给了另一个角度：把上下文窗口当缓存。近期可能用到的信息直接内联，超出预算或低频的内容溢出到窗口外、只留引用。再用对象 ID 串成召回链，需要时一跳一跳找回来。这比"压缩摘要"更彻底，我把它记在第 25 篇。

落地案例：翻自己的日志，看上下文花在哪

场景：我总觉得上下文用得快，但说不上快在哪。界面只给我一个百分比，我要知道那几万 token 具体分给了谁。

做法：先找到会话目录。本机在用户目录下的 .dsh/storages 里面，挑一份最大的 session.v4.jsonl.zstd，用 zstd -d 解开。然后在里面找请求上下文和上下文时间线这两类记录，把每次请求的提示 token 抄出来。按用户、注入、技能、助手、工具五类分开，排成五行。最后挑最大的那一类，问自己一句：它该占这么多吗。

验收：能报出这份日志里最大的一类是什么、占多少；能指到某一次请求的具体 token 数；如果最大的一类和你猜的不一样，把它记下来，下次别再靠猜。

耗时：第一次 40 分钟（多半花在找目录和装解压工具），之后每次 10 分钟。

读完这一篇，你应该能不看界面，用自己的日志回答"这次上下文花在哪了"。

下一篇

下一篇拆那个反复出现的词：一切皆插件。

我会把一个插件的注册、服务、可撤销效应讲清楚，也会解释为什么它敢说"没有特权内核"。

术语小抄

会话日志：按事件一条条追加的文件，没有“保存”这个动作，发生一条写一条。

只追加：只能往后加，已经写下的那一代不许改名、替换、删除。

遮蔽：把某段标成“看不见”，原文还在文件里，token 数也记着。

投影：从日志折出来的视图，界面读的是它，不是日志本身。

事件序号：每条事件的编号，剪枝和摘要都靠它指明“遮的是哪一段”。

代际：日志的格式版本，第 0 版叫 session.jsonl，第一版起叫 session.vN.jsonl。

我还没搞懂

一，什么时候自动压缩、什么时候只写摘要，这条线画在哪，我没找到。官方只写了“长对话自动压缩”。

二，扉页里那个“继承的事件数”，我看到的都是 0，分叉到底继承什么，我没想明白。

三，182 个目录里有 36 个带 session 前缀，我猜是派生出来的，但没逐个确认。

四，投影的版本号如果升错，界面会显示成什么，我只能推测，没有复现过。
