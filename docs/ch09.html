为什么 DSH 敢让你中途卸掉一个插件

版本 v1.1 ｜ 2026-11-08 02:41 (Asia/Shanghai) ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）
系列第 09 篇 ｜ 版本 v1.1 ｜ 2026-11-08 02:41 ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）
学习笔记 ｜ 第 9 站 ｜ 我带着的问题：为什么它敢让我在跑到一半时把插件摘掉？
读之前我以为：插件是挂在主体边上的配件，挂上去容易，摘下来一定留疤。
读完我的一句话答案：每一次注册都自带一句“怎么撤销”，摘插件等于照账本一条条擦掉。
读完我能答出来的三个问题：1 卸载插件时它注册的东西靠什么收回？2 配置里写在前面就先加载吗？3 它凭什么敢说“没有特权内核”？（答不出就说明我没学会，这篇先不发）

我给 DSH 写过一个小插件，一百一十一行，装上去能跑，后来觉得没用就卸了。卸完我盯着界面看了半天——它注册的那个工具真的不见了，也没留下什么要我收拾。我不太信，就去翻它是怎么做到的。这篇是我顺着这个问题挖下去学的，不是教程。

没有重启，没有残留，也没有"请删除缓存后重试"。那个工具从模型的能力列表里消失，就像从没出现过。

这件事看起来小，其实是整套架构的分水岭。我见过的多数"插件系统"做不到：插件是挂件，挂上去容易，摘下来会留疤——配置项留在文件里，监听器没人回收，热重载之后行为变得古怪。

DSH 能摘干净，靠的不是打包工具做得好，是它底下那套框架的一条规则：「所有注册都是可撤销的 effect」。这篇就讲这条规则怎么落地，以及它的价格。

顺带说一句：这台机器启动时的插件树有 197 个条目，全部由这条规则拼出来。为什么数量本身不重要，后面会讲。

一、我原来的判断

我原来的判断：插件化就是多留几个扩展点。像 VS Code 那样，核心功能写死在里面，边上开几个口子，让人挂点东西上去。插件是配件，是挂在车上的行李架。

所以我第一次听说 DSH 的"一切皆插件"，反应是：哦，口号。谁不这么说。

现在的判断：插件化不是数量词，是动词。它指的是把产品的每一块都做成"可撤销的注册"，包括那些我以为一定是核心的部分。代价是——没有任何一处，官方会替你维护。

这两句差多远，得从那四个导出说起。

二、一个插件到底要交什么

官方开发文档给的最小插件，只有三样东西。

第一样是名字，一个字符串，说明这个插件叫什么。

第二样是依赖声明，叫 inject，写清楚"我需要哪些服务已经在了，我才能干活"。

第三样是一个函数，叫 apply，框架加载插件时会调用它，并且传进来一个上下文对象。

官方的原话很短：插件就是一个导出了 apply 函数的模块，框架在加载时调用它，插件通过这个上下文对象注册自己的能力。

注意"注册自己的能力"这个说法。后面整篇都围绕它。

除了这三样，包里还有一个 npm 字段，写着一个标记，声明"我是一个 DSH 插件"。宿主读这个标记来识别，命令行工具也靠它来决定能不能装。

这里有个区分很容易搞混，但很实用：插件和 bundle 不是同义词。

插件是一个能挂载的模块。bundle 是一种能一次插进一堆条目的分发格式。自己写的插件通常只有插件标记，得手动在配置里加一行把它挂上去；而一个 bundle 可以被自动叠进层里，不需要我手动改任何文件。

我用配置审计命令数过一次自己这台机器上的启动树，展开之后是 197 行插件条目。这 197 行没有一行来自那个空文件，它们是从几个 bundle 的配置里叠出来的。空的那个只是"用户层"，它没有话说，所以是空的。

三、apply 里到底在干什么

抽象讲没用，拿我自己的插件说。

我给自己的工作流写过一个插件，111 行。名字叫 linkdesk，声明的依赖只有一个：工具注册表。

它的 apply 函数里，从头到尾只做一件事——注册一个工具。

注册的时候要交代四件事。

第一件，这个工具叫什么名字。这个名字是模型看到的，不是人看到的。

第二件，一段描述。模型读这段描述来决定什么时候用它、怎么用它。描述写得含糊，模型就用得含糊，这是工具设计里最容易被低估的一环。

第三件，参数。我这个工具有两个：一个动作名，必填，只能是几个枚举值之一；一个条数上限，可选，不填就是 10。

第四件，一个执行函数。它收到参数，去跑一条命令，把输出的前几行带回来。

就这样。apply 执行完，函数返回，它不持有任何状态，不留任何全局变量，也不记住自己注册过什么。

这一点我第一次读的时候觉得平淡，后来才意识到它有多重要：如果 apply 结束后插件不留状态，那"把它卸掉"就成了一件可能的事。留了状态的东西是卸不干净的。

四、注册即撤销：这才是热插拔成立的根因

DSH 的文档里有一句话，我认为是整个架构的地基：所有注册都是可逆的副作用。

具体怎么实现？插件注册任何东西，都要通过上下文对象的一个提交方法，把"怎么撤销这件事"一并交上去。框架替我记着这笔账。等这个插件被卸载，框架按注册的逆序，一条一条执行那些撤销操作。

逆序这件事不是随手定的。后注册的先撤销，是因为后面注册的东西往往依赖前面的——先拆依赖方，再拆被依赖方，才不会拆到一半发现有人还在用。

还有一条更硬的约束：在一个已经销毁的上下文上再注册，会直接抛错，不会静默成功。这条约束把"插件已经死了但还在偷偷注册"这类问题堵在门口。

所以热插拔能成立，根因不在打包工具做得好，在于每一个注册自带撤回。

我原来以为热插拔是工程上的锦上添花：能热更新当然好，不能也照样用。现在我认为它是这套设计能不能自洽的分水岭。因为一旦有一部分注册是不可撤销的，我就永远不敢真正卸载任何东西，"一切皆插件"立刻退化成"一切皆预装"。

五、ctx 上的每个键，都是一条缝

现在说那个上下文对象。

它不是一个空壳。它是一袋服务。工具注册表占一个键，模型调用占一个键，会话日志占一个键，文件系统、shell、沙箱、存储、浏览器模块，各占一个键。

一个键就是一个可替换点。因为插件之间不互相引用具体实现，它们只按这个键去找服务。

官方管这种可替换的能力叫缝，并且给了一个很严格的三角定义，缺一个都不算：

一是服务定义，它拥有那个键，也拥有相关的类型词汇；二是提供方，一个或多个，负责真的实现；三是消费者，一个或多个，注入这个服务来用它。

有个细节我觉得很能说明设计者的态度：服务定义必须是一个抽象类，官方明确写了"绝不是一个 TypeScript 的 interface"。

为什么？因为 interface 在运行时是不存在的，它只是编译期的契约。而这个键需要有一个真实的对象去占住，需要在运行时被注册、被查、被替换。用 interface 写不出这套东西。

这个三角最值钱的地方，是那句我抄在笔记里的话：文件系统和子进程的提供方共享同一个执行世界，所以把它们指向一个远程沙箱，Bash、终端、LSP 会跟着一起搬过去，不需要为任何一个工具做分支。

换一个实现，整条链路的行为跟着变，而工具那一层一行代码都不用改。

我在别的项目里见过太多反过来的写法：想换执行后端，得去改每个工具的调用处，改完再补一堆 if。这里不用，因为工具只认识那个键。

六、没有加载顺序，只有服务依赖

这一点我错得最彻底。

我原来以为，配置文件里谁写在上面，谁就先加载。这是绝大多数工具的行为，我下意识就这么以为了。

DSH 不是。官方在配置文件里留了一行注释，写得很直白：条目的先后不携带任何加载语义，分组只是给读的人看的。

那顺序由什么决定？由服务可用性决定。

一个插件声明了它需要哪些服务，框架就让它在原地等，等到那些服务都在了，才激活它。所以顺序不是排出来的，是算出来的。

换句话说，启动图就是服务依赖图。

这个设计有几个连带的好处：配置可以乱序写，不影响结果；某个服务晚到也没关系，等它的人会一直等着；依赖谁写清楚了，卸载的时候就知道该先拆谁。

但它也有一个不那么舒服的代价：我没法靠"把它放在前面"来抢优先级。想抢，只能老老实实声明依赖。

我花了一点时间才接受这件事。它把"位置"这个隐式的、好用的、大家都会用的手段拿走了，换成"声明"这个显式的、麻烦的、但可验证的手段。

这大概是整套设计的一个缩影：所有隐式的手段都被换成了显式的声明，代价是写的时候更啰嗦，收益是读的时候不用猜。

七、把框架层买断：Cordis 是怎么被吃进仓库的

DSH 底下这个插件内核叫 Cordis。它比 DSH 早四年，2022 年 4 月就在 npm 上发了第一个版本，到现在一百六十多个版本。

一般项目怎么用框架？写进依赖列表，npm 装下来，版本用波浪号锁一下。DSH 不是这么干的。

它把 Cordis 的源码拷进了自己的仓库，放在一个专门的目录下，一共九个目录：七个 Cordis 包加两个基础库。而且全部改了包名的作用域，从 Cordis 自己的名字改成 DeepSeek 的名字。

改包名这件事，看起来只是贴个标签，其实是宣布主权：这一份，我负责。

更说明问题的是那份改动日志。编号已经排到 V27，目前还活着 20 条改动，下一条是 V28。规则写得很硬：每一条与上游的分歧都必须列出来，编号永远不许重排、不许复用；差异消失的条目会被删掉，但那个编号不再给别人。

我翻了几条，都挺具体。比如有一条是给插件生命周期加加固，堵掉三个重入销毁的缺口；还有一条是给内核补文档注释，原因很实在——文档站的接口生成器遇到没写注释的成员会直接报错。

这两条放在一起看很有意思：一条修正确性，一条修工具链。没有一条是为了顺自己的手，都在真的维护这一层。

官方的理由是"让 harness 完全拥有自己的框架层"，括号里三个词：可审计、可打补丁、可锁定。

我信这个说法，因为它和那个空配置文件是同一件事的两面：如果我连框架层都要自己拥有，那产品里当然没有哪一块是"官方的、我不能动的"。

八、这套模型的价格

说了这么多好处，得说价格。这套模型对插件作者的要求，比"写个扩展"高一个量级。

第一，我得懂可撤销。我注册的每一样东西，都得想清楚卸载时怎么收回。想不清楚，写出来的就是一个只能装不能卸的插件。

第二，我得懂服务依赖。我注入的服务如果被别人换掉了，我的插件还成不成立？这个问题在写的时候就得回答。

第三，也是我自己栽过的：手里得有契约。

我那个 111 行的插件，写的时候手里没有权威的工具定义文档。为了让它在不同版本上都能注册成功，我在代码里写了三种签名变体，一个个试过去，哪个不报错用哪个。

这个做法很丑，但它精确地复现了一件事：没有契约的时候，人就是靠猜的。而官方的类型定义一直都在包里，一个 import 就能消掉全部猜测。

我后来对照官方契约逐条核了一遍自己那个插件，契约层面错了三项：返回值格式错了，报错方式错了，该声明的输出结构压根没写。

我那个插件到现在还能跑，但它跑在一个"我猜对了"的基础上，不是"我写对了"的基础上。

对只想装着用的人，这套模型也是负担。官方自述过一个数字：大约六成用户至少装了一个第三方插件（单条官方推文，我没有找到第三方复核）。而按官方安全文档的描述，插件能执行模型生成的命令、读写向它开放的文件——它不是一个受限的扩展点，它是能和我的文件系统说话的东西。

官方在版本闸门那里写了一句很诚实的话：这些检查是兼容性检查，不是防恶意代码的沙箱。

装插件是在信任作者，不是在信任一个沙箱。

九、我错在哪，以及这篇的边界

我错在把"插件化"当成了数量词。以为插件越多越插件化，以为留的口子越多架构越开放。

不是。真正的分界线只有一条：一个注册能不能被撤销。能，热插拔才是真的；不能，插件再多也只是预装。

边界也得说清楚，两条。

第一条，可撤销只覆盖通过上下文提交的、进程内的资源。文件写了就是写了，删了就是删了，撤销不回来。业务动作的回滚不归它管，那是另一件事。

第二条，那个 197 不是"DSH 有 197 个插件"这个事实。它是我这台机器、这个 profile、这一天数出来的条目数。换个 profile、升个版本，这个数就会变。写文章的时候我特意没有把它写成产品的属性。

十、下一篇

这篇讲完了缝的三个角色，但没讲一条缝具体长什么样。

下一篇专门拆这件事：一条缝的定义、提供方、消费者各自是什么形状，以及当我想换掉文件系统的时候，到底哪些东西会跟着一起搬走，哪些不会。

那篇里会有一个我觉得很漂亮的例子：把文件系统和子进程指向远程沙箱，Bash、终端、LSP 全部跟着搬家，而工具层一行没改。

最后想问你一句：你手上有没有一个"只能装、不敢卸"的插件？

不管是 DSH 的，还是别的工具的。它为什么不敢卸——是因为它留了状态，还是因为你已经记不清它到底改了什么？

留言说说。我猜这个比例不低。

术语小抄

apply：插件被加载时框架调用的那个函数，插件在里面注册自己的能力。

inject：插件声明的“我需要哪些服务先就位”，也是启动顺序的依据。

effect：可撤销的注册。注册时把“怎么撤销”一起交上去，卸载时框架照着撤。

缝：一个可替换的能力，要三角齐全——定义、提供方、消费者。

bundle：能一次往配置里叠很多行条目的分发格式，跟“插件”不是同义词。

上下文对象：插件拿到的那个东西，里面是一袋服务，按名字取。

我还没搞懂

一，这台机器那 197 行条目里，哪几行来自实验性 bundle，我没有逐条归因。

二，并发卸载时撤销顺序到底怎么保证，官方写的是“无序”，我没实测过。

三，官方说约六成用户装了第三方插件，这条只有单条推文，我找不到复核。

四，版本闸门到底拦住什么、漏掉什么，我只读到“这不是防恶意代码的沙箱”那句免责。
