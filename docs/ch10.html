一个接口，换掉整个产品

版本 v1.1 ｜ 2026-11-08 02:41 (Asia/Shanghai) ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）
系列第 10 篇 ｜ 版本 v1.1 ｜ 2026-11-08 02:41 ｜ 依据：本机 dsh 0.2.2-rc.1 实测 + 系列资料（官方文档/X 与社区/架构实读）
学习笔记 ｜ 第 10 站 ｜ 我带着的问题：一个能力要真能被换掉，靠的到底是什么？
读之前我以为：写好一个接口、几个实现去实现它，这就叫可替换了。
读完我的一句话答案：缝要三个角色同时在场——定的、供的、用的，少一个就只是留了个空位。
读完我能答出来的三个问题：1 一条缝要凑齐哪三个角色，少一个会怎样？ 2 shell 这条缝上的四个提供方和两个消费者分别叫什么？ 3 我自己定的三条判据里，那条反判据说的是什么？（答不出就说明我没学会，这篇先不发）

先说人话版。换灯泡的时候，换的是灯泡，不是灯座，也不是墙上那个开关。灯座是标准，灯泡是能换的那部分，开关照旧用。

DSH 想干的事，是让"执行一条命令"也变成灯泡：把本机执行换成沙箱、换成远端，那个给模型用的工具一行都不用改。这篇就是我弄明白"它凭什么敢这样"的笔记。

官方架构文档里有一句话，我第一遍读的时候以为它在吹：把文件系统和子进程的提供方指向远程沙箱，Bash、PTY、LSP 会跟着一起搬走，不用 fork 任何一个工具。我心里当时回的是“说着容易”。后来我把装好的三百多个包翻了一遍，发现它至少做到了一半，而且做到的方式跟我以为的完全不一样。

一、我原来的判断

我原来的判断：可替换就是把实现藏到接口后面。写好一个 interface，几个实现都去实现它，调用方依赖 interface 不依赖实现，这件事就完了。

现在的判断：可替换不是写一个接口，是三个角色同时在场——服务定义、提供方、消费者。而且真正的门槛不在定义，在消费者：只要有一个消费者偷偷 import 了某个具体实现，这条缝就漏了；反过来，消费者只认定义，缝才成立。少一个角色，那不叫缝，那叫预留了一个位置。

这个区别很要紧。接口抽象是编译期的事，缝是运行时的事。前者管“我能不能换”，后者管“换了以后谁不用动”。

二、官方只用了三个角色定义这件事

DSH 的术语表里有一条对“seam”的定义，措辞很硬，我把它翻成中文：一条缝是一个可替换的能力，由三个角色组成。服务定义（那个持有 ctx 键和词汇类型的 Service，它是一个抽象类，明确写着永远不是 TypeScript 的 interface），一到多个服务提供方，一到多个注入了这个服务的消费者。

后面还跟了一个“标准范例”，正好是进程执行这条缝：dsh-shell 是定义，dsh-bash-local 和 dsh-bash-sandbox 是两个提供方，dsh-tool-bash 是消费者。

我第一次看到“永远不是 interface”这个限定，觉得是作者较真。想了一会儿才明白这是整件事的关键：interface 只是类型层面的合约，它管不住谁在运行时持有这个能力、谁负责撤销、谁能在卸载时把副作用收回去。在 Cordis 里，服务是带所有权的东西，注册要走 effect，卸载要能回滚。用 interface 描述它，等于用一张菜单描述一家餐厅。

三个角色里，我认为最容易被忽略的是消费者。定义谁都会写，提供方写两个也不难，难的是让所有消费者老实到“只认定义”。因为消费者通常是最有话事权的那一方——在 DSH 里，消费者往往就是给模型用的那个工具。

三、最硬的例子：三个提供方一起搬家

先说官方那句原话，我不改它的意思：文件系统和子进程的提供方共用同一个执行世界，所以把它们指向远程沙箱时，Bash、PTY、LSP 会跟着一起搬，不用 fork 任何一个提供方。

这句话的技术含量在于“共用同一个执行世界”。如果文件系统是一个世界、进程是另一个世界、沙箱是第三个世界，那你想把执行挪到远端，就得分别挪三次，而且中途任何一次不同步，就会出现“文件在远端、命令在本地”这种鬼故事。

我去装好的产品里找这条缝的实物。三百三十二个 @deepseek-ai 开头的包，shell 这条缝上的编制是这样的：一个定义 dsh-shell；四个提供方，dsh-bash-local、dsh-bash-sandbox、dsh-pwsh-local、dsh-pwsh-sandbox；两个消费者，dsh-tool-bash 和 dsh-tool-pwsh。文件系统那条缝是另一套对称的编制：dsh-fs 做定义，dsh-fs-local 和 dsh-fs-sandbox 做提供方，dsh-tool-fs、dsh-tool-fs-search、dsh-fs-patch 当消费者。

沙箱包自己的说明里有一句让我停了一下：一个执行世界。文件系统、子进程、沙箱这三个提供方跑在同一个文件系统和同一个内核上；远程组合会把这三个提供方一起替换掉，隔离在那个世界里异步生效。

这句话反过来解释了官方的说法为什么敢写。要搬的不是那个工具，是工具脚下那三个提供方。

再看两个提供方的自述，味道就出来了。本地版写的是：每条命令都用一个全新的、非登录的 bash 进程跑，不带任何 rc 文件，所以调用之间不残留 shell 状态；命令用的是 harness 进程自己的权限，这个执行器什么都不限制，需要沙箱就叠上沙箱版。沙箱版写的是：它注册为同一个 ctx.shell，但要求有沙箱提供方和沙箱策略；如果找不到能真正执行受限模式的运行器，命令会直接失败并返回 SANDBOX_UNAVAILABLE，而不是无隔离地跑下去。

一个什么都不管，一个宁可失败也不放行，两个都叫 ctx.shell，消费者是同一个工具包。定义包的说明里有一句总结：一个 profile 可以选择本地或沙箱的 Bash 或 PowerShell 执行，而不用改调用方。

文档里提到的 LSP，是我花时间最多的一处。我装好的三百三十二个包里，一个带 lsp 的包都没有，所以一开始我以为这半句是宣传。后来我去仓库里翻，发现有这么一个目录，三个包：一个定义，一个走标准输入输出的提供方，一个给模型用的工具。

那个提供方的说明把机制写清了：它需要文件系统和子进程的提供方，为的是“同一个执行世界”。也就是说语言服务器本身是被子进程那条缝拉起来的——把子进程指向远端，语言服务器就跟着在远端起来，LSP 自然跟着搬。

这半句我从“吹牛”改成“说得通”。但它在我机器上确实没装、没跑过，所以这是本篇里我唯一没有亲手验证的环节，机制成立和现场验证是两件事。

四、缝的左端：一个 ctx 键就是一个可替换点

翻完这些包，我对“ctx 是什么”的理解变了。它不是一个全局变量容器，它是一张服务登记表：每个键占一个位置，谁提供了这个键，谁就是这个能力的提供方；谁注入了这个键，谁就是消费者。

官方文档里有一张核心包的表，我照着数，能点出名字的键有十九个：工具注册表、系统提示词、会话、agent 注册表、agent 循环、模型适配、会话投影、存储、存储域、后台任务、人类命令、目标、终端、shell、文件系统、沙箱、客户端模块、浏览器模块、连接。

其中九个偏“平台底座”（工具、提示词、会话、agent、循环、模型、投影、存储、连接），剩下的更偏具体能力，而具体能力里最典型的就是执行那三件：shell、文件系统、沙箱。

我又做了一次更笨的统计：把三百三十二个包的 README 全捞出来，数里面出现过的 ctx 点号键名，去重之后有九十三个。其中被提到最多的是文件系统（三十八次），然后是后台任务（二十六次）、shell（十九次）、沙箱（十二次）。

这个数字有意思的地方在于：它说明“被依赖最多的那几个键”恰好就是最基础的能力。九十三个名字里肯定混着不少消费者在提别人的键，不能直接当成九十三个缝；但量级摆在这里——这个系统里能替换的点，是两位数。

五、缝的右端：消费者真的只认定义吗

不只看定义方怎么写，要看消费者怎么用，这是我这两天才学会的检查方法。

先看一个第三方插件。我机器上装过一个上下文管理插件，它的注入声明短到只有一项：只 inject 会话投影。但它实际干了六件事：注册三个投影单元；往 HTTP 连接上挂五条路由；往系统提示词里插两个段（其中一个的位置是拿内置身份段的位置减一千算出来的）；在 agent/pre-step 这个 waterfall 事件上抢到最前面，给缺 id 的消息补 id；直接读写一张投影缓存表；只读查询技能、agent 预设、会话查询这三个服务。

六件事，五条缝加一个事件。没有一处 import 宿主的内部实现，全部靠“注入一个键、按约定的形状注册”。这就是消费者只认定义的样子。

再看我自己写的那个小插件。它一共一百一十一行，导出的注入声明只有一项：注入工具注册表。然后它把一段命令行调用包成一个工具注册进去。它不知道工具注册表内部怎么排队、怎么做把关、怎么把 schema 拼进提示词，也不需要知道。它只认“我能注册一个工具”这一条合约。

这里我原来有个误会，正好借它纠正：我以为“消费者只认定义”就等于“消费者一定写得对”。不是。我那个小插件在返回值上就违了合约——官方要求工具返回一个可校验的 JSON 值，报错要靠抛出，它却返回了一个内容块加一个自己填的错误标志。它能只注入一个键，说明缝是通的；它返回错形状，说明缝通不等于它对。这两件事得分开看。

六、有些能力天生不该做成缝

如果只讲好处，这篇就成了宣传。读文档和包说明的时候，我看到三个反例。

第一，会话日志。官方把它写成硬约束：模型能看见的东西必须都能从日志里重建；已经提交的一代日志绝不重命名、替换、删除，要改结构就在旁边发布新一代，每个迁移包只负责一步。这种东西不能做成可替换的实现——如果日志格式可以随便换，“模型看见过什么”就永远无法重建，整个系统的可审计性就没了。插件可以随便换，日志不行，这是配套的。

第二，权限。在 DSH 里权限不是配置文件里的一个开关，它是一次会话级的切换，落成一条事件，再投影成界面上的状态。所以它可回放、可审计、会话之间互不影响。我第一次看到“这个开关就是它的事件”这句话时觉得绕，现在觉得这是设计上少见的清醒：有些状态该被记录，不该被配置。

第三，环境变量。有个专门管这事的包，把模型每次跑命令时拿到的受信任变量登记成一张表，插件可以注册自己的条目，随插件卸载一起消失；重复登记或者没声明的运行期键会直接报错，而不是悄悄覆盖。它的说明里还有一句我很喜欢：这个注册表不改变模型看到的其他任何东西，shell 工具自己拥有自己的 schema 和提示。

所以“一切皆插件”不是“一切都该做成缝”。更准确的说法是：能力可以缝，事实不能缝。

七、三条判据，和一张搬家清单

我后来给自己定了三条判据，用来判断一个能力要不要做成缝。

判据一：消费者能不能不 import 实现就跑起来。方法很土——把消费者包的引入列表翻出来，看有没有直接指向某个提供方的路径。有一条，这条缝就漏了。

判据二：这个能力有没有两个以上真实现，而且差异是策略不是开关。本地执行和沙箱执行是两个策略，各自有独立的失败语义；如果两个实现只差一个布尔值，那不是缝，是参数。

判据三：换实现时，模型看到的那一层变不变。如果一个能力的替换会改变模型看到的工具描述，那我就不把它当可替换实现，而是回去重拆一遍。

反过来还有一条反判据：如果换实现要改消费者，那它就不是缝。

至于“换一个提供方，什么会跟着搬、什么不会”，我在上面这些包里读到的是一个很清楚的划分。

跟着搬的：执行发生在哪台机器上；受限级别；失败语义（比如沙箱不可用时直接报错而不是降级、文件写被拒时返回哪个错误码）；超时与输出上限；副作用的边界。

不跟着搬的：工具的名字；参数 schema；工具的说明文字；模型看到的呈现方式；事件名；会话日志的格式；提示词段的所有权。

这个划分不是审美，是被逼出来的：如果工具的说明文字跟着执行器走，那换执行器就等于换了一个产品，模型的行为会莫名其妙地变；反过来，如果错误码不跟着走，模型就分不清“我写错命令了”和“我被权限拦了”。

八、我错在哪，以及这套东西的边界

第一个错：我原来以为缝的价值在“将来能换”。其实它的价值在现在——现在就可以把某一个实现删掉，而消费者一行不动。我高估了抽象，低估了“不用改调用方”这件事本身有多贵。

第二个错：我以为抽象要用类型来表达。官方那句“永远不是 TypeScript 的 interface”把我按住了。抽象在这里是运行时概念：谁持有、谁撤销、谁在卸载时收尾。

第三个地方我只对了一半，前面已经招了：LSP 那半句我没验证到实物，只能当设计意图。

边界有三条。第一，缝越多，装配越难。它启动时要读的那一叠配置，合起来接近一千行补丁、近两百个配置行，这不是普通人愿意维护的东西。我自己的体会是，如果只是想装上用，这些缝对我没好处，反而是负担——出问题的时候我先得判断是哪一层出的问题。

第二，有些东西在我看来就不该换成可换的，比如日志格式，缝化它等于自毁审计。

第三，我上面说的“三个提供方一起搬”在今天的默认产品里是同一个世界里的隔离；真要把整个环境隔出去，要靠容器、微型虚拟机或者远端执行器，那是组合出来的，不是我机器上现成能点的开关。官方的说法是设计空间，我的说法是使用现状，这两个我要分开讲。

九、下一篇

缝讲完了，接下来讲穿过缝的东西。这个系统里“发生了一件事”被分成三种事件，用途完全不同；写插件挂错事件，是新手最常犯的错。下一篇讲这三种事件，以及为什么其中一种事件可以“包裹”另一种。

所以想问你一个问题：你手上的系统里，有没有哪一层是“换掉它，调用方一行都不用动”的？我见过的大多数号称可替换的层，第一次真换的时候都会漏出三四个偷偷依赖了实现的调用点。你踩过哪一种，留言聊聊。

术语小抄

缝（seam）：一个能被整体换掉的能力位。它得三个角色凑齐：定的、供的、用的。

提供方：真正干活的实现。同一条缝可以有两个，比如本机执行和沙箱执行。

消费者：调用方。在这套系统里，消费者通常就是给模型用的那个工具。

ctx 键：服务登记表上的一格。谁提供这个键谁占位，谁注入这个键谁使用。

执行世界：文件系统、子进程、沙箱三件事共用同一套环境，所以要换就一起换。

我还没搞懂

一，我数出九十三个 ctx 键名，但那是"文档里被提到的次数"，不是"缝的个数"。到底有几个真缝，我还没数明白。

二，"消费者只认定义"这件事有没有自动检查？现在我只能翻引入列表人工看，翻漏了也不会报错。

三，换到真正的远端执行时，失败语义还剩多少是本地的？我只在文档里读到设计意图，没跑过。
