系统提示不是一段文本，是一张拼出来的清单

版本 v1.1 ｜ 时间待补 (Asia/Shanghai) ｜ 依据：官方仓库 docs + 本机 dsh 实测
系列第 13 篇 ｜ 版本 v1.1 ｜ 2026-11-08 ｜ 依据：本机实测 + 系列资料
学习笔记 ｜ 第 13 站 ｜ 我带着的问题：模型每次开口之前，那段"你是谁、要遵守什么"的话，是从一个文件里读出来的吗？
读之前我以为：系统提示就是一段人写的文字，存在某个提示词文件里，找到它、改字、保存就行。
读完我的一句话答案：它是每次请求前现拼出来的一张清单——身份、规则、工具说明书、运行时上下文，四样各有来源。
读完我能答出来的三个问题：一，系统提示里占比最大的是哪一部分？二，配置里那个叫 complete 的字段是干什么的？三，提示被换掉了，缓存为什么没有全废？

这篇讲一个我一直没想通的地方：模型每次开口之前，那段"你是谁、要遵守什么"的话，到底是谁写的、写在哪。

我以前以为它是一个文件，谁写的谁负责，改它就去改那个文件。

后来我发现，每次请求之前，这段话都会被重新拼一遍。

我在自己的会话日志里翻到一条事件，类型叫 system/message。

它在第一轮第一步出现，内容八千多字符；到第六轮第一步，它被替换了一次，换成八千四百多字符。两次之间，那次请求里声明的工具从 57 个变成了 60 个。

那一刻我才明白，我一直在说的"系统提示"，在它这里不是一个文件，是一次装配。

我原来的判断

我原来的判断：系统提示就是一段人写的文字。找个提示词文件，写清楚它是谁、要遵守什么，存进去，每次请求带上。

现在的判断：它是运行期组装出来的一张清单——身份段、规则段、工具 schema、运行时上下文，四样东西各自有来源，每次请求前现拼一次，拼完还会被写进消息历史。

两个判断的差别不在措辞，在"谁能改它"：前者只有写提示词的人能改，后者装个插件、加个工具就变了。

一条命令就能看见它是拼的

我先用不着读源码。把配置树打出来，搜 system-prompt 这个 id，一行就够说明问题。

那是 id 叫 system-prompt 的一行，挂的是 dsh-system-prompt 这个包，它的配置里只有一句：

personaPrefix: You are a coding agent powered by the {{model}} model.

我盯着双花括号看了半天。它不是写给模型看的字面文本，是一个变量占位，装配的时候才被替换成具体模型名。也就是说，连"你是谁"这句话，都是拼出来的。

再往下翻，会看到几个 id 以 preset 开头的块。标准预设里列着这么一串插件：persona、agent-instructions、time-context，然后是一长串工具行。persona 带的还是那句前缀，agent-instructions 带一个上限值——65536 字节，也就是项目里的说明文件最多注入这么多。

另有一个预设，里面同样叫 persona 的行写着一句完全不同的话：You are a helpful software engineer assistant，并且多了一个字段，叫 complete，值为真。

这个字段是整件事的关键。它意思是：别拼了，我这一句就是完整提示。装配流程照样跑（工具和上下文还得解析），但最后会把这个段恢复成唯一的提示段。

官方把它当注册表，不当文档

官方文档里，这个服务的名字叫 ctx.systemPrompt，描述只有一句话：提示段与工具 schema 的组装。

能往上挂的东西有四类：段（section）、运行时上下文（context）、工具 schema（tools）、变量（variable）；另外还有一个显式的装配入口（assemble），谁都可以调。

一个段有四个字段，我当时记了下来：名字、排序号、文本、是否完整。文本可以是死字符串，也可以是一个函数——每次装配时拿当前上下文现算。排序按升序，序号相同的按名字的字符顺序排。

这些序号不是装饰。官方文档里给了具体的数字：改补丁那个工具的序位是 1350，夹在编辑工具（1300）和通配查找工具（1400）之间。装一个新工具，本质上是往这条数轴里插一个数；插错位置，工具出场顺序就变了。

还有一条硬规则：整个装配里只能有一个"完整段"，多一个就直接失败。我第一次觉得多余，后来才想明白：要么这套流程拼，要么你一个人说了算。

装配结束之前还有一道瀑布：注册过的监听者可以拿到拼好的文本，改完交回去。但"完整段"是在瀑布之后才被恢复的，所以监听者改不动它——能加注释、调格式，改不了主心骨。

变量是第三层，不是装饰

段和上下文之外，还有变量。

往注册表里挂一个变量，要守两条：名字只能是小写字母开头、后面跟小写字母数字或下划线；同名重复注册会抛错。渲染的时候，段文本里的占位会被替换成变量值；如果某个变量找不到值，而又有段引用了它，渲染直接失败。

这条"失败"的设计我挺喜欢。它不留一个空白或者占位符，让我在模型行为异常之后回头猜。要么替换成功，要么这一轮根本发不出去。

还有一个开关叫"不插值"。打开它，段里的双花括号会被当成普通字符保留——因为现实里真的有目录名长得像变量。我工作区里就有名字带大括号的路径，第一眼看见这个字段时以为多余，现在觉得它是被坑过的人写的。

工具 schema 才是大头

文档里还有一句话，把工具和提示绑死了：往 ctx.tools 注册一个能力，它的 schema 会加入提示装配。

我之前以为工具是工具、提示是提示。直到我把会话存储里那份"上下文时间线"投影翻出来，才看见比例。

同一台机器上，最近三个会话的这两个数字完全一致：系统段 2114 个 token，工具声明 11670 个 token。

也就是说，固定开销里大约八成半是工具的说明书，不是"你是谁、你要遵守什么"那部分。那次请求声明了 57 个工具，就等于在正式说话之前，先背了 57 份说明书。

这个比例解释了我在别处见过的一个现象：工具装得越多，模型不一定越聪明，可能只是每轮先花掉更多注意力在工具目录上。这一点我没有做 A/B，只是从比例上觉得可疑。

我抓到了那次替换

接下来是今晚最有意思的一段。

我把这台机器上全部 183 份会话日志解压，只筛 system/message 这一种事件。结果：183 份里每一份都有它；总共 243 条；其中 195 条是追加写入，48 条是替换；有 31 份会话的提示被替换过一次以上，最多的一份换了 7 次。

文本长度中位数是 7461 个字符，最长的一份 19590 字符。还有 6 条是空的——文档里说空文本等于清空提示，我这台机器上真出现过。

每一次替换，事件里都带着一句操作记录：替换的是哪一条、区间从哪到哪。注意它是"区间覆盖"，不是删除再插入——旧的那条事件还在日志里，只是被标成被覆盖了。这一点和上下文那篇里说的压缩是同一个做法：不动历史，只标引用。我最早看到的那份日志里，第一次写入是第 8 条事件（第一轮第一步，8173 字符），第六轮第一步时被第 1110 条事件替换（8440 字符，替换目标是第 8 条）。

而就在这次替换之后的下一个请求头里，工具声明的数量从 57 变成了 60。

顺序很清楚：工具集合变了，提示重新装配，旧的那条被原地换掉，新请求带着新的工具清单和新的提示出去。

我不是在推论里看见这件事的，我是在自己的日志里看见的。

为什么不破缓存

提示被替换了，缓存会不会全废？这是我当时最直接的疑问。

这正是官方在 2026 年 9 月 8 日那个版本里专门解决的事。release note 原文写得很克制：支持动态修改系统提示词且不破坏 KV Cache，模型需显式声明支持。

同一版还有一条更重要的变更，写在"其他变更"里：会话格式升级至 V3，恢复历史会话时生成新版日志并保留原文件，系统提示词纳入消息历史。

两条连起来读就通了：提示不再作为一个"请求字段"跟着每次请求走，而是变成历史里的一条消息。它变了就原地替换，没变就不动。模型侧只认历史，缓存按历史前缀命中，于是小改动不会把整个缓存打穿。

文档里把这个设计叫"把系统提示当成 surface node（表面节点）"。第一轮追加在历史最前面；渲染结果变了就原地替换；如果当前调用声明支持"在历史里更新"，非空的新版本会追加在缓存历史之后。

我在自己日志里看到的 48 次替换、6 次清空，就是这个机制在跑。

运行时上下文走的是另一条路

还有一种东西，长得像提示，走的却不是同一条路。

我每轮开头都会看到几个注入：项目说明文件 1650 个 token、技能目录 1933 个 token、运行环境快照 337 个 token、时间上下文 74 个 token。

它们不是系统段的一部分。文档把这类东西叫"动态提示上下文"，定位是"以用户角色落成的一份持久快照"，而且只在内容变化、或者压缩把旧的那份遮蔽掉之后，才重新记一条。

所以一条会话里，系统段只有 2114 个 token，但注入可以每轮都变。前者是"你是谁"，后者是"现在世界是什么样"。混在一起写的人，改起来会很痛。

我现在的四条做法

这四条是我这几天真的在用的，写下来给自己以后翻。

一、我现在装插件之前，会先想它的提示增量。工具 schema 占八成半这个比例，是我这台机器的现状，不是定律，但它提醒我：每装一个能力，都在给每次请求加税。

二、我改人设是去改配置行，不再去找一段文本。人设那行带变量，改完重启即生效，不需要动代码。想整体接管提示，就在那行加 complete。

三、我改完先看日志，不看界面。界面上看到的是渲染后的结果，日志里才能看见它是什么时候被换掉的、换成了多长。我这次能讲清楚，全靠那 243 条事件。

四、我给自己算了一次固定开销。会话存储里有一份投影叫上下文时间线，里面有三个数：系统段、工具声明、注入。我这台机器上是 2114、11670、大约 4000。三个数加起来，就是你每轮开口之前先要背的东西。这个数乘上你的请求轮数，就是你的固定税。

我错在哪，边界在哪

第一处错，是我一直把"系统提示"当成作者的产物。它其实是运行时的产物，作者只提供零件。

第二处错，是我以前改提示词，改的是我心里那版描述，改完没有回去看日志里的长度变化。现在我会看——从 8173 到 8440 这个差，就是那次功能变更留下的指纹。

边界有四条，都得说清楚。

一是段与段之间的优先级和覆盖规则，我只读了文档，没有做实验。文档说作用域里的段会遮挡同名的全局段，重复注册会抛错，但"遮挡之后渲染成什么样"我没实测。

二是改提示对输出质量的影响，我没有 A/B。这篇只讲它在结构上怎么拼，不讲"拼成什么样更好"。

三是"完整段只能有一个"这条，我只在配置里看到了一个现成的完整段（就是那句 helpful software engineer assistant），没有亲手把两个切成一个再切回去，验证它是不是真的会失败。文档这么写，我信，但我没验。

四是提示正文我没有贴。那份内容里混着我工作区的规则和私人上下文，能讲结构，不该贴原文。这一点我宁可少一个细节，也不贴。

下一篇

下一篇讲配置：为什么我打开配置文件，里面只有两个方括号。

因为讲完提示怎么拼，下一个问题自然是——这些行是谁写进去的。

术语小抄

  • 系统段：提示里"你是谁、要遵守什么"那部分，可以拆成小块单独排序。
  • 工具 schema：每个工具的说明书，它也计入每次请求的固定开销。
  • 完整段（complete）：打开就表示"别拼了，我这句就是全部提示"。
  • KV 缓存：模型对前文的记忆缓存，前缀不变就能复用。

我还没搞懂

一是段的遮挡规则。文档说作用域段遮挡同名全局段，但遮挡后渲染成什么样，我没做实验。

二是"完整段只能有一个"这条。我没亲手把两个切成一个，验证它真的会失败；也没搞清楚工具 schema 占八成半，到底是默认就这么重，还是我装多了。
