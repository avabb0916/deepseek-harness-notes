两半结构：host 与 client，没有第三半

版本 v1.3 ｜ 时间待补 (Asia/Shanghai) ｜ 依据：官方仓库 docs + 本机 dsh 实测
系列第 15 篇 ｜ 版本 v1.3 ｜ 2026-11-08 ｜ 依据：本机实测 + 系列资料
学习笔记 ｜ 第 15 站 ｜ 我带着的问题：写一个插件，到底要给几个"身体"写代码？
读之前我以为：一个插件有三个身体——后台干活的、屏幕上画界面的、给模型用的工具。系列提纲上就是这么写的。
读完我的一句话答案：官方只有两个半边（编译期分给哪个程序），后台一个、浏览器一个；工具不是第三个半边，它是后台那一半上的一个注册面（运行时注册给谁看）。
读完我能答出来的三个问题：一，为什么必须切成两个程序？二，浏览器那一半在导出的配置树里能找到吗？三，判断一个第三方包属于哪一半，看什么？

这篇记录一次纠错，错的是我自己。

我原来把两件事混着数了：一件是"代码写到哪儿"，一件是"东西给谁看"。混着数，就数出了三个。这个说法我信了很久。

后来去核原文，发现只有两个地方；第三个不是"一个地方"，是"挂在哪个地方上"。

题目我改过一次。系列提纲里它叫"三半结构：host / client / tool"，我照着这个说法把骨架都列好了，动笔前去核官方原话，发现第三个"半"不存在。

先把话说在前面：错的是我，这个错在中文圈已经传了一阵。这篇先更正，再讲清楚两半怎么分，最后说清楚那个被我误当成"半"的东西是什么。

读完你能做到

  • 只翻清单，就能判断一个第三方包有没有浏览器半边
  • 给插件加上客户端声明和一处 slot 注册，让页面上出现它自己的内容
  • 界面不出现时，先说清问题在宿主半边还是浏览器半边，再去那头找

一、我原来的判断

这一节是我原来的数法：插件有三个身体。

我原来的判断：一个插件可以有三个身体。一个跑在宿主里，管模型和工具；一个跑在浏览器里，管界面；还有一个是给模型调用的工具本身。三个身体、三套入口，写插件就是选一个身体。

这个说法好用，能解释我见过的几乎所有现象：为什么有的插件装完只是界面多个按钮，有的模型多个工具，有的两边都动。

现在的判断：官方只有两个半边，宿主半边和浏览器半边。工具不是第三个半边，它是宿主侧一个面向模型的注册面。我现在的说法是：两个半边，三个面。

我改口的原因不复杂：我去数了官方文档里 half 这个词。

二、这个说法为什么流行

这一节回答：这个说法为什么好骗人。

先说我为什么会上当。

"三半"这个框架太顺手了。它把三类东西并排放：进程、界面、能力。听的人不用懂编译，也能秒懂"原来插件有三种"。

而且它有一半是真的。DSH 里确实有三类注册：注册给模型看的工具、注册给人看的界面、注册给运行时用的服务。三类都在，都真实存在。

错在把它们叫成"半"。

"半边"在 DSH 里是个很具体的技术词，指编译期切分：哪些代码编进宿主那个程序，哪些编进浏览器那个程序。这是两个独立的 TypeScript 编译单元。而工具是运行期的一次注册，发生在宿主程序启动之后，跟编译期没关系。

把编译期的切分和运行期的注册放进同一个层级去数，自然数出三个。数错了层级，再多一个都数得出来。

而且它好画：三个方块排成三角形，箭头互相指，看着特别像那么回事。图能做到自洽，但这个词在官方文档里一次都没出现过。

三、官方文档里只有 half 这一个词

这一节回答：官方的原词到底是什么。

我在安装包里翻了一遍。

三百多个官方包里，带 half 的 README 到处都是：宿主半边、Node 半边、浏览器半边。中文包 README 里对应的是"主机半边"，有个包第一句就写"open-in-app 的主机半边"。

我又按"三半""three halves"这类写法全文搜了一遍，零命中。

开发文档说得更直接。仓库把代码切成 Host 和 Client 两个独立的聚合程序。普通包只注册进其中一个，宿主包进宿主那份配置，客户端包进客户端那份配置。

所以不是官方没讲清楚三半，是官方从头到尾只有两半。

四、为什么必须切两半

这一节回答：为什么不能合成一个程序。

这一段是我这次读文档收获最大的地方，因为它解释了"为什么不能合成一个"。

官方给的理由是：两边都在同一个 Context 接口上做声明合并，但塞进去的是不同的服务；一个编译程序同时看到两套，就会报冲突。

翻译一下。DSH 的所有能力都挂在 ctx 这个对象上：工具是 ctx.tools，模型是 ctx.llm，会话是 ctx.sessions。浏览器那边也有一套同名的键，名字像，实现完全不同。

TypeScript 有个机制叫声明合并：同一个接口声明两次，类型会合并成一份。要是在一个程序里同时看到宿主版和浏览器版的 ctx.tools，合并出来的类型就是两套方法的并集，编译器没法判断哪个是真的。

官方没有加判断，而是把它们切成两个程序，各看各的。

这条约束一成立，很多事情就顺了：为什么客户端插件不能直接在宿主里 import；为什么同一个包的两半要分两份源码；为什么"半边"这个词总跟"编译"出现在一起。

反过来看"三半"：如果工具真是第三个半，那它也该有自己的编译单元、自己的 ctx 声明、自己的冲突规则。它没有。它老老实实待在宿主那半边里，只是注册的东西给模型看。

五、我在本机数出来的两半

这一节是我数出来的现场：332 个包。

讲完规矩，来看现场。我把运行时里的包翻了一遍，按 manifest（包的身份证）里的声明分类。

运行时一共 332 个官方包，其中 330 个能读到 package.json，另外两个是打包时的链接条目。

按声明分：带客户端声明的 88 个；带组合补丁声明的 21 个；两者都带的 1 个；两者都不带的 222 个。

这个分布很说明问题。绝大多数包是纯宿主插件，服务、工具、适配器，它们不带任何半边声明。带浏览器半边的 88 个里，只有 1 个同时还能当组合包分发。

再看本机这张桌面 profile。它叠了 12 个组合包：10 个官方，2 个第三方。

10 个官方包里，带客户端声明的是 0 个。

2 个第三方包里，全带：一个是插件市场，客户端依赖 3 项；另一个是上下文插件，客户端依赖 6 项。

我原以为官方组合包该带一堆客户端声明，数出来正好相反：界面能力不在组合包里，在单独那批客户端包里。

还有一个细节能佐证：浏览器应用那个组合包，它的补丁声明不是单文件，而是五个补丁文件，主补丁加四个预设。它管的是组合顺序，不是界面代码。

六、配置树里只有一半

这一节回答：浏览器那一半在哪，为什么树里没有。

上一节说带客户端声明的有 88 个，那这些包在启动树里长什么样？

我把配置树打出来数了一遍：197 个条目里，有 62 个名字以 dsh-client 开头，其中 54 个是界面类。

注意这 62 行加载的是这些包的宿主半边，也就是包的主入口。它们是宿主侧插件行，会注册服务、会挂路由。浏览器那一半不在行里。

那浏览器半边怎么进去？包在 manifest 里写一段客户端声明，至少两样东西：平台写 web，以及它要等哪些其他客户端模块。

我翻到的界面主题包，客户端依赖列了 6 项：连接、语言、快捷键、渲染器、设置、远端接口。意思是"等这六个模块就位，我再加载"。带语音输入的那个实验包列了 7 项，还多一条外部模块请求。

很多客户端声明里还带一个“立即”标记，意思是别等第一次交互，启动就加载。界面主题、连接、客户端模块系统这三个包都带这个标记，所以页面一打开主题就是对的。

宿主半边的工作是扫描已启用的条目、组装启动图。再由 Web 载体把每个声明做成 /plugins 下的一个 bundle，顺序保证提供方先于使用方。

所以两半的分工是：配置树管宿主，声明管浏览器。你在 dump 出来的配置里永远找不到"浏览器半边"这一行，它本来就不在树里。

我必须交代一句：桌面 profile 不允许命令行导出配置，会直接报一句"由 Electron 应用独占管理"。上面这些数字来自另一个只装了两个基础组合包的 profile，层栈机制一样，层数少一些。

七、tool 不是第三半，它是三个面之一

这一节回答：工具为什么不是第三个半。

现在回到那个被我误伤的东西。

工具活在宿主侧。它注册进 ctx.tools，注册完这句话就够了：注册表会把它的 schema 自动喂进系统提示词的组装。也就是说，工具的"身体"就是宿主进程里的一次注册，没有第二个身体。

那为什么它看起来像第三个半？因为它有一整套配套：工具定义、参数声明、返回契约、执行流水线、权限拦截。丰富得像一个子系统。

但"有子系统"和"是半边"是两件事。半边决定代码编进哪个程序；面只决定在同一个程序里，你把东西注册给谁看。

我现在的说法是：两个半边，三个面。

工具面，注册给模型看，schema 会进提示词。
提示词面，注册给规则和人格看，按顺序插段。
投影面，注册给界面看，从会话日志折叠出视图，再决定要不要投给客户端。

三个面都在宿主侧，都是运行期注册，都跟着插件的生命周期撤销。它们和半边不是一个维度：半边走编译，面走注册。

投影面这个例子最能说明"面"是什么。它是折叠出来的视图，不另存一份状态；宿主里注册一个单元，界面上就能读到对应的快照。我核过一个第三方插件注册的三个投影单元，其中两个能在本机磁盘缓存里对上号：一个版本号 38，一个 6。

这种"注册完就能被消费"的关系，跟编译期切分没有半点关系。

八、我现在的三条做法

这一节是我现在照着做的三条。

第一条，我现在写插件之前先问：我要注册的东西给谁看。

给模型看的，写工具，挂宿主侧，注册进工具面。
给人看的，写界面，挂浏览器半边，用客户端声明等依赖。
两边都要，一个包两个入口：主入口是宿主半边，client 目录是浏览器半边，中间靠服务通信。

第二条，我排错时先问在哪一半。

配置树里查不到你那一行，说明它是浏览器半边，去插件 bundle 那头找；行在、但按了没反应，多半是宿主侧的服务没就位，先看它的依赖等的是谁。

这一条最容易白忙：改的对象如果本来就不在配置树里，重启多少次都不会有变化。

第三条，我判断一个第三方包属于哪一半，只看 manifest。

有组合补丁声明，说明它能把一组条目叠进启动树；有客户端声明，说明它有浏览器半边；两个都有，说明它两头都沾。本机那两个第三方包就是两个都有。

九、我错在哪，以及这篇的边界

这一节是我错在哪，还有我没验的部分。

我错在把运行期的注册面当成了编译期的半边。

这个错有个很具体的后果：它让人以为写插件是"选一个身体"，实际上写插件是"选一个注册面，再确认这个面在哪半边"。前者听起来更爽，后者才能指导动手。

更该说的是，这个错我写进了系列提纲，提纲上白纸黑字挂的就是"三半"两个字。

边界有三条。

客户端 bundle 的构建流程我没跑过。我只看了产物和包里的说明，没自己从源码编一个客户端包出来。所以"声明怎么变成 /plugins 下的 bundle"这一步，我讲的是文档和产物能确认的部分。

Web Worker 那条预览路径我也没验证，只在包里见过相关字段，没实际跑。

两半的数量是本机这个版本、这批包上数出来的。换一个版本，332、88、62 这些数字都会变。但我认为结论不会变：两半，不是三半。

最后反问你一句：你写过的插件，落在宿主侧还是浏览器侧？

如果两边都写过，有没有遇到过"配置里明明改了这一行，界面上就是不出现"的情况？我后来才想明白，那种东西本来就不该在配置里。你的经历如果不一样，欢迎在评论区讲讲，这一篇我会带着补充再改一版。

落地案例：给插件补上浏览器半边，让它在侧栏露面

这一节是一套能照着做的动作：加半边，让它露面。

场景：你的插件只有宿主半边，工具在对话里能用，界面上什么都没有。目标是右侧栏出现一行它自己的状态，约半天。

做法：在插件包 package.json 的 dsh 字段里加一段 client，platform 写 web。inject 照抄 ~/.dsh/profiles/desktop/node_modules/dsh-context/package.json 里那六项。exports 补一条 ./client 指向浏览器入口。入口里注册一个懒加载工厂，标识等于包名。再把视图挂到右侧栏的 slot 上，slot key 用插槽检查接口打出来，数字从宿主那半边暴露的只读查询取。

验收：刷新页面，右侧栏出现你写的那一行；开发者工具的网络面板里，/plugins 下多出一个以你包名命名的 bundle；在配置里把这一行 disabled 掉，那行字跟着消失，控制台不报错。

耗时：第一次 4 小时（大半时间在等注入的模块就位），之后 40 分钟。

读完这一篇，你应该能在不动别人页面的前提下给插件加一张脸，并且知道它不出现时该先查哪一半。

术语小抄

  • 半边：编译时决定这段代码进后台那个程序，还是进浏览器那个程序。
  • 注册面：运行时把东西注册给谁看，比如给模型看、给界面看。
  • 声明合并：同一个名字声明两次，类型自动合到一起，这正是必须分两半的原因。
  • manifest：包的身份证，写明它有没有浏览器半边、有没有补丁。

我还没搞懂

一是浏览器那一半到底怎么编出来。我没自己从源码编一个客户端包，只看了产物和包里的说明。

二是 Web Worker 那条预览路径我没跑，只在包里见过相关字段。

三是 332、88、62 这些数字换版本都会变，我没有跨版本对照，所以"数量会变但结论不变"这句是我的判断，不是实测。
