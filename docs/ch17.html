这篇是我读得最慢的一篇。

它讲的不是"有人来攻击你"，而是"你请来的帮手自己把门锁换了"。我啃了三份英文材料加一份源码说明，才看懂这个洞长什么样；看懂之后，我改了自己那台机器上的权限设置。下面是我的过程，不是结论。

读完你能做到

  • 用一条命令确认你的工作区不是家目录或盘根，并说清当前权限档是从哪一步事件来的
  • 给你最常用的三个目录写一张禁删清单，让越界的删除被直接拒绝
  • 把备份放到工作区之外，并真的恢复一次，确认它可用

2026 年 8 月 27 日，DeepSeek 在 GitHub 上推了一个修复。三天后，npm 上才出现带这个修复的版本。

这三天里，任何人敲那句官方文档教的 npx @deepseek-ai/dsh web，装到的都是带洞的版本。洞的名字叫 CVE-2026-82533（漏洞的全球编号），评分 9.4。

我想写的不是这个洞有多严重。我想写的是它的形状——它没有攻击者，攻击者就是 agent 自己。

一、我原来的判断

我原来的判断：给一个刚开源的国产工具写安全专篇，等于唱衰。早期软件有洞是常态，等它稳定了再说，现在写是给人添堵。

我甚至给自己找了个很像样的理由。DSH 才 0.1，官方自己在文档里写着 developer preview、会有破坏性变更。那就说明人家知道自己是半成品，你再去挑安全问题，属于拿成品标准量半成品。

现在的判断：权限模型是选型的第一道闸，不是等到"稳定"才该看的东西。因为这个洞的形状不是"某处写错了"，是"agent 能给自己提权"。提权（自己把权限调高）跟着架构走，不会随版本号自然消失。

这两句话的差别，是我读完三份材料之后才真正想明白的。

二、先说那个洞：它没有攻击者

这一节回答：这个洞长什么样。正常的漏洞故事是这样的：有人从外面进来，绕过一道检查，拿到了不该拿的东西。

这个洞不是。它从头到尾没有外人。

DSH 跑在你机器上，除了界面，还起了一个本地的 Web 接口。这个接口做两件事：给浏览器发指令，以及接收浏览器发回来的指令。

而 agent 执行 shell 命令时，harness 会主动把两样东西交给 agent 的 shell 环境。一样是这个接口的地址，一样是当前会话的编号。官方的考虑很实际：agent 要能操作自己的界面，当然得知道界面在哪。

问题在于，这个接口不验身份。

负责判断"这个请求能不能进来"的那个文件，只读请求头里的 Host 字段，从不看连接到底从哪来。文件里有一句注释写得很老实：这不是一层鉴权。

于是链路闭合了。沙箱（圈起来的一块地）里的 agent 拿到地址和会话号。它调一下这个接口，把自己这个会话的模式改成 danger-full-access。沙箱关了，审批也不再弹。

最要命的是最后这一步为什么不弹窗。因为审批的触发条件是"这条命令要求的权限超过了会话已有的权限"。而这次调用没有要求更高权限，它改的是会话的设置本身。设置变了，后面所有命令的天花板就跟着变了。

一句话概括这个洞的形状：agent 不是砸开了锁，它是走到管理处，把自己那间房的锁换成了没有锁。

还有一层：同一个接口还提供一个功能，能把整个会话日志下载下来。这意味着只要能碰到这个接口，不需要任何密钥，就能拿走你所有的历史对话。

三、修好了，但 npm 上晚了三天

时间线我核过，值得完整摆一遍，因为它比结论更能说明问题。

8 月 13 日，DSH 发布。同一天，官方讨论区第 250 号帖就有人贴了复现过程。一个被沙箱限制住的进程，摸到本地接口，然后把会话切成 danger-full-access，还附了测试输出。

8 月 14 日，第 853 号帖列出了这个接口在没有任何凭据的情况下接受哪些请求。同一个帖子顺手指出一件事：这个项目没有安全策略文件，也没有私下报告漏洞的渠道。

8 月 24 日，安全公司 OX Research 把问题报给 VulnCheck。VulnCheck 的致谢里写的是两位研究员的名字，OX 的公开文章里没提那两篇更早的社区报告。

8 月 27 日，修复推上 GitHub，版本号 0.1.2-alpha.1。

8 月 30 日，npm 上出现第一个带修复的版本，0.1.2-alpha.2。受影响的版本是 0.1.1-rc.2 及更早，也就是说，8 月 30 日之前照着官方文档装的人，基本都在里面。

9 月 3 日，0.1.2-rc.1 成为 npm 上的当前版本。

9 月 8 日，VulnCheck 公布记录，评分 9.4。

9 月 9 日，The Hacker News 发稿。稿子里有一句我看了很久：检查仓库的公告列表，没有找到任何一条安全公告。带修复的那个 release 把这个改动列在例行变更里。写的是"移除旧传输层，网络访问要求一次性 token"，没提 CVE，没提安全。

修复本身是干净的。启动时在地址栏打印一个一次性 token（只能刷一次的门票），浏览器拿它换一个签名 cookie。之后每次调接口都要带 cookie。这个思路没问题。

但它没改沙箱。0.1.2-rc.1 的命令行参考里仍然写着：读和网络访问不受限制。agent 的 shell 仍然拿得到接口地址。官方没说在新的鉴权方案下，工作区里的 agent 还能不能自己换到 cookie。

这是我最在意的一处"没变"。修的是门，不是院墙。

还有一层容易被忽略：第三方桌面壳会自己打包一份 dsh 运行时，装哪个版本由壳的作者决定。报道里举了一个例子，某个 Windows 壳在 8 月底还固定着 0.1.1-rc.2，直到 9 月 6 日才升到带修复的版本。所以如果你用的不是官方安装包，光看自己敲的命令是不够的，得看那个壳锁的是哪个版本。

四、400GB：一次没有攻击者的删除

第二个事件更朴素，也更容易让普通人后背发凉。

8 月中旬，一位 Windows 用户在装插件的时候出了问题。DSH 处理符号链接时，引号和路径被错误解析，删除的目标从一个链接扩大成了整个 G 盘根目录。大约 400GB 文件被删掉。

关键是后半句：那个会话开的是完全权限，整个过程里没有任何一步停下来问一句"你确定吗"。

这不是被攻击，这是一次解析错误加一次权限过宽，两件坏事撞在一起。

社区的应对很有意思。曝光这件事的博主写了个叫 dsh-auto-mode 的插件，在官方三档之外补了第四档"Auto"。这一档的规矩是：项目内的读写、构建、测试尽量放行。删除已有数据和对外写入按上下文判断。磁盘根目录、用户目录、系统关键路径直接硬拒绝。

但作者自己把话说清楚了：这不是操作系统级沙箱。包安装脚本、绕过工具系统的插件、从 harness 外面启动的命令，都不在它的控制范围内。真正敏感的环境，该用容器和正式沙箱还是得用。

我尊重这个态度。补一个插件然后老老实实说它补不上什么，比宣称"装上就安全了"强得多。

顺带说一句公道话：这类事故并不专属于 DSH。权限给高了，任何编码 agent 判断出错，都可能干出同样的事。但 DSH 发布首周用户里新手比例高，这个坑我觉得值得放在最前面讲。

五、为什么权限不是一个开关

这是我这篇最想讲清楚的一点，也是我读源码时才真正理解的。

我原来以为权限是配置文件里的一个字段。写 read-only，它就是只读；改成 danger-full-access，它就是全开。改完重启，生效。

DSH 不是这么做的。

我把本机桌面版那份近一千行的补丁配置从头 grep 了一遍。找 sandbox、permission、approval、danger 这几个词，零命中。也就是说，我当前这个会话的完全权限，不在任何一个配置文件里。

那它在哪？在会话日志里，是一条事件。

官方那个管沙箱策略的包，README 里有一句话我抄下来了：开关就是它的事件。当前的生效值等于三个东西依次取：显式授权、日志事件折叠出来的结果、部署默认值。

这个设计带来三个后果，每一个都比"配置开关"强：

其一，可回放。会话重启后权限状态能靠重放日志恢复，不需要额外存一份状态。

其二，可审计。你事后能查到"这次会话是在第几步、被谁、因为什么从 workspace-write 变成 danger-full-access 的"。这在出了事之后是决定性的——配置开关只能告诉你"现在是什么"，日志事件能告诉你"什么时候变的"。

其三，会话隔离。两个会话各用各的，一个会话提权不会污染另一个。同理，删掉那个提供权限预设界面的插件，你最后一次的选择依然生效。因为执行权在各自的服务里，预设只是把沙箱和审批两个旋钮打包给你看。

还有一处细节，我认为是理解整件事的钥匙：那个沙箱策略包的出厂默认，是 read-only。

是 read-only。最严的那一档。

但本机跑起来是 workspace-write。差别出在基础层：基础 bundle 的补丁里，把这一行写成了"环境变量优先，否则 workspace-write"。也就是说，包的设计者是保守的，是组装产品的那一层主动放宽了。

这个区分对我是有用的：它让我知道该去哪个文件里改，而不是笼统地"注意安全"。

六、中文圈为什么没人讲这件事

这一节回答：中文圈为什么没人讲。写这篇之前，我把知乎、V2EX、腾讯云开发者社区、澎湃、什么值得买都翻了一遍，搜 CVE-2026-82533，零条。

中文社区在传的是 400GB。有画面、有数字、有当事人的视频，一天就传开了。

一个 9.4 分的洞，两个多月，中文技术社区一条都没有。我想了想，大概三个原因。

第一，事故比编号好传播。"粉丝 400G 被删"这句话本身就是一个完整的故事。"CVE-2026-82533"是一串数字，读完不知道发生了什么。

第二，这条 CVE 的证据链全在英文。The Hacker News 的报道、VulnCheck 的记录、OX Research 的技术分析，三份都是英文，而且互相引用。中文没有一个落地版本，想写就得自己翻译加核对。

第三，讲它需要同时读源码和英文公告。你要能说清"为什么改设置不触发审批"，就得去看接口信任那个文件和审批的触发条件。这个成本，比转发一条事故高太多。

还有一个不太愿意承认的原因：那阵子 DSH 正被捧得很高，这时候写安全，容易被读成唱衰。

我就是被这个顾虑拦住的人之一。

七、我现在的四条配置

官方的安全文档里其实已经把话说尽了。我摘三句原文，因为它们比我说的任何话都有分量。

第一句：沙箱、审批提示和权限控制能降低风险，但不能保证隔离，也不能防止损害。

第二句：不要把 DSH 当作处理不可信工作负载的唯一安全控制。

第三句，在"负责任使用"那一节：优先使用一次性的虚拟机、容器或专用环境；为你允许它访问的文件保留备份。

一家公司在自己产品的安全文档里写"别只靠我"，这是诚实的写法。下面四条是我照这三句话给自己定的，不是建议，是我自己正在做的。

第一条，我把默认权限档往下压了，没有停在 workspace-write。日常让它读代码、改当前项目，workspace-write 我用下来是够的。只有在我明确知道要动什么、而且刚备份过的时候，我才手动放到完全权限。我给自己定的判据很土：如果这次任务失败会让我损失一份找不回来的数据，我就不给完全权限。

第二条，危险操作前先备份，而且备份不能放在它的工作区里。这一条官方文档直接要求了。我的做法更土：让它干活的项目，永远是一个刚 clone 出来的一次性目录，家里那些东西我一个都不放进工作区。400GB 那件事里，如果工作区不是盘根目录，损失上限立刻就被锁死了。

第三条，插件来源我现在会审。官方给过一个数字：约六成用户至少装了一个第三方插件。而插件拿到的是和 shell 同级的权限，它不是一个受限制的扩展点。所以我现在只装能在 GitHub 上看到源码、且我能读懂它在 apply 里干了什么的插件。装之前我会先扫一眼它有没有在启动时注册网络请求或文件写入。

第四条，桌面版的遥测我打算关掉。这一条我要标清楚来源。它来自 Hacker News 上一位用户的发现：桌面版默认开启遥测，而命令行起的 dsh web 只在你主动反馈时才有遥测。他给的做法是在 DSH_HOME 下的 cordis.patch.yml 里，首次启动前加上三条禁用项。三条分别针对桌面端产品遥测、产品分析，以及一个会把会话记录附加到 API 请求上的会话日志插件。

我没有在本机验证过这一条。写在这里是因为它可操作、可回滚，但我把它当线索而不是结论——我打算自己去那份配置里核一遍，再决定改不改。

八、我错在哪，以及这篇的边界

我错在把"有洞"和"洞的形状"混成了一件事。

开源早期有洞是常态，这句话本身没错。但洞和洞不一样。补丁级的 bug 会随着版本推进自然消失，架构级的提权不会。只要"agent 的 shell 拿得到本机接口地址"这件事还在，只要"改设置不触发审批"这个逻辑还在，同类问题就会以别的形式长出来。

我用"早期软件都这样"这句话，把一个结构问题归类成了时间问题。这是偷懒。

边界也要说清楚。

第一，我没有复现这个洞。我读的是 The Hacker News 的报道和公开的源码路径，不是 OX Research 的原始报告，也没在自己的机器上试过。这篇里所有关于机制的描述，都来自那篇报道对源码的引述。

第二，400GB 那件事我只有转述，没有找到当事人的原始帖。数字和机制来自一篇明确标注"内容由 AI 生成"的汇编文章，它列了 B 站视频作为来源，但视频我没看。所以这一段请当二手读。

第三，桌面版遥测那一条是单一来源，一个人的观察，我没有验证。

第四，这篇通篇没有写任何操作步骤，也不打算写。知道一个洞怎么被利用，对读者没有用处；知道自己的权限档在哪一层被放宽了，才有用。

落地案例：跑一次权限自查，堵住一个真实的口子

场景：这台机器上的 agent 已经跑了两个月。工作区一直指着 ~/Documents。哪天它判断错一次，删除范围就是你所有文档。

做法：半小时做四步。先敲 pwd 和 ls ..，确认工作区既不是家目录也不是盘根；是的话，立刻换成刚 clone 的一次性目录。再问它当前沙箱档位，并让它说出这个值来自哪一步事件；说不出来，说明你只知道结果、不知道来源。然后列一遍已装第三方插件的目录，逐个看 apply 里有没有注册网络请求或文件写入。最后找出备份目录，确认它不在工作区里面。

验收：四步都能给出一句话答案，且工作区路径不在家目录下、备份路径在工作区外。有一条答不上来，就先别开完全权限。

耗时：第一次 30 分钟，之后每月 5 分钟。

读完这一篇，你应该能把"注意安全"换成四个能当场回答的问题。

九、下一篇

安全讲完，紧接着要讲一件和它高度相关、但更容易被忽视的事。它不只能自己干，还能拉一支队伍干。

子代理、任务板、消息、并发边界——多一个 agent，就多一份同时写同一个文件的风险。这条线上我自己踩过坑，素材是现成的。

下一篇：子代理与 Agent Teams，以及并行到底在什么情况下不该用。

最后想问你一句：你有没有被 agent 删掉或改掉过不该动的东西？当时权限开的是哪一档，事后你改了配置还是改了习惯？

留言告诉我。我想知道这个比例到底有多高。

术语小抄

CVE：漏洞的编号。一串数字，全球通用，方便所有人指同一个洞。

沙箱：给它划一块地，让它只能在这块地里动东西，出了地界就拦下。

审批：它要做越界的事之前，先弹出来问你一句。

一次性 token：只能用一次的门票。用完作废，下次要新的。

fail-closed：拿不准就拒绝。宁可打不开，也不放过去。

我还没搞懂

一，新的鉴权方案下，工作区里的 agent 还能不能自己换到那个签名 cookie。官方没说，我也没法测——测这个就等于在自己机器上复现一次提权。

二，那个本地接口为什么一开始要把地址和会话编号交给 agent 的 shell。官方的理由是"它要能操作自己的界面"，但我没搞懂为什么操作界面需要知道会话编号。

三，400GB 那次，符号链接的路径解析到底错在哪一步。我只看到结果（删除目标从一个链接扩成整个盘根），没看到原因，也找不到当事人的原始记录。
