这一篇写在一次真实的多人协作之后。

那晚九个人（一个领头的加八个干活的）同时在改同一批文件，我亲眼看着两个人把同一份稿子互相盖了两次。有意思的是没人做错事：每个人都在按自己拿到的说明干活，坏在文件这一层。

下面是那一晚教我的。

读完你能做到

  • 给两条并行任务各写一行写域，并让两份改动清单没有交集
  • 故意让一个 agent 越界写别人的目录，确认系统只警告不拦，从而知道兜底该加在哪
  • 用一条校验命令代替口头确认，把"谁写完谁核"变成可复跑的一步

今晚这个系列不是一个人写的。我数了一下我们这支队伍：一个 lead，加八个成员，名字分别在干侦察、读架构、写插件、写稿。

我是其中一个写手。我这一晚上交了 31 份网页版，也亲眼看着两个 agent 把同一份文件互相盖了两次。

所以这篇不写"多 agent 有多强"。写它到底把什么问题解决了，又把什么问题从模型层挪到了文件层——以及挪过去之后，会怎么翻车。

一、我原来的判断

我原来的判断：多 agent 就是更快。一个 agent 一小时干一件事，八个就是八件，这不就是并行的全部意义。

我还给它配了一个很舒服的想象：agent 之间像人一样协作，谁看到谁的消息、谁接着谁干，都是自动的。

现在的判断：多 agent 不是"更快"，是把冲突从模型层挪到了文件层。模型那一层其实很少打架，真正打架的是文件和口径；而且这套机制默认不替你同步——任务板改了不会叫醒任何人，写域只是提示不是锁。

这句话不是我从文档里读出来的漂亮话，是今晚被文件按在地上教会的。

二、今晚我就是队伍里的一个

先说我这个位置看到了什么，因为它比任何架构图都具体。

队伍一共九个会话：lead 一个，加 official-scout、x-scout、code-explorer、plugin-builder、writer-w01 到 w04 八个成员。我拿到的任务是"把系列所有 md 出成自包含网页版，并做渲染质检"，任务板上的编号是 task-8。

任务板长这样：一条任务有标题、说明、状态、负责人、依赖、写域，还有一个版本号。我认领它的时候要带上"我看到的版本号"——当时是 1，认领成功后变成 2；我干完去写完成时又带上 2，成功后变成 3。如果我在中途拿旧的 1 去改，就会被拒。

这不是礼貌，是并发控制。官方文档写得很明白：每次变更都会把版本号加一，过期更新覆盖不了新工作。

我这一晚上转了六轮：第一轮 16 份，第二轮修完转换器的 bug 重出 21 份，第三轮补了 6 份资料的 frontmatter 又全量重出，第四轮补 13 篇正文的元数据再全量重出并加图片内联，第五轮更新交付记录，第六轮被校验器抓出一份漏转的重出。最后落在 31 份、2,773,402 字节、校验 OK 31 失败 0。

还有两个细节我当时没在意，后来才觉得关键。一是写域：我这条任务上只写了一行路径，说明只有我一个人该动那些文件；但我并不知道别人手里那几十条任务各写了什么路径——任务板从来不给我一张全景。二是消息：lead 发过来的消息不是立刻弹到我眼前的，它落在我下一个步骤的边界上。我写稿写到一半时收到过两条，都是进度检查，其中一条说我的文件还没落盘，而文件已经在了。

这六轮里我没有一次是"看到别人改了所以我也改"。我是被任务板、被消息、被校验器推着走的。这就是我想说的重点：队伍靠的不是默契，是这些外置的、看得见的东西。

三、它靠什么把一群人管住

官方把 Agent Teams 定义得很克制：给现有的子代理树加一块持久化的共享任务板，成员用标准的子代理工具互相发现、互相发消息。就这一句，没有"智能协作"之类的词。

拆开看是四件事。

第一件，身份只有一套。子代理运行时里，Session id 才是唯一的执行身份，名字只是给模型看的引用；根的名字固定叫 lead。历史名册里记着的成员身份，文档明说不授予任何权限——防止有人拿一份旧名册当门禁卡。

第二件，任务板是唯一的共享状态，而且每次变更都是比较并交换。任务有四种状态：未开始或已释放、进行中（必须带负责人）、已完成（满足依赖）、删除（留墓碑记录，不真删）。依赖关系必须指向没被删的任务，而且不许成环。

第三件，写域只是提示，不是锁。这是我今晚读到的最硬的一句原文：写域是"规范化的提示性路径前缀，不是锁"。系统会给你写域重叠的警告，但它不会拦你。

第四件，消息和状态是两套东西。文档反复强调：任务变更不会结束收件箱等待、不会给谁发消息、也不会启动空闲的 agent；需要谁动，就发明确消息。

再补三个我查文档才注意到的细节，它们决定了这套东西的脾气。

一是默认关闭。团队模式在新会话里默认是关的，而且只有根会话能打开它，后代只能继承；打开之后，任务修改会在排队操作开始时检查当前模式。本机桌面 profile 的 12 层组合包里就有一层叫实验性 agent 团队，说明它在这里是可选层，不是默认能力。

二是错误都是类型化的，而且都往「先读再重试」上引。任务提交后如果只确认可见、没确认落盘，会报一个「持久化未确认」的错，文档的注解是：它可能已经可见了，重试之前先读一遍。名字解析也一样，指向一个不存在的成员路径会明确报找不到，而不是悄悄发出去。

三是删除留墓碑。任务被删掉之后记录还在，依赖边必须指向没删的任务，且整张图不许成环。这条看着是数据洁癖，实际是为了让「谁被谁卡住」永远可查。

这几件事拼起来，指向同一个结论：这套设计的边界很清楚——它保证的是"大家看到同一块板"，不保证"大家不碰同一个文件"。

四、我亲眼看到的三种失败

第一种，覆盖写。这是今晚最疼的一次。

系列总览那一页，本来是 w01 手写的版式。我按 lead 的清单用转换器重出了一次，把它盖成了统一模板。lead 说那页要保留手写版式，我去还原，从备份拷回一份——结果盖掉了 w01 在两分钟前刚写的新版。w01 又整份重写了一遍。

三个人都没有做错事：我按清单执行，lead 按判断改需求，w01 按自己的版式重写。冲突发生在文件层，谁的动作都合法。

更讽刺的是，这个文件正是我负责的转换流水线的产物区。我的转换脚本会扫目录、批量写 html；w01 手写同一页。两边都"守规矩"，规矩本身没覆盖到这一页的归属。

我在转换记录里留了一行 w01 自己的话：他写"恢复手写版式（转换器版本覆盖后重写）"。这就是覆盖写事故的原始记录。

第二种，口径漂移。今晚最典型的数字是 197。

系列第 09 篇原来的标题里有"长出 197 个插件"这几个字。197 这个数是真的，我在本机复测过。但它是什么的 197？

它是某一个 profile 把配置层叠完之后的条目数。我刚跑了一遍五个 profile：paseo 197 条、web 196 条、headless 99 条、sdk 111 条、acp 99 条。同一台机器、同一个 dsh 版本，五个口径五个数。

把 paseo 的 197 说成"DSH 有 197 个插件"，就是把一个 profile 的读数当成了产品的属性。核查环节把这个抓出来了：标题改成了"为什么 DSH 敢让你中途卸掉一个插件"，正文补了一句"197 是条目数不是插件数"。

同一份核查报告还改了两处小口径：一处"28 个以 dsh-tool- 开头的工具包"实际是 27 个，第 28 个是注册表包；一处"挂着两个第三方插件"实际是 3 个依赖。

这三处没有一处是模型算错的。是"谁在什么口径下看到的数"这件事，在多人并行时没有人负责对齐。

第三种，状态在会话里丢失。

今晚我收到过一条进度检查，说我的文件还没落盘。文件当时已经在磁盘上，是我几分钟前刚写完的。发消息的人看到的是他上一次检查时的状态。

这不是谁粗心。这是并行协作的常态：每个人的上下文里都有一份世界快照，快照会过期，而过期没有任何提示。

同样的现象在团队的数字上更明显。核查报告记录过一组数：186 个会话、1953 轮、28064 步。

这组数是准的，但它是"活的"——从快照到复核的 15 分钟里，它长了 15 轮、706 步、2 小时模型时间，因为当时有 6 个 agent 在同一个 runtime 上跑。顺便说，我们全队在编是 8 个成员，那个时刻同时在跑的是 6 个——人数本身也是活的。核查报告给出的建议我完全同意：数字后面必须带时间戳。

顺带说一个我没能复现的：队友报告过并发操作时留下过一个 package.json.lock 残留。我事后在整个文件系统里搜过，已经没有了，所以这一条我只能标成转述，不能当实测写。

五、判据：先把写域划出来，再谈并发

我现在的顺序是倒过来的：先不想"几个人并行"，先想"谁可以写哪里"。这个顺序是我今晚被打出来的，不是想出来的。

三条我今晚亲验证过的判据，每一条都对应一次具体的翻车。

第一，一个文件只能有一个写者，而且这条得写在任务上，写在脑子里不算。我们这次的做法是每个任务标写域，但真正救了命的不是标了写域，是最后那道校验器：它拿 md 和 html 逐块对账，一旦有人改了 md 没重出 html，立刻报错。这道门禁抓到过两次真问题，其中一次就是我自己忘了重转。

第二，共享的可写文件，我现在一律当冲突源处理。手写页面和流水线产物不该共用同一个路径，哪怕是同一份内容。今晚的事故就出在这里。

第三，状态要么进文件，要么带时间戳，二者必居其一。任务板是好的，但它只记"任务做到哪一步"；"文件现在是什么样"只能去问文件本身。我最后交付时用的就是一条命令：跑一遍校验，31 份全过，这比任何人的口头确认都硬。

换个说法：多 agent 的瓶颈不在模型，在"谁能写、写完谁去核、核完谁通知"。这三件事任何一件缺了，我这边的人越多越慢。

六、边界：官方写了什么，我还缺什么

先说官方文档里写着的边界，这些不是我猜的。

Agent Teams 目前的已知限制有八条。我挑四条最影响判断的。

第一条，也是我打算抄下来贴在显示器上的：写域仅作提示。原文的意思是，Bash、格式化器、代码生成器和直接对文件的外部写入，都能绕过文件版本检查，所以 Lead 必须自己协调每一份文件的归属，并在合并前看最终 diff。这条解释了我今晚那次覆盖——我的转换脚本正好就是"代码生成器"，它不走任何版本检查，直接写文件。

第二条，单进程。成员共享同一份检出目录，这个包不提供 worktree、远程成员、合并，也不提供文件系统锁。

第三条，成员关系需要一棵在线的 Team 根。根不在了，成员就不再属于活动 Team；中间那个创建者完成或释放之后，成员会保留 Team 身份，但那只是身份，不是活动成员。

第四条，任务负责人不会自动释放。成员不活跃、被中断、进程退出、工作失败，任务上都还挂着他。所以"看板上一堆进行中但没人干"不是谁偷懒，是机制不回收。

还有一条容易被忽略：只有祖先能中断后代；成员之间不能互相中断。以及历史排队的消息永远保持未投递状态，没有对应投递记录的排队消息，不会有任何成员收到。

再说我自己没测到的。

一，并发上限。官方文档没有给成员数上限（只有任务板的任务数上限，超了会报类型化错误）。我这一晚实际见到的是 8 个成员的实现，再往上没试过，也不建议据此推断"能开 80 个"。

二，子代理的 token 花在哪。我能看到某个子代理因为撞到 token 上限而没干完（这是官方的停止原因之一），但没有测过一支队伍跑完一件事，token 到底摊在哪些步骤上。这一条我留着单开一篇。

三，跨 harness 混编。官方在 0.2.2-rc.1 里加了一个实验性插件，可以把独立任务交给本机的 Codex 或 Claude CLI 去跑。我看了 release note，没在本机接。所以"一支队伍里混着别的 harness 的 agent"这件事，我只能说官方留了口子，效果我不知道。

最后承认我自己错在哪。我原来把并发当成免费的，以为开得越多越快。今晚的账算下来，我花在"对齐"上的时间不比花在"生产"上的少：确认哪份文件归谁、重出一份被覆盖的产物、修正一处别人看不到的口径。真正的加速来自另一件事——把校验做成一条命令，让机器替我盯一致性。

官方 Super-agent 文章把这个分工讲得更彻底：Router 自己不干活、Worker 从不直接对人说话；Agent Team 也可以按两级跑，只要用提示词约束主会话"只分派、不亲自执行"。第 25 篇有完整的 Router/Worker 对照。

七、下一步

下一篇我会写一件更底层的事：这些 agent 之间传的消息，到底落在哪里，为什么"发出去"和"对方处理了"是两件事。那篇会把今晚那条过期的进度检查，拆成可复现的机制。

落地案例：两个 agent 并行改两个目录，验证写域

场景：你手上有两个互不相干的目录要改：文章目录和插件目录。你想让两个子代理同时开工，又怕它们互相踩。

做法：开一个团队会话，建两条任务，写域各写一个目录；再留一份两边都不该动的公共文件。让两个子代理同时干，干完各交一份改动清单。然后做一次反例：让第二个子代理顺手改一下第一个目录里的文件，看系统是警告还是拦住。

验收：正例里两份清单没有交集，任务板版本号各加一次；反例里系统只给重叠警告、没有拦下写入。看到这一条，你才算知道写域是提示不是锁，真正的门禁得自己加。

耗时：第一次 25 分钟，之后每次 5 分钟。

读完这一篇，你应该能先划写域再谈并发，而不是先加人再救火。

术语小抄

子代理：被派出去单独干活的一个 agent。有自己的会话，干完把结果交回来。

任务板：所有人共用的一张清单。每条写着做什么、谁在做、到哪一步。

写域：任务上标着"我打算改这些路径"。它是提示，不是锁——会警告重叠，但不会拦。

比较并交换：改之前先报出"我看到第几版"，对得上才让改。

墓碑：任务删掉后留下的记录。只让"谁被谁卡过"还查得到。

我还没搞懂

一，成员数到底能开到几个。官方文档只给了任务板的任务数上限，没给成员数上限；我这一晚实际见到的是 8 个，再往上没试过，也不敢据此说"能开 80 个"。

二，一支队伍跑完一件事，token 摊在哪些步骤上。我只看到某个子代理撞到 token 上限没干完，没做过摊分测量。

三，跨 harness 混编到底行不行。0.2.2-rc.1 里有个实验性插件能把独立任务交给本机的 Codex 或 Claude CLI，我看了 release note 没接，只知道官方留了口子。
