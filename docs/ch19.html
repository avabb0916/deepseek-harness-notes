这篇讲我怎么给一个助手加了一项新本事：让它直接告诉我今天该写哪篇。

我一开始以为，加本事就是写个说明贴上去，跟装个浏览器插件差不多。结果第一版交上去，它要么当场报错，要么看着像成功了、实际拿到的东西没法用。

下面是我把这件事弄明白的全过程，包括我踩的三个坑，和一套不花钱就能自查的办法。

读完你能做到

  • 用三个导出写一个 40 行以内的插件，并在激活日志里看到它注册成功
  • 给工具补上 output 里的 schema 和 render，让它不再被宿主当场拒绝
  • 用四步自查判断插件能不能用，而不是看到注册没报错就收工

一、我为什么要自己写一个

先说清楚这件事的来路，因为后面所有折腾都是由它决定的。

我写这个插件不是为了学插件开发。是为了少读文件。

这个系列要出二十几篇，文章卡、素材、进度散在六个 markdown 里。每天开工我得先读一遍才知道"今天该写哪篇"。我想让 agent 直接回答这个问题，于是给它写了个插件，名字叫 research-desk，研究台。

我原来的判断：插件就是写个函数，在函数里注册一个工具，照官方文档抄一遍形状，就能跑。

现在的判断：插件确实是三个导出，但"注册没报错"和"模型用得上"是两件事。照印象写，最可能的结果是注册静悄悄通过了，模型拿到的参数表是废的。

研究台要管四类东西：系列、文章卡、素材、进度。每天被问到的就三句：现在到哪了、下一篇写什么、这篇素材够不够。

这三句话以前靠我读文件回答。五个方向并行产出，谁写到哪只有主控 agent 的上下文知道；换一个会话，那份上下文就没了。

所以我要的不是写作工具，是一个状态文件加几个查询入口。写正文仍然在 markdown 里，插件只存指针和进度。

这件事有个天然的好处：它本身能证明我在学写插件。一个能跑、能验证、有单元测试的真插件，比一篇"插件怎么写"的教程更能说服我自己。

二、最小插件长什么样

这一节回答：最少要写几样东西。官方的说法很朴素：Harness 里一个插件就是一个模块，导出 apply 函数，框架加载它的时候把 ctx 传进来。

所以我原本以为要写很多东西，读到这句话之后，发现一个能干活的插件文件，只要三样。

第一样，导出常量 name，一个字符串，就是插件的标识。第二样，导出常量 inject（先说好用哪些服务），一个数组，写你要用的服务名。我要注册工具，就写一个字符串 tools。第三样，导出函数 apply，接收 ctx 和 config，函数体里通过 ctx 注册能力。

就这些，几十行就能写完第一个能跑的工具。我第一次看到"只有三个导出"时有点不放心，觉得少了点什么，比如入口、生命周期、注册表。后来明白：注册本身就是入口，生命周期由 ctx 管。

inject 这个字段值得单独说，因为它不是"声明一下"那么轻。

官方 primer 的原话是，声明服务依赖的插件会等服务出现才激活，所以加载顺序是靠服务需求表达的，不是靠人工排序。

换个说法：DSH 里没有"启动顺序"这个概念。配置里那一行写在前面，不代表它先加载。

我一开始以为配置文件的顺序就是加载顺序，还想去调换行的位置来修一个时序问题。这条路走不通，原因就写在 dsh-base 那个 patch 文件的注释里：行序不携带加载语义，激活由服务可用性驱动。

再说分发形态。上面那三样东西放在一个目录里，能被宿主加载，就是一个插件。它是不是 npm 包、有没有那个 dsh.plugin 标记，跟"能不能跑"无关。

那个标记的作用是让安装流程和插件管理器认得它，相当于贴在箱子上的标签。真正的加载靠的是配置里插进来的那一行，指向包的入口文件。

我一开始把顺序搞反了，以为加上标记就等于装好了。后来发现标记只是简历，入职还得有人给我排工位。

三、第一个坑：output 不是可选项

这是我最想记下来的一条。它推翻了我"照官方文档抄就行"的自信。

在写研究台之前，工作区里已经有一个我自己更早写的小插件，叫 linkdesk，管外链的，111 行。它的注册代码很"直觉"。给一个对象，写 name、description、parameters，再加一个 execute 函数，返回内容。

它的 README 里留了一句话：宿主内注册尚未验证，需要重启才能确认签名。

我当时看到这句觉得挺诚实，但没当回事。写研究台的时候，我先在真实宿主里放了一个探针插件（故意放进去试错的），就照那个形状注册，然后看日志。

报错原文是这样的：tool "naive_tool" must declare output { schema, render, presentationMeta? }。

一行。意思是我注册的工具必须声明 output，里面要有 schema 和 render。

我不服气，又试了一次：补上 output，但只写 schema，不写 render。报错一模一样，还是那句 must declare output。

这时候我才回去认真读契约。在本机用检查工具直接查工具注册服务，读到的类型是这样的。register 接收一个定义，定义包含 name、description、parameters，加上 output。output 里有 schema 和 render。再加 execute，接收参数和执行上下文。

也就是说，output 是必填的第一等字段，不是可选的贴心提示。

为什么它必填，官方 cookbook 讲得比我清楚。原话大意是：execute 只负责返回一个规范 JSON 值。注册表会对它做快照、校验、冻结，然后交给 output.render 去变成模型能看的内容。

所以内容是 render 生产的，不是 execute 生产的。这两件事被拆开了，我原来把它们当成了一件。

回头看 linkdesk 那 111 行：它直接在 execute 里拼内容块返回，还自己填了个 isError 字段。按官方契约，这两件都不对——内容不该从 execute 出来，isError 也不该由工具自己填。

它还有个更诚实的细节。因为当时手里没文档，代码里写了个循环，依次尝试 execute、run、handler 三种字段名，哪个不报错就留哪个。

这段代码我后来再读，有点心酸。它精确记录了"没有类型、没有契约，只能靠猜"的成本。而官方其实有个 defineTool 辅助函数，类型齐全，import 一下就能消掉全部猜测。

我这一节的结论：output 不是装饰，它是"返回值长什么样"的唯一声明。少了它，注册直接失败——这反而是好事，因为它大声报错。

四、第二个坑：parameters 要完整 JSON Schema

第二个坑比第一个阴险，因为它不报错。

官方 cookbook 的例子，parameters 写成一张参数表：某个字段是什么类型、必不必填、说明是什么。看着像 JSON Schema（一种参数的标准写法），其实不是。

而 defineTool 这个辅助函数会把这张表编译成真正的 JSON Schema。

问题出在那条裸调用上。官方也说了，ctx.tools.register 直接接受原始 JSON Schema 的定义。MCP 来的工具就是这么进来的。defineTool 只是第一方工具用的类型化包装。

我做了第三个探针：parameters 用参数表，output 补齐，然后注册。

结果：不报错。日志里我自己打的那行是，参数表写法 register() 没抛错，说明宿主不校验 parameters 形状。

这一下我就明白哪里最危险了。旧写法缺 output，注册会当场炸，我立刻知道错了；参数表写错，注册一声不响，我以为成了。

真工具的参数长什么样，我查过本机现有工具。都是完整 JSON Schema：一个对象，type 是 object，properties 里逐个字段，required 是一个数组。

也就是说，模型的工具描述是从这份 schema 生成的。参数表塞进去，模型看到的是一张没有 properties 的怪东西，它可能根本调不动，或者乱填参数。

而我当时没法从"注册成功"这个信号里看出任何异常。这个坑我到现在也没能百分百钉死。我能证明注册不报错，也能证明现有工具都是完整 JSON Schema，但我没有证据证明模型看到的最终形态是什么样。因为要看到它，得真跑一轮模型调用。这个边界我放在第九节说。

五、第三个坑：execute 只返回一个 JSON 值

第三个坑和第一个是一对。

我最早的设计是让 execute 直接返回内容块，因为那样最省事：想给模型看什么就拼什么，还能顺手加个"失败"标记。

官方契约把这条路堵死了，而且理由很扎实。如果工具返回的是散文一样的内容，模型就得自己从里面刮出 id 和字段。如果返回的是结构化 JSON，注册表能校验、能冻结、能重放，还能保证不同插件之间格式一致。

所以正确的分工是：execute 做业务，返回一个对象。output.schema 声明这个对象长什么样。output.render 负责把它转成读得顺的文字。

我的研究台就是这样。五个工具，每个 execute 返回一个对象。比如看盘返回系列数组、文章计数、素材计数、一个推荐项。render 再把它们排成几行中文。

这带来一个额外好处：同一个返回值，可以渲染给模型看，也可以将来渲染给界面看。数据和行为分开了。

也带来一个额外成本：我得写两遍。一遍算数据，一遍排版面。762 行里有很大一块是排版。

我一开始觉得这是冗余，写到第三个工具才认下来：这块排版是"给未来的界面"留的接口，不是浪费。

六、怎么自查：不花钱的四步

这一节回答：不花钱怎么验它成了。这一段是我觉得最该记下来的，因为我找到的插件教程大多只教怎么写，很少讲写完怎么知道它成了。

第一步，纯函数单测（同样输入同样输出），不碰宿主。我把能算的都写成纯函数：选篇排序、登记素材的校验、改文章状态、坏文件怎么兜底。然后用一个假的 ctx 把插件装起来，检查注册出来的东西结构对不对。

这一步不依赖 DSH 本身，跑一条命令就行。我最后是 89 条断言全过，其中相当一部分查的是失败路径：坏 JSON、写不进磁盘、注册函数抛错。

第二步，用临时家目录起一个干净的 profile。这一条是我给自己定的安全底线：我用的是 DSH_HOME 指向一个临时目录。从官方 web 模板新建了一个叫 lab 的 profile，跟日常在用的 desktop 完全隔离。

我不想因为测一个插件，把每天在用的环境搞坏。

第三步，看层栈（叠起来的配置层）。用 dsh --profile lab --dump-config 打出组合后的配置树。在我这里一共 1248 行，我那一行出现在 1245 到 1248。这个数比日常那个 profile 小得多，因为它是从官方模板新建的，只叠了基础层、界面层和我这一行。

看到自己插件的 id 躺在最后一段，才算真的进了层栈。配置文件里写了个名字，不等于它被组合进去了。

第四步，看激活日志。这个是最硬的证据。启动 web 应用时，我的 apply 里会打一行日志，内容是已注册 5 个工具，后面跟着五个工具名。

这行字出现，说明 apply 跑通了、五次注册全被接受。它不出现，说明插件根本没被激活——哪怕配置里明明有那一行。

我一开始拿"配置文件里有我的插件"当成功标准，用它验证过一次，结果误判了大半天。

顺带说，官方也有现成的安装入口。命令行里是 dsh plugin 加 profile 名加 add 加包名，会话里是插件管理器的安装动作。我没走这两条路，原因很简单：插件管理器作用于当前 profile，而当前 profile 就是我天天在用的那个。我不敢。

七、失败要软着陆

插件代码出错，我最怕的不是工具不能用，是宿主起不来。

我一开始以为 apply 里抛异常会连累整棵插件树。要是真是这样，我的插件就不只是"坏了自己"，而是"坏了整个环境"。

为了确认这件事，我在 lab profile 里塞了一个故意抛错的坏插件，就三行。导出 inject，导出 apply，apply 里直接 throw。

然后启动服务，日志是这样的。先是我的研究台正常注册，接着一行 dsh: warning: 1 entry did not activate。再下面是被点名的那行，lab-broken 加包名，加 Error 加我写的那句话。

而 Web 界面照常起来了，带 token 访问返回 200，页面四万字节；不带 token 是 401。

结论很明确：单个插件抛错，宿主会给它一条警告、跳过它、继续跑。这是宿主层的兜底。

那为什么还要在插件里再兜一层？因为宿主兜的是"整行不激活"，我想要的是"部分能力还在"。

研究台的 apply 里，注册五个工具是个循环。如果第三个工具的定义有问题抛了异常，没有内层 try 的话，后面两个工具就一起丢了。所以我把 apply 整个包在 try 里，注册失败就打日志返回空表，宿主继续跑。

工具内部也一样。execute 里一群意外（文件被删、磁盘满、JSON 被我手改坏了），任何一个冒出去都会变成一次难看的失败。所以每个 execute 外面还有一层 try，统一翻译成一个结构化结果：成功与否、错误码、人话。

数据文件我也按这个思路处理。读到坏 JSON，不硬撑，把它改名成带时间戳的损坏备份，然后按空库继续，并在结果里附一句警告。

宁可丢一次统计数字，也不想让 agent 卡在一个打不开的文件上。

我一开始觉得这些兜底很啰嗦，占了代码里一大块。后来想通了：我这半边的失败成本不对称。最坏的情况是丢一两个工具，没人受伤；但我要赌"宿主会兜住"，就是把风险丢给了整个环境。

八、什么时候不该写插件

这一段是被自己打脸打出来的。

我最开始的冲动是把整个写作流程都塞进插件：选题、写、质检、配图、发草稿。写完第二个工具就发现不对。

第一，凡是"可能跑几分钟"的事，不适合做成工具。工具是模型在一次对话里等着结果的东西，一个跑五分钟的工具会让那一次对话一直等。这类事我放在工作区里的脚本里，手动跑，或者让 agent 用命令行跑。

第二，凡是还在变的东西，不适合焊进插件。我的系列标题、篇数、判据，这一周改了三轮。如果插件里写死一套流程，改一次就得改代码、重装、重启。

第三，凡是"人要做价值判断"的环节，插件只能记录不能替代。比如这篇该不该发、这段话会不会得罪人。工具能做的是把状态摆在我面前。

最后我砍到五个工具，而且给自己定了个规矩：工具总数不超过五个。多一个，就必须合并进去。

研究台里"新建文章"这个动作，就是被合并进"更新文章"的：有 id 就改，没 id 有标题和系列就新建。少一个工具，模型就少一次选错的机会。

还有一条更硬的边界：插件不存正文。正文在 markdown 里，插件只存路径。

我一开始设计过让插件自己写正文草稿，后来想到一旦有两份内容，改哪份、以哪份为准，会变成每周都要处理的麻烦。

九、我错在哪，这篇的边界

先说我这篇最想承认的错误。

我原来的判断是"照官方文档抄一遍形状就行"。真实情况是：官方文档给的示例走的是 defineTool 这条路，它帮你编译参数表、帮你补类型。而裸调用注册接口是另一条路，两个形状不一样。我把两条路的写法混着抄了，所以踩到了静默失败。

第二个错误更根本：我把"注册没报错"当成了"功能能用"。这一个判断偏差，让我在同一个晚上多绕了一整圈。

现在我的标准变了：注册成功只是第一关，能证明模型真的调得动才算过关。

再说这篇的边界，有三件事我没做，我不敢把它们当成已完成。

第一，我没有真跑过一轮模型调用。所以"模型看到参数表长什么样""失败返回值会不会被标成错误"这两件事，我只能给出推论，不能给出证据。要补这一步，得花一次真实调用，我把它留到下一次。

第二，客户端界面我一行没写。插件现在只有宿主半边，界面在计划里，是这个系列的下一篇要讲的。

第三，安装流程我只走了一条：手工把插件链进 profile 的依赖目录，再往用户的补丁层插一行。官方的安装命令和插件管理器动作我都没跑，因为它们会改当前 profile，而当前 profile 是我天天在用的那个。

另外，所有验证都只在 0.2.2-rc.1 上做过。这是开发者预览版，官方明说会有破坏性变更。所以我把兼容性写进了包的元数据，也留了一键重跑的验证脚本。

升级之后我做的第一件事不是加功能，是重跑验证。

落地案例：40 行写一个真能用的插件

场景：你每天开工都要先问一句"昨天改过哪几个文件"。你想让 agent 自己回答，不想每次都让它把目录读一遍。

做法：建一个目录，写一个入口文件，只放三样：name、inject 写 tools、apply 里注册一个工具。工具只做一件事：收一个天数参数（完整 JSON Schema，一个必填整数），读你指定的目录，返回最近改动的文件名数组。output 里写 schema 和 render，render 把数组排成三行中文。全程不超过 40 行。

验收：启动日志里出现已注册 1 个工具加工具名；在会话里问"昨天改过哪几个文件"，它调这个工具并给出文件名。两条都出现才算过。

耗时：第一次 40 分钟（含读契约），第二遍 10 分钟。

读完这一篇，你应该能用一个 40 行的插件，替掉每天早上那一次翻目录。

十、下一篇

下一篇我想弄清给插件加界面是怎么回事。客户端半体怎么注入，页面、侧栏、会话节点各挂在哪。

我这个研究台的界面还没开始。最麻烦的一步我已经试过了：查界面插槽的接口，十秒超时，没拿到数据。所以下一篇的第一个动作是重连页面再查，不能凭印象写插槽名。

如果你也在写第一个插件，我最想问一个问题：你验证过"模型真的能用"吗，还是也跟我一样，看到注册没报错就收工了？

这两个状态之间，我隔了一整轮排查才走过去。

术语小抄

name：插件的名字，一个字符串，宿主靠它认人。

inject：我写的一个清单，意思是"这些服务得先在了我才开工"。它同时也是加载顺序的写法。

apply：插件被加载时自动执行的那个函数，我的所有注册动作都写在里面。

ctx：宿主递给我的那个上下文对象。我要注册工具，就伸手问它要 tools。

output：声明"我的执行函数会返回一个什么样的值"。少了它，注册直接被拒。

render：把返回值排成模型读得顺的文字的那个函数。数据和文字在这里分家。

我还没搞懂

一、defineTool 到底替我省了多少事？我知道它编译参数表、推类型，但它在编译的时候还做了哪些校验，我没读完。

二、模型看到的参数表，和我在注册时写的 schema，中间还经过几道加工？我只能证明"注册没报错"和"现有工具都是完整 JSON Schema"，中间那段我没证据。

三、多个插件注册同名工具会怎样？官方说同一层里重名会失败，但"层"具体怎么算，我还没试。

四、插件卸载的时候，我那些注册到底按什么顺序撤？我知道有撤销这回事，没亲眼看过顺序。
