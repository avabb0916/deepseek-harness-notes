我的插件只有一半：另一半跑在浏览器里

系列第 20 篇 ｜ 版本 v1.2 ｜ 2026-11-08 ｜ 依据：本机实测 + 系列资料

这篇讲我一个想不明白的事：我的插件明明装好了，模型能用，可人打开窗口，什么都看不到。

后来我才知道，我给插件写了"手"，没写"脸"。手是给模型用的，脸是给人的。这两样在 DSH 里是分开做的，做在两套程序里。

这篇就是我弄懂这件事的过程，以及我最后做出来的东西——一份设计稿，不是能用的页面。

读完你能做到

  • 说清一个插件为什么必须分成宿主和浏览器两半，而不是塞进一个程序
  • 在包清单里加一段客户端声明，让宿主知道这个包还有另一半
  • 选一个已经分好空间的 slot 挂视图，数据走远程方法，不自造路由

一、我原来的判断，和现在的

我给研究台插件写完工具，五个，全在真宿主里注册成功。然后我发现一件事：在界面里，我什么都看不到。

它能回答"今天该写哪篇"，但只回答给模型听。人打开窗口，看不到这个系列有几幕、哪一列在堵、素材还够不够。它没有脸。

我原来的判断：插件就是注册工具。把能力写成工具挂上去，插件就完整了。

现在的判断：插件是两半加一个注册面。我只做了跑在 Node 的那半，另一半跑在浏览器里；界面不是装饰，它是插件能力里"人能用"的那部分。

二、两半，是官方的说法

我一开始以为"一个插件"是一个模块。翻资料才发现，官方的用词很稳定：两半。

Host half、browser half，或者说 Node 半边、浏览器半边。这一批资料里有一份专门的核查，在安装包内三百多个官方包的 README 里全文检索，两个词命中很多次；而"三半""three halves"是零命中。

为什么要切成两个程序？官方开发文档给的理由很硬：两半都要在 Cordis 的 Context 上做类型声明合并，而且是同名不同实现——同一个键，宿主那边是一套服务，浏览器那边是另一套。一个程序同时看见两份声明，会直接报冲突。

所以分成两个编译程序，是物理上必须，不是审美选择。

这也解释了一个我原来想不通的问题：为什么浏览器那边不能直接用宿主的工具注册表。因为它们根本不在一台机器上，也不在一个运行时里。

顺带纠正我自己一个说法。我原本想说"插件有三个半边：宿主、浏览器、工具"。查完发现，工具不是第三半，它是面向模型的注册面：注册进宿主的工具注册表，schema 自动流进系统提示的组装。它是运行期的东西，不是编译期的半边。

准确的说法是：两半身体，加几个面向模型和界面人的注册面。

三、一个包，两个身体

一个 npm 包里怎么放两个身体？答案在包的清单里。

宿主那边，清单的入口文件指向一个模块，导出一个 apply 函数。浏览器那边，清单里加一段声明：平台写 web，再列一个注入数组，写明它要等哪些浏览器模块先就位。

我手边最完整的例子是一个第三方上下文插件。它的清单里，那一段一共六项：远程接口、连接、语言包、会话界面、设置界面、右侧栏。另外还导出了一个客户端入口文件。

它的补丁文件只有六行，注释比代码值钱，原话大意是：这一行把包的主入口当作宿主半边加载；而那段客户端声明，让 Web 应用把它的客户端包当作浏览器半边加载。

一行配置、一个包、两个身体。这就是"一切都是插件"最小的完整形态。

浏览器那半怎么被送到页面里？有个专门的模块负责：宿主半边扫描启用的配置条目，拼出一张启动图；有 Web 载体时，把每个声明的客户端包成一个可加载的 bundle，走插件路径发出去；顺序还要保证动态提供的模块先于消费者。

而我原来以为"依赖注入"只是宿主的事。翻完发现不对：客户端那半也有注入数组，只是它等的是浏览器服务。注入这个机制，两半都成立。

四、挂进界面，靠 slot，不靠改 DOM

我的第一反应是：那我在页面里找个位置插进去就行了。

这个想法错了，而且是那种"能跑但会坏"的错。官方的界面插件文档写得很直白：不要在插件里替换应用根节点，不要往页面体里再追一个应用。

正确的入口是 slot：界面上预先划好的、带位置和属性的挂载点。

写界面那半的时候，不是一个组件文件搞定，而是一个注册动作：注册一个懒加载的工厂函数，标识等于包名；React 从浏览器的模块表里拿，不需要再装一份，也不该从外面引脚本。

真正挂载时，往目标 slot 上注册视图。而且这层注册是有主人的：父级声明收起来，注册自动撤掉；父级回来，注册重新装一遍。

选哪个 slot 也有讲究。官方文档的建议是：优先选一个"已经分配好空间"的 slot，比如输入框上方那条工具带；只有确实需要浮层、而且位置清楚时，才去用覆盖层。这句话背后的经验是——别自己算坐标。算出来的位置，会随宿主改版漂走。

这条设计对我影响挺大。我原来以为"注册"就是一次性动作，写完就留在那儿；实际在 DSH 里，注册是可撤销的效应——宿主半边如此，浏览器半边也如此。

写的时候还有几条规矩，都是我读过之后才明白为什么的：

一是我没有让自己的组件去引官方界面组件库。那些包会变，插件是纯 JavaScript，没有类型兜底。我为了长得像，去抄了标记和样式，把类名换成自己的前缀。

二是样式只用主题变量。我第一版写死了颜色，宿主一切深色，白底就露馅了。

三是界面上的文案要走语言包服务。我原本直接写死了中文，读完文档才知道还有这么一层。

四是最狠的一条：组件抛异常，那个 slot 条目会直接变成空白。控制台只会丢一句"某个 slot 里的条目崩了"。所以视图外层该有一层兜底。

五、对话流也是一种界面

除了页面和侧栏，还有一种挂载点我原来没想到：对话流本身。

做法是注册一类"会话节点定义"：给一个种类标识，再把视图注册到会话流的 slot 上，用那个标识当渲染键。

这跟工具结果渲染是两件事，值得分清楚。

工具结果渲染解决的是"这次调用返回了什么"，跟着一次调用走；会话节点解决的是"这段内容在对话里长什么样"，跟着会话日志走——分页、滚动、归属第几轮第几步，都由对话层负责，插件只负责一个节点画成什么样。

换句话说，这个定义交出去的是"长什么样"，不是"放在哪"。放在哪由对话层决定，它要保证一屏里的顺序、折叠、以及重新打开会话时还能复原。插件要是自己去算位置，等于把这份工作抢过来又做不对。

我这次的插件两条都没用上。工具结果走的是默认渲染，界面还是一个静态设计稿。也就是说，我这个插件的"脸"，连挂载点都还没选。

六、数据从哪来：别自造路由

这是我在设计稿阶段做的唯一一个架构决定。

两半不共享内存。浏览器那半拿不到宿主那边的对象，也读不到本地文件。所以界面要显示"磁盘上有 13 篇"这种数字，必须有通道。

通道有两条。一条是宿主把一个只读查询暴露成远程方法，浏览器那半直接调；另一条是自己起一个 HTTP 路由，浏览器请求，自己回。

我选了第一条。理由不高级，就是"不想养一套"：鉴权、错误码、请求生命周期，这些在远程方法那条路上已经有人管了；自造路由我就得自己再实现一遍，还得和宿主的安全模型对齐。

还有一条我原来不知道的机制：如果客户端要用的值是从会话日志派生出来的，不该让客户端自己折叠日志，而该在宿主那侧的投影上声明一个视图，客户端直接拿到算好的值。

一句话：能算在宿主那边，就别让浏览器重算。这是我这次唯一想清楚的事。

七、我做了什么：一份能打印的设计稿

讲完原理，说结果。结果很有限：我做的是设计稿，不是接入页。

产物是一个单文件 HTML：内联样式、零外部依赖、双击能离线打开、带打印规则。桌面 1440 宽，A4 纵向打印出来四页，四万多字节。

第一屏是判断：磁盘上已经写完 13 篇、49,121 个字，研究台里对得上的 0 篇；再跟一句结论，今天该做的不是写，是对账。

再往下三块，就是设计文档里写的那三块：

系列进度，六幕二十四篇的刻度，每行一条：编号、幕名、刻度格、完成数、字数、这个幕要回答什么。

文章看板，六列状态：想法、提纲、初稿、待修、可发、已发。十张卡全在"想法"列，每张卡上挂着缺口标签：缺提纲、缺落盘路径、无备注。这五个空列不是占位，是设计的一部分——我要让"哪一列在堵"一眼可见。

素材箱，按类型计数（官方、社区、本机实测、随手记），加最近五条，只有一条真的。

中间我加了一条设计文档里没有的东西：对账条。左边磁盘 13 篇 49,121 字，中间研究台对得上 0 篇，右边十三行文件清单。这一条是全页唯一让我自己觉得"这个工作台值得做"的地方——它一眼指出：稿子在磁盘上，卡片在文件里，两边没接上。

页面下半部分还有一块，是我硬加进去的：写动作预览。

它长这样：一条待办——把第 1 号文章从"想法"推到"提纲"；下面两行差异，减号那行是旧状态，加号那行是新状态；再下面一行影响预测：想法那列从 10 变 9，提纲那列从 0 变 1，进度日志追加一条。最后两个按钮：批准、拒绝，都是禁用的。

为什么值得单独做一块？因为界面上最容易埋雷的地方，就是"写动作"。如果页面自己拼一个请求、插件里再写一份写入逻辑，那同一件事就有两条路径，迟早会出现"页面改了、工具没改"的数据事故。所以设计上我给自己写死一条：页面上的写动作，只能调宿主那半的同一个函数。

这条规矩在原型里只能表现为两个禁用按钮。但它决定了接入那天要改什么：按钮背后不是新接口，是已有工具的入口。

这套东西写完，我得承认一个观感：它看起来比它实际做的多。页面是静态的，按钮全禁用，输入框是假的。这正是设计稿该有的样子，也是它最大的风险。

八、两个坑，都值钱

第一个坑：先查真 slot key，再写视图。

要挂进界面，得知道挂哪。官方提供的检查接口可以查界面插槽的实时树，包括每个 slot 的可注册项和属性。我试了一次，十秒超时——页面对那次查询没有应答。

于是就卡在这。我没有凭印象写 slot 名，因为凭印象写出来的东西，最可能的结局是"装上了，但什么也不显示"，而我会以为是样式问题，去改一堆无关的 CSS。

这一步没走通，后面就全停：没有 slot key，就没有注册动作；没有注册，就没有接入。所以这篇的边界不是我偷懒，是它真的卡在第一步。

第二个坑：桌面排版在打印时会塌。

设计稿的第一版在 1440 宽下很好看。打印出来才发现：纸宽只有七百来像素，触发了我自己写的响应式断点，六列看板塌成一列，系列表格每行塌成五行，一份设计稿打成了五页。

修法不是删断点，是给打印单独写一套栅格：把桌面的列宽搬回来，字号降一点，区块允许跨页但表头不许孤行。改完打出来四页，和屏幕上那块版对得上。

我一开始以为打印是"顺手支持一下"。后来发现它是检验设计密度最狠的一关：屏幕上能塞下，纸上塞不下，说明信息层级本来就有问题。

还有个测量乌龙。我截窄屏图时，看到右侧被裁掉，以为移动端溢出了。后来写了个探针页，把原型塞进一个 390 宽的容器里，用脚本量了文档宽度：容器宽 390，滚动宽也是 390，没有溢出。被裁掉的是截图工具的最小窗口宽度，不是页面。

这件事的收获不在 CSS 上：我看到的"问题"，可能只是测量工具的口径。

还有一个小细节：页面上的数字是生成那一刻的快照。等我把这篇写完，磁盘上的稿子已经从 13 篇涨到了 22 篇。设计稿不会自己活过来——重跑脚本才会。这恰好是"原型不等于产品"最好的证据。

九、我错在哪，这篇的边界

先说最该承认的：我没有真的把客户端插件挂进 Web UI。

我这个插件，清单里没有那段客户端声明，没有导出客户端入口，没有注册过任何一个 slot。它有宿主半边，有五个工具，在真宿主里验证过注册；但它的浏览器半边，一行代码都没有。

所以严格讲，这篇写的不是"我怎么加上了界面"，而是"我搞清楚了界面该怎么加，然后只做到了设计稿"。

第二，原型不连数据。它不读宿主的任何服务，数字是脚本写进去的。所以它证明的是信息架构成立，不证明数据通道能用。

第三，数据通道只是决定，没有实现。我选了远程方法那条路，但一行都没写。

第四，所有宿主侧验证只在 0.2.2-rc.1 上做过。这是开发者预览版，官方明说会有破坏性变更；界面那一层的接口，我连名字都还没拿到。

还有一个更基本的边界：设计稿能回答"长什么样"，回答不了"挂得上吗"。挂载点、属性、生命周期，这三件事只有在真机上才算数。

十、下一步

下一篇讲这个研究台从需求到 v0.2 的全过程，包括三次返工。

那三次返工里没有一次是功能不够，全是形状不对：契约的形状、状态的边界、统计的口径。界面这一半，大概率也会栽在同一类地方——问题不在画得好不好看，在注册点有没有选对、数据有没有走对路。

所以下一步很明确，也很不性感：等页面可以应答的时候，去查真实的 slot 树，把 key 抄下来，再写第一版视图。第一版只显示系列进度这一块，先证明"能挂上"，再谈好看。

如果你也给自己的插件画过界面，我最想问一个问题：你是先画图，还是先去查挂载点？

我是先画图的。画完才发现，图再好看，也得先知道往哪儿挂。

落地案例：挂一个槽位，把磁盘上的数字显示出来

场景：你的插件已经能回答"今天该写哪篇"，但人打开窗口什么都看不到。你要在输入框上方那条工具带上显示一行：磁盘 13 篇、工作台对上 0 篇。

做法：先在包清单里加一段客户端声明，平台写 web，列出要等的浏览器模块；再写一个客户端入口，注册一个懒加载工厂，标识等于包名。挂载点选已经分好空间的工具带，不选覆盖层，也不改页面结构。数据不要自己起路由：在宿主那半把一个只读查询暴露成远程方法，客户端直接调。slot key 先用官方检查接口查实时插槽树，查不到就记成待办，别凭印象写名字。

验收：刷新页面后工具带上出现那一行字，数字和你手动数的一致；把宿主查询的返回值改一下，刷新后界面跟着变。两条都成立，才算接通。

耗时：第一次 2 小时（含查 slot key），之后加第二个视图 20 分钟。

读完这一篇，你应该能给自己的插件接上一张脸，而不是只交一只手。

术语小抄

半边：官方把插件分成两块——跑在 Node 的那半（宿主半边）和跑在浏览器的那半（浏览器半边）。一个 npm 包里可以同时装两半。

slot：界面上预先划好的挂载点，带位置和属性。界面插件往里注册视图，而不是自己改页面结构。

客户端声明：包清单里的一段，写平台是 web、要等哪些浏览器模块。宿主读到它，才知道这个包还有浏览器那半。

远程方法：宿主把自己的能力暴露成一个可以被浏览器直接调用的函数。我就不用自己起 HTTP 路由了。

投影：宿主把会话日志折叠成一个算好的值，客户端直接读。省得浏览器自己重算一遍日志。

我还没搞懂

一、slot key 到底怎么拿到？检查接口我试了一次，十秒超时，没拿到数据。是不是页面必须处于某个状态才应答，我还不清楚。

二、浏览器那半的 bundle 是谁打出来的？我知道宿主会把它包成一个可加载 bundle 发出去，但打包发生在构建期还是运行期，我没查。

三、语言包服务怎么注册？我只知道文案要走它，具体接口没看过。

四、为什么组件抛异常会让整个 slot 条目变空白，而不是只坏那一块？官方文档只说了结果，没说为什么这样设计。
