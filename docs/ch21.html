这篇讲我自己给自己写的一个小工作台：它能跑，能用，我却在两天里把它推翻重来了三次。

三次都不是因为功能不够。三次都是因为我一开始把"形状"想简单了——工具对外承诺什么、哪些数据是别人的、一个数字按什么规则数出来。

这篇是我把这三次返工摊开看的过程。

读完你能做到

  • 把六幕的计划写成数据文件，而不是写死在初始化代码里
  • 用六列状态管十张卡，id 一次定死，之后只改标题不动 id
  • 用集合差算漂移，并让脚本把口径一起打印出来

一、我原来的判断，和现在的

凌晨两点，我把这个系列的状态文件打开，改了一遍。改完发现：我给自己写的工作台，比这个系列里大部分文章都难伺候。

它现在管着六幕二十四篇的计划、十张文章卡、一条素材，以及"今天该写哪篇"这个我每天早上都要重新想一遍的问题。但它在能干活之前，被我推翻重来了三次。

我原来的判断：插件是写功能。想清楚要什么能力，把它写成工具、注册上去，剩下就是打磨。

现在的判断：插件是写契约、写状态边界。三次返工里，写错的地方没有一处是功能不够，全是形状不对。

二、需求：我要的不是写作工具

先说清楚它为什么存在，否则后面所有返工看起来都像瞎折腾。

这个系列有六个方向并行产出：官方资料、社区讨论、架构实读、文章、提纲、索引。谁写到哪、哪篇在等素材，只有统筹这个系列的那个会话知道。换一个会话，那张图就没了。

第二个痛点更具体：每天开工我要判断"今天该推哪篇"。判据是多维的——系列顺序、有没有素材、提纲落没落、上一篇是不是卡在待修。靠肉眼扫目录，慢，而且每天结论不一致。

第三个：素材散在资料文件里，一条好引文、一个链接，真要动笔时得全文搜索。

所以它的定位从一开始就很窄：不是写作工具，是状态索引。它不生产内容，只让内容生产这条流水线的当前状态可查询、可交接。

窄是关键。我一开始差点把它写成写作工具，那就是另一个故事了。

后来也砍到了五个工具，硬性定了个规矩：总数不超过五个，多一个必须合并进去。新建文章被并进了更新文章——有 id 就改，没 id 有标题和系列就新建。少一个工具，模型就少一次选错的机会。

三、第一版：三个导出的自信，撞上 111 行留下的坑

第一版的形状，我以为很清楚：三个导出。

导出 name，一个字符串当标识；导出 inject，写一个数组，说我要用 tools 这个服务；导出函数 apply，在里面调注册接口，把工具挂上去。

顺便说一句我当时就弄清楚了的事：它是不是 npm 包、有没有那个 dsh.plugin 标记，跟能不能跑无关。那只是分发形态和识别标记，真正的加载靠配置里插进来的那一行。

再加一段：宿主调 apply 的时候可能抛异常，所以整个函数体包在 try 里，注册失败就打日志、返回空表，让宿主继续跑。这一点我当时就想到了，因为我不想因为一个插件把整个环境搞坏。

问题出在"注册"这一步写成什么样。

工作区里已经有一个我自己更早写的小插件，管外链的，111 行。它的注册代码很直觉：给一个对象，写 name、description、parameters，再把处理函数放进去，函数里直接返回内容。它的 README 里留了一句话：宿主内注册尚未验证。

我当时看到这句，觉得挺诚实，但没当回事，照它的形状写了研究台的第一个工具，然后放进真实宿主里看日志。

报错原文是这样的：tool "naive_tool" must declare output { schema, render, presentationMeta? }。

一行。意思很直白：我注册的工具必须声明 output，里面要有 schema 和 render。

我不太服气，又试了一次：补上 output，但只写 schema，不写 render。报错一模一样。

这时候我才回去认真读契约：定义里要有 name、description、parameters，加上 output，output 里要有 schema 和 render；再加处理函数，接收参数和执行上下文。内容和文字是由 render 生产的，处理函数只负责返回一个规范的值。

顺手我也确认了另外两件事。

一是 parameters 要写完整的 JSON Schema：一个对象，标类型，逐个字段写进 properties，必填项单独列一个数组。而官方文档示例里那种"参数表"写法，是辅助函数帮你编译成 JSON Schema 的；直接调注册接口，得自己写完整。

二是宿主不校验 parameters 的形状。我做了第三个探针：parameters 用参数表，output 补齐，注册——没报错。

这一下我就明白哪里最危险了。缺 output，注册当场炸，我立刻知道错；参数表写错，注册一声不响，我以为成了。

第一版真正的成本不在功能上。五个工具的业务逻辑我写得很快，反倒是"形状"占了大头。

四、验证：不花钱也能证明它成了

写完之后我面对一个新问题：怎么知道它真的能用，而不是"看起来注册了"。

我的做法是四步，一步比一步硬。

第一步，纯函数单测，不碰宿主。把能算的都拆成纯函数：选篇排序、登记素材的校验、改文章状态、坏文件怎么兜底。然后用一个假的 ctx 把插件装起来，检查注册出来的东西结构对不对。最后是 89 条断言全过，其中相当一部分查的是失败路径：坏 JSON、写不进磁盘、注册函数抛错。

第二步，用临时家目录起一个干净的 profile。我用 DSH_HOME 指向一个临时目录，从官方模板新建了一个叫 lab 的 profile，和日常在用的那个完全隔离。我不想因为测插件把每天在用的环境弄坏。

第三步，看层栈。用 dsh --profile lab --dump-config 打出组合后的配置树，在我这里一共 1248 行，我那一行出现在 1245 到 1248。这个数比日常那个 profile 小得多，因为它是从模板新建的，只叠了基础层、界面层和我这一行。

看到自己的 id 躺在最后一段，才算真进了层栈。

第四步，看激活日志。启动界面时，我的 apply 里会打一行字：已注册 5 个工具，后面跟着五个工具名。这行字出现，说明 apply 跑通了、五次注册全被接受。

顺带我还做了一次反向实验，因为"失败要软着陆"这句话我之前只是听说。

我在同一个 lab profile 里塞了一个故意抛错的坏插件，就三行：导出 inject，导出 apply，apply 里直接 throw。然后启动服务。

日志是这样的：先是我的研究台正常注册，接着一行 dsh: warning: 1 entry did not activate，再下面是那个坏插件被点名报错。

而界面照常起来了，带 token 访问返回 200，页面四万字节；不带 token 是 401。

结论很明确：单个插件抛错，宿主会给它一条警告、跳过它、继续跑。

那为什么还要在插件里再兜一层？因为宿主兜的是"整行不激活"，我想要的是"部分能力还在"。注册五个工具是个循环，如果第三个定义有问题抛了异常，没有内层 try 的话，后面两个就一起丢了。

这也是我后来一直记着那句判断的原因：插件的失败成本不对称——最坏丢一两个工具没人受伤；可要是赌"宿主会兜住"，风险就摊给了整个环境。

五、返工一：五个系列，变成六幕二十四篇

第一版写完当天，数据结构就被现实改了。

我按当时的项目简报，在初始化逻辑里写死了五个系列：前世今生、设计原理、底层架构、怎么用、怎么写插件。计划篇数加起来是 18。

几小时后，提纲落地，是六幕：起点 3 篇、上手 5 篇、设计原理 5 篇、底层架构 5 篇、建设者 4 篇、判断 2 篇。合计 24 篇。

差得不算离谱，但性质变了：我的五个系列里，"怎么用"要拆成"上手"，"怎么写插件"要扩成"建设者"，还多出一个"判断"。

这时候我面对一个选择：要不要连 id 一起重排？

我一开始是真想重排的，因为 s-01 到 s-05 的顺序和新六幕的顺序对不上，看着别扭。手都放到键盘上了，突然想到一件事：十张文章卡和所有素材，是靠系列 id 挂靠的。id 一动，全部失联。

于是改成：id 全保留，只改标题、排序、计划篇数和目标。原有五个系列按语义映射过去，新多出来的那一幕补一个 s-06。

具体落到文件里是这样：起点 3 篇、上手 5 篇、设计原理 5 篇、底层架构 5 篇、建设者 4 篇、判断 2 篇，合计 24 篇；id 是 s-01、s-04、s-02、s-03、s-05、s-06，顺序号变了，id 没变。

还有个细节我一并改了：插件里的初始化骨架也同步成六幕。因为初始化动作是幂等的，但有一个 force 开关会覆盖；如果骨架还停在五系列，某天误跑一次 force，好不容易对齐的 24 篇就被退回旧版了。

这个坑我现在写进设计文档了，标成警告那一句。

我这一节的结论只有一条：骨架不是数据。我在初始化逻辑里写死的结构，会在第一次和真实提纲对齐时变成负债；能靠改数据解决的，别改 id。

六、返工二：漂移不是减法

第二版做完，我开始做界面原型。原型上有一条我自己很喜欢的对照：磁盘上已经写完多少篇，研究台里登记了多少篇，差多少。

第一版的算法特别朴素：磁盘篇数减卡片数。当时磁盘 11 篇、卡片 10 张，页面显示"漂移 1 篇"。

我看了一眼，觉得不对劲。那 10 张卡里的标题，没有一个和磁盘上的稿子对得上——它们是我初始化时手写的选题占位。真实情况是：11 篇稿子，一张卡都没登记，漂移应该是 11。

两个数字相减，得到的是"数量差"，不是"漂移"。漂移是集合差：磁盘上有、研究台里没有的那些。

改法是把比对写实：按路径比，路径相同算同一篇；路径没有，就按标题比，去空白、忽略大小写。改完之后，漂移从 1 跳到 12，然后又跟着磁盘长到 14。

这一版还顺手改了一处措辞。原来封面写"研究台里还是 0 篇"，读起来像"研究台是空的"；改成"研究台里对得上的：0 篇"——研究台里其实有 10 张卡，只是没一张对得上磁盘的稿子。

我这一节的结论：两个集合的差，不等于两个数字的差。统计口径写错了，页面比没有页面更危险，因为它看起来很权威。

七、返工三：12 变 14，又回到 13

第三次返工是我最不想提的一次，因为它纯粹是粗心。

原型的数字本来是手写的，后来我改成脚本生成：扫文章目录，数 .md 文件，算汉字数。跑出来 12 篇。

过了一会儿再看，13 篇。再过一会儿，14 篇。我当时的第一反应是"大家写得真快"，还顺手把封面的数字一起改了。

直到统筹的人提醒我一句：你把核查报告和写作手册也算成篇了。

我去看过滤条件，写的是"排除 00 开头的文件"。可目录里除了 00 开头的写作手册，还有一个 99 开头的核查报告。它被算进了正文。

改成"两位数字前缀，且排除 00 和 99"之后，数字回到 13 篇、49,121 个汉字，和实际稿子一一对上。

这件事让我把口径写进了两个地方：脚本的控制台输出里，和原型页脚的一行小字——漂移 = 磁盘正文篇数减研究台里能对得上的卡片数，还跟着写了当前算式：13 减 0 等于 13。

我这一节的结论有两条。第一，数字必须由脚本生成，手改的数字迟早对不上。第二，口径要写进交付物，不能只存在我脑子里——不然下次被问"这个数怎么来的"，我只能重算一遍。

八、三次返工的共同点：错的全是形状

把三次返工摆在一起看，有个共同点很明显：没有一次是功能不够。

第一次错在契约：output 是必填字段，我照着一份没写完的旧代码抄，抄出了一个注册不上、或者注册上了但模型拿到废参数表的工具。

第二次错在状态边界：id 是外键，我差点为了"看着顺眼"重排它，那样十张卡和素材会集体失联。

第三次错在统计口径：同名不同物的时候，减法不等于集合差；文件名的规则不写清楚，数字就会自己长。

这三次都不是"再加一个工具"能解决的。它们分别对应三件事：这个能力对宿主承诺什么形状、这个插件的状态被谁引用、这些数字按什么规则数出来。

所以我后来写插件的顺序反过来了。先写三张纸：工具面对宿主承诺的字段是什么、哪些数据是别人的外键不能动、每个统计数字的定义是什么。写完这三张纸，功能往往很快就填完了。

我一开始以为这是我的个人习惯。后来发现它其实是插件这种形态的必然：插件不是独立程序，它是长在别人运行时上的东西，形状对了功能才可能对。

九、我错在哪，这篇的边界

先说这篇最该承认的错误：我把"注册没报错"当成"功能能用"。

这个判断偏差让我在同一件事上绕了两圈。直到今天我也只能说，注册成功是必要条件，不是充分条件。

再说三个边界，都不许当成已完成。

第一，我没有真跑过一轮模型调用。所以"模型看到参数表长什么样""失败返回值会不会被标成错误"这两件事，我只有推论，没有证据。要补这一步得花一次真实调用，我一直排在后面。

第二，客户端页面还没接真数据。原型是一份静态 HTML，数字由脚本写死进去；真正接入要走宿主的数据通道，而第一步——查界面插槽的接口——我试了一次，十秒超时，没拿到 slot key。所以原型证明的是"信息架构成立"，不是"能接上去"。

第三，官方的安装流程我没走。我只走了手工那条：把插件链进 profile 的依赖目录，再往用户的补丁层插一行。官方的安装命令和插件管理器动作会改当前 profile，而当前 profile 就是我天天在用的那个，我暂时不敢。

还有一处得说清楚：严格讲，它现在管的是"计划与判断"——六幕的篇数、十张卡的状态、今天该写哪篇。磁盘上那十三篇正文，它一篇都还没登记回来。这正是漂移那条要暴露的事，也是下一版第一个该补的动作。

另外，所有验证都只在 0.2.2-rc.1 上做过。这是开发者预览版，官方明说会有破坏性变更。

十、下一步

下一篇讲什么该插件化、什么不该。这个判断我在这三次返工里被逼出来了半个：插件适合承担"每天会重复问的判断"，不适合承担"还在变的结论"和"跑几分钟的任务"。

我的系列标题、篇数、判据这一周改了三轮。如果我把它们焊进插件的流程里，每改一次就要改代码、重装、重启。现在它们全在数据文件里，改一次是一个 JSON 字段。

如果你也在给自己写工作台，我最想问一个问题：你返工的那几次，是因为功能不够，还是因为形状没想清楚？

我这边三次全是形状。而且每一次，都是在"它能跑了"之后才发现的。

落地案例：用研究台管一个十篇的系列

场景：你手上有一个十篇的系列，写到第三篇开始乱：哪篇在等素材、哪篇卡在待修，只有你脑子里有。

做法：先建六个系列槽位，每个写标题、计划篇数、要回答的问题；id 一次定死，之后只改标题。再把十篇登记成卡片，每张写标题、所属系列、状态、落盘路径；状态只用六列：想法、提纲、初稿、待修、可发、已发。每周跑一次对账：磁盘上的正文篇数，减去工作台里路径对得上的卡片数，差出来的就是漂移。

验收：任意一天问"今天该写哪篇"，它给出一篇并说出理由：系列顺序、素材够不够、上一篇是否卡在待修。对账数字和脚本数出来的一致。

耗时：第一次建库 40 分钟，之后每周维护 10 分钟。

读完这一篇，你应该能把一个系列从"我记得"搬到"它记着"。

术语小抄

契约：工具对外承诺的东西——名字、参数长什么样、返回什么。写错了，注册可能不报错，但模型拿到的是废的。

外键：别人靠这个编号来挂靠自己。比如文章卡和素材都靠系列 id 挂靠，所以这个 id 一旦改动，关联的东西就全丢了。

漂移：磁盘上有、但工作台里没登记的那些稿子。它是"集合差"，不是"两个数字相减"。

口径：这个数字到底怎么算。比如"篇数"要不要算写作手册和核查报告，就是口径问题。

幂等：同一个动作重复执行，结果一样。初始化是幂等的，但那个 force 开关会强行覆盖，所以骨架写错时误跑一次就会退版。
