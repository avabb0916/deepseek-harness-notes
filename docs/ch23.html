DSH、Claude Code、Codex：三种 Agent 形态，不是三个竞品

这篇想回答一个我被私信问过的问题：这几个终端里的编程助手，到底哪个强。

我一开始也以为它们是一回事，后来发现连官方都不这么看。所以这篇不比分数，只做一件事：把它们摆在不同货架上，看各自占哪一格。

上周有人私信我，让我给个干脆的结论：DeepSeek Harness 和 Claude Code，到底哪个强。

我说这问题我答不了。不是客气，是它默认这两样东西摆在同一个货架上、贴着同一张价签。我一开始也这么以为。翻完官方资料、又在自己机器上把配置树 dump 出来之后，我发现连 DeepSeek 自己都不这么看。

我原来的判断

我原来判断：DSH 就是"国产版 Claude Code"。理由很顺手——都能在终端或桌面里改代码，都有插件，都能接 MCP，发布时间又晚一年多，那不就是照着抄一遍、再用便宜模型打价格战吗。

现在的判断：这是三种形态，不是三个竞品。Claude Code 和 Codex 是两件成品，DSH 是一个可替换的运行时。所以真正的问题不是"哪个更强"，而是"你要买成品，还是要自己盖房子"。

这个问题问错了，后面所有比较都会歪。

转折：官方文档里那两句话

第一句在 DSH 的版本日志里。2026 年 10 月 3 日，v0.2.1-alpha.1，官方加了一个实验性的 Claude Code Mods 兼容层，然后自己写了一句注释，大意是：现阶段的主要目的是验证 Claude Code Mods API 的功能大致为 DSH 插件的一个子集，而不是为用户提供实际的完整兼容性。

我注意到这个措辞。它没说"我们要兼容 Claude Code"，也没说"我们要替代它"。它说的是：我怀疑你那套扩展接口，是我的一个子集。这是一句技术判断，不是一句营销话。

第二句在 DeepSeek 的 API 更新日志里，2026 年 10 月 17 日。同一页面上，官方同时承认了两件事：一，DeepSeek 系列模型的 Code Agent 基准测试，用的是 DSH 的极简模式作为框架；二，Terminal-Bench 4.0 这个测试，用的是 Claude Code 框架。

一家公司，一边用自家 harness 跑分，一边老老实实写上"这项我们是用 Claude Code 跑的"。这不像打仗，更像实验室。

还有一条更容易被忽略的：2026 年 8 月 19 日的 v0.1.0-rc.8，官方把 Claude Code 和 Codex 的子代理做成了可以按需安装的 Profile Bundle；到 11 月 4 日的 v0.2.2-rc.1，又加了个实验性工具 subagent_oar，能把独立任务直接交给本机的 Codex 或 Claude CLI 去跑。

还有一处，是我翻 API 文档时撞见的。DeepSeek 的文档站有个栏目叫 Agent Integrations，我本以为里面只放"怎么用 DeepSeek API 接第三方工具"。点进去发现，这个列表的第一项是 DeepSeek Harness，后面依次是 Claude Code、Codex、OpenCode、OpenClaw、Hermes、Reasonix、WorkBuddy/CodeBuddy、Qoder。

也就是说，在 DeepSeek 自己的官方文档里，DSH 和 Claude Code、Codex 是并排的八个条目之一。它是被当成"一种接入 DeepSeek 模型的方式"列出来的，跟其他七种平级。

这一栏的存在本身就说明了很多：官方想要的不是"你换成我"，而是"你用谁都可以，只要用的是我的模型"。

一个把竞品装进自己肚子里的产品，不会把自己定义成竞品。

三种形态，看三个能核对的结构事实

我不喜欢用"定位""理念"这种词做对比，太容易说服自己。看三个能查的硬指标。

第一个是时间。Claude Code 的 GitHub 仓库建在 2025 年 2 月 22 日，Codex 建在 2025 年 4 月 13 日，DSH 建在 2026 年 8 月 13 日。晚了大约十八个月和十六个月。

十八个月在 agent 这个行当里是很长的时间。第一代人把"终端里的 agent 该长什么样"试出来了——权限怎么问、diff 怎么看、上下文怎么压、什么时候该停。第二代人不用再猜这些，可以直接在骨架上做选择。DSH 选的是：把骨架全部拆成插件。

第二个是许可证。DSH 是 MIT，Codex 是 Apache-2.0，Claude Code 的 GitHub 仓库在 API 里没有 license 字段。

这三个不一样，不是道德高下，是三种商业选择：买的是使用权、源码，还是组装权。买使用权，得到一套调好的体验；拿到源码，能改但得自己维护；拿到组装权，得先想清楚要组装成什么。

第三个是他们怎么描述自己。Claude Code 的仓库简介是"一个住在你终端里的 agentic 编码工具，理解你的代码库，帮你更快写代码"。Codex 的 README 第一行是"来自 OpenAI 的、运行在你本机上的编码 agent"，仓库简介更短："一个跑在终端里的轻量编码 agent"。

DSH 的简介是"DeepSeek Harness：一切皆插件"。官方文档站给的一句话定义是"用于构建 Agent Harness 的插件化 SDK"。

工具和 agent 关心的是"帮我把这件事干完"，SDK 关心的是"你打算拿它搭什么"。这三个句子的主语不一样，产品形态就不可能一样。

那个"精装房"的比喻，我想补一句

知乎上有一句我觉得说得最准的话，被转引过很多次：如果说 Codex 是精装房，那 harness 就是画了一块地，给你一堆水泥沙子。

这个比喻对了一半。对的那一半是交付形态——一个是拎包入住，一个得自己砌墙。

我想补的是另一半：这块地上其实已经盖好了一栋楼。DSH 出厂就带五个 profile——web、headless、sdk、sdk-minimal、acp，桌面版、网页版、一次性命令行、给程序调用的 SDK 服务，都是现成的。

所以它更像我老家的自建房：框架、水电、门窗全装好了，能住；但承重墙也允许拆。差别不在装修档次，在"你动得了哪面墙"。

在 Claude Code 里能换的是用哪个模型、挂哪个 MCP、加几条自定义指令。在 DSH 里能换的是模型适配器本身、工具注册表本身、会话日志本身，以及 agent 循环本身——这四样在官方架构文档里被明确写成"每一部分都是插件"，而且"不存在需要打补丁的特权内核"。

我在本机 dump 到的东西

这一段是我这篇里最想写的部分，因为它是能复现的。

我在自己机器上跑了一条命令，把 web profile 的完整配置树打出来，一共 2380 行。里面有个东西叫 agent preset，一共四个：standard、ptc、minimal、cordis。注册表里的默认值是 standard。

那个叫 minimal 的，就是官方口径里的"极简模式"。

我原以为"极简"是形容词，打开看才发现是字面意思。它的工具面只有两个：一个 readImage，一个持久的 bash。文件读取、写入、编辑三个开关，全是 false。

它的系统提示词前缀只有一句话——"你是一个有帮助的软件工程师助手"——并且明确关掉了运行时上下文注入。

顺手把一个我上一篇标了"待验证"的问题结掉：极简模式不是 sdk-minimal 那个 profile。sdk-minimal 是给 SDK 用的另一套东西，自带完整的显式配置树，里面根本没有这四个预设。极简模式就是 minimal 这个 agent preset，跟着 web 这类标准 profile 一起发布，不用另装任何东西。

这个"两个工具"的数字，和澎湃新闻那篇实测对得上：极简模式 2 个工具、标准模式 26 个工具，拿去做一个单页官网，"几乎没拉开差距"。

工具多不等于结果好。这句在别处是一句经验，在这里是一个可以打开配置、逐条数出来的事实。

所以这是一张分工表

我把它们排成一张表，不是比高低，是看各自占哪一格。

Claude Code 是成品。模型和体验绑在一起卖，你付钱买的是"已经调好的那一套"：它知道什么时候该问你、diff 怎么排版、上下文什么时候该压。这些东西改不动，也不需要改。

Codex 是同层的另一件成品。同样绑模型（绑 OpenAI 的），同样卖调好的体验，只是形态更轻，也开了源。

DSH 是可替换的运行时。模型、工具、循环、会话存储、沙箱策略都能换，代价是得自己决定换什么。

Cursor 是 IDE 层，我不放进这张表。原因很直接：我把 DSH 的官网、文档站、整个仓库翻了一遍，官方对 Cursor 的提及是零。硬把它拉进来凑"四国杀"，是内容需要，不是事实需要。

真正的分工是：上面两家在争"谁的成品更好用"，DSH 在争"你愿不愿意自己组装"。这是两个不同的购买决策，不是一个排行榜的上下名次。

这里有个陷阱，我自己差点踩进去。网上有很多横评，用同一个模型分别套在 Codex、DSH、WorkBuddy 上跑同样的任务，然后比谁快、谁便宜。澎湃那篇实测就是这么干的，它甚至在同一批任务里对比了标准模式和极简模式。

这种横评有意义，但它测的是"模型加某套壳"的组合成绩，不是壳本身的高下。因为同一个模型换一套系统提示词、换一套工具、换一个压缩策略，成绩能差出一大截——官方自己都承认，他们为了适配 V4.1 去调了图片缩放和 token 估算。

所以看到"某模型在 DSH 上比在某 CLI 上高几分"这种结论，那个数字可以信，但别把它翻译成"DSH 比某 CLI 强"。它可能只说明那套壳对那个模型的适配更早一步。

四个问题，我拿来自查

与其背结论，我宁愿带四个问题回来。

问一：你要不要锁模型？

如果答案是"我就要最强的那一个，谁强我用谁"，成品更划算，因为成品在追新模型这件事上是零成本的。如果你的答案是"我要能随时把模型换掉，甚至换成本地模型"，那只有运行时给得了你。

问二：你要不要改工具链和循环？

绝大多数团队不需要。我需要的可能只是多几个 MCP、多几条规则。但如果你在做的事本身就跟"agent 怎么跑"有关——比如你要给业务嵌一个 agent、要控制每一步的审批、要知道每个工具的耗时——成品会立刻撞墙，因为你能插手的只有外围。

问三：你的合规允不允许会话数据过第三方？

这一条最容易在选型会上被忽略，出事时最贵。DSH 的桌面版被社区指出默认开启遥测；后来有用户在 Hacker News 上澄清，说真正上传的是把会话记录附加到 DeepSeek API 的推理请求里，而这部分本来就要随请求发出去，如果你接本地模型就什么都不发。他同时说，桌面版这个默认值"令人失望"。

这段话我读了两遍。它同时说明了"它没那么可怕"和"它确实有默认值问题"。合规判断不能靠产品名，要靠配置。

问四：谁维护？

成品的维护方是厂商，你付订阅。运行时的维护方是你自己，或者你那半个工程师。Hacker News 上有个人说他攒了 25 个下游 commit、0 个新插件——"一切皆插件"的真实代价不是学不会，是核心功能也能被改，于是得自己跟进上游。

我错在哪，以及 DSH 的代价

我原来的错有两层。

第一层是把"产品成熟度"当成唯一标尺。用这把尺子量，所有 harness 都像半成品，因为它们本来就不是成品。第二层是把"开源"自动等同于"更好用还免费"，这是这几年最容易被带着走的一个错觉。

DSH 的代价，我按重的说，不修饰。

它是预览版，官方 README 用全大写写着"将出现破坏兼容性的变更"。从 2026 年 8 月 17 日到 11 月 4 日，79 天发了 37 个版本，一个正式版都没有，平均两天多一个版本。跟着它跑，就得接受随时返工。

安全上，官方自己的安全声明写着"尚未接受安全审计，不得视为安全或可用于生产环境"。2026 年 9 月还公开过一个 9.4 分的漏洞：沙箱里的一条命令，能把会话切到全权限模式、自己把沙箱关掉。修复先推到 GitHub，隔了三天才到 npm。这类时间差，在生产环境里是要命的。

成本也不是零。社区里有人说 API 两天半花了快五十块，也有重度用户说一周二十美元、挂了三十个插件。这不算贵，但它不是免费，而且要你自己盯着。

所以我的选择很朴素：如果我的活是"这周把这个功能上线"，我选成品；如果我的活是"给团队造一个能长期改的 agent 基座"，那才轮到它。

这两件事没有高下，只有先后。

下一篇

这个系列下一篇文章，我想算一笔账：现在用 DSH，本质上是在赌一个还没定型的架构。赌注的赔率是多少，什么信号出现该加注，什么信号出现该撤。我会把自己这一年里判断错的地方也写进去。

你现在用的是成品，还是自己搭的？如果是自己搭的，卡在哪一步——是搭不起来，还是搭起来了没人用？也欢迎说说你选错了的那一次。留言告诉我，下一篇我会挑几个具体场景讲。

术语小抄

成品：模型和体验绑在一起卖，付钱用调好的那一套，改不动也不需要改。

运行时：骨架也给出来，模型、工具、循环都能换，代价是得自己决定换什么。

profile：一套预先配好的启动配置，桌面版、网页版、一次性命令行各是一个。

agent preset：同一套配置里再选的"性格"，比如标准、极简。

MCP：一种让外部工具接进来的通用接口，各家都在用。

我还没搞懂

一，横评里"模型加某套壳"的成绩，有多少算壳的功劳，我拆不开。

二，六成用户装了第三方插件，这是官方口径，我没法独立验证。

三，桌面版默认遥测那条，社区澄清说上传的是随请求就要发出去的会话记录。道理我懂了，但"默认值该不该这样"，我还没想清楚。
