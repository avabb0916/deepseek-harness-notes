官方把 Agent 从会话里拿出来了：Super-agent 设计笔记

版本 v1.1 ｜ 2026-11-08 13:35 (Asia/Shanghai) ｜ 依据：官方《Super-agent 设计探索》（2026-10-31）+ dsh-superagent-prototype + 本机 dsh 0.2.2-rc.1 实测
系列第 25 篇 ｜ 版本 v1.1 ｜ 2026-11-08 ｜ 依据：官方《Super-agent 设计探索》（2026-10-31）+ dsh-superagent-prototype + 本机 dsh 0.2.2-rc.1 实测
学习笔记 ｜ 第 25 站 ｜ 我带着的问题：如果 Agent 已经能自己干活，为什么我们还在一个会话一个会话地伺候它？
读之前我以为：Super-agent 就是"更强的模型 + 多开几个 agent"。
读完我的一句话答案：它是一套把会话从"工作单元"降级成"实现细节"的系统架构，模型只是其中一个零件。
读完我能答出来的三个问题：1 官方说的四个特征是哪四个，为什么单个 ReAct 循环给不了？ 2 Router 和 Worker 各自负责什么，为什么 Worker 不直接对人说话？ 3 实验里"更高产"的代价是什么？（答不出就说明我没学会，这篇先不发）

先说人话：我原来以为，Agent 的边界就是聊天窗口——一个窗口一件事，事情多了就多开窗口。官方这篇文章说，这个边界是错的：窗口只是你看到的那一层，底下应该是一套能同时接很多活、你在哪儿说话它都在、出事还能自己爬起来的系统。这篇就是我把这套设计读明白的笔记。

一、我原来的判断

我原来的判断：Super-agent 是"模型更强之后自然出现的形态"。模型越会调用工具，Agent 就越自主；自主到一定程度，就成了 Super-agent。所以要等模型，不用改架构。

现在的判断：模型再强，也改不了三件事——一个 ReAct 循环一次只能走一步；不同任务挤在一个上下文里会互相污染；跑它的那台机器一关，它就停了。这三件事不是模型问题，是系统问题。官方文章开篇就写了：单个 ReAct 循环无法同时提供那四个特征，它们必须来自外围架构。

这句话把"等模型"变成了"改系统"，是整篇文章的分水岭。

二、四个特征，其实是四道验收题

官方给 Super-agent 定了四个特征，我读下来觉得更像四道验收题：

第一，连续。你在 IM 里说方案 A，后来在 GitHub 评论里改成方案 B，它得知道这是同一件事、并且改过来。不用你琢磨"会话 X 里有没有信息 Y"。

第二，高产。几条复杂任务并行推进，上一条命令还没跑完，它就能接你的下一条。

第三，主动。它盯着环境里的事件，值得处理就动手，不值得就安静。不是每件事都等你敲一句。

第四，持久。一直在线，连着你真实的工作环境，长期跑出异常能自己恢复。

这四道题里，前两道是"会话组织"问题，第三道是"驱动方式"问题，第四道是"部署与恢复"问题。没有一道是"模型参数"问题——这就是为什么文章后面全是系统设计。

三、五个模块，我一个个拆

官方把支撑这四个特征的架构拆成五块，我按自己的理解重讲一遍。

第一块是两级架构：一个长期存在的 Router 层，加一群上下文隔离的 Worker。

Router 接所有人机交互、维护全局上下文、分派任务，但它自己不干活——官方甚至说它可以不配 Bash 工具。为什么不自己干？因为它要保证"连续"，一旦它陷进具体任务，就成了新的单会话瓶颈。

Worker 则是每个任务一个会话，配完整工具，专心干活。它从不直接对人说话，只把状态和结果汇报给 Router。这样既保住了并发，又不会出现几个 Worker 各说各话、把用户淹掉。

我原来以为"多开几个 agent"就是多智能体，读完才发现区别在职责：Agent Team 的队长要拆任务、深度协调；Router 只分派、不拆解，协调放在更高层。官方还特意说，Agent Team 也可以按两级跑，只要用提示词约束主会话"不亲自干活"。

第二块是事件驱动：Trigger 和 Thread。

输入不再是"人敲的提示词"，而是环境事件：群聊消息、邮件、日历、PR 评论、CI 结果。同一件持续的事——一个 PR、一个 IM 话题、一封邮件链——构成一条 Thread。

这里有两个我很喜欢的工程设计。一个是两阶段过滤：先用代码做快路径（来源、群组、白名单），把大部分噪声丢掉，再交给模型做慢路径判断。另一个是订阅与直通：Router 只为 Thread 的第一个事件建 Worker，之后这个 Thread 的新事件由代码直接送给订阅它的 Worker，不再经过 Router。

直通解决的是很实际的问题：如果所有后续事件都走 Router，这个唯一的全局节点会被压垮。但直通不扩大授权——超出任务范围的事件，Worker 要退订或者交还。

第三块是上下文组织：Inline & Spill 和召回链。

官方把上下文窗口当缓存用：近期可能用到的信息直接内联（Inline），超出预算或者低频的内容留在窗口外，只留引用或摘要（Spill），需要时再读。再往上一层是召回链：给 Trigger、Thread、Worker 会话都编上 ID，注入时把"下一跳"的 ID 一起内联，模型就能沿着引用一跳一跳把历史任务找回来。

这一段对我冲击最大。我之前的笔记里，上下文管理约等于"压缩摘要"；官方这套说法是"把窗口当缓存，把对象关系当索引"。压缩只是其中一种动作。

第四块是全双工：异步 ReAct。

经典 ReAct 调工具是同步的，工具不返回，会话就卡着。官方改成异步的 start 和 stop：start 立刻返回"已开始"，工具在后台跑，跑完把结果当成一条新事件送回会话。这样前台可以继续接新消息，模型也能用 stop 终止跑太久的命令。

这里有一条我必须原样记住的事实：官方明确说，这套异步任务机制 DeepSeek Harness 已经实现，但目前尚未默认开启。所以"它支持全双工"和"你现在就能用上全双工"是两件事。

第五块是计算、状态、环境分离，外加一个看门狗。

计算（Agent Loop）放云端、无状态、可弹性伸缩；会话状态进数据库；执行环境留在原地，每个端点只装一个轻量守护进程，不存状态，只执行命令、返回结果。官方把这条路叫 BYOM，自带机器：你自己的开发机、有未提交改动、有本地凭据、还可能间歇在线，都能接进来。

看门狗则是一个主系统之外的独立会话，定时被唤醒。它不只看进程活没活，还用模型判断 Worker 有没有实质进展、有没有跑偏；修得了就修，修不了就持续复查。因为它本身是个带工具的 Agent，你还能用自然语言问它"刚才为什么失败"。

四、实验数字：高产不是免费的

官方做了两组实验，都是合成负载、简化环境，各跑五次。我把关键数字抄在这里，因为它们是这篇文章里最容易被忽略、也最该被记住的部分。

端到端那组：Super-agent 的任务完成时间中位数 12.4 分钟、95 分位 15.7 分钟；单会话加子代理、用中性提示词，中位数 20.4 分钟、95 分位 29.5 分钟。

但代价在 token：Super-agent 每轮缓存读 2320 万 token，单会话那组只有 610 万。也就是说，它是用大约四倍的上下文开销，换来更短、更稳的完成时间。官方自己写得很直白：这是用 token 换时间。

还有一组对照很值得看：去掉直通的 Super-agent，完成时间几乎一样（12.6 和 15.5 分钟），但 Router 每轮多做约三成决策，缓存读从 2320 万涨到 3180 万。所以直通省的是 Router 的开销，不是完成时间。

Router 压测那组：事件从每分钟 1 个加到 40 个，批大小从 1.0 涨到 2.8，单次请求耗时只从 2.5 秒涨到 3.9 秒，每个决策分摊的推理时间反而从 6.4 秒降到 1.6 秒。官方的解释是批处理：积压的事件合并进一次调用，预填充阶段并行算，所以积压越多、单个决策越便宜。

这段数字纠正了我一个直觉：我以为"并发高了一定更慢"，实际上在一个范围内，忙起来反而更划算；真正的上限是上下文长度和模型单轮能处理多少事件。

五、原型里看到的三个硬细节

文章末尾给了原型仓库，我顺着第三方拆解看了几个实现细节，它们比架构图更能说明"这套东西真要做，难在哪"。

第一个是任务和授权分开。原型里一条工作请求要走：事件 → 判断要不要接 → 建任务单和授权依据 → 分配执行轮次 → Worker 干活。任务单可以经历多次执行轮次，重试时复用原来的会话、目录、分支和 PR。这解决的是"中断之后别假装是新请求"。

第二个是先落账，再动作。状态在数据库事务里改，同时把要做的外部动作排进队列，事务提交之后才真的去发消息、开 Worker。否则先发消息再写库，进程恰好崩了，就会留下一个系统不记得的动作。原型还用一个发件箱记录消息回执，避免重复入队。

第三个是名额算的是"还在干活"，不是"还在说话"。默认三个 Worker 名额，另有一个名额留给人工唤醒；Worker 的文字轮结束了，只要后台 shell 或子代理还在跑，它仍然占名额。这个细节解释了为什么面板看起来空闲、实际却排不上队。

这些都不是文章里的架构图能画出来的东西，但它们决定了这套系统能不能长期跑。

六、我还没搞懂

第一，Router 到底能撑多大。官方说在团队规模下单个 Router 会话还没到瓶颈，也给了分片的方向；但"什么时候该分、分多细"没有答案。我自己没有负载数据，只能记着这个问号。

第二，长期记忆。召回链解决的是"近期任务找得回来"，跑几个月之后怎么办，官方明说是主要瓶颈。我的笔记库也在变长，这个问题我迟早会撞上。

第三，安全。云端 Agent 接着你的开发机，提示词注入、本地凭据、跨设备权限，官方列了三条风险，但没说怎么解。我现在的做法仍然是"危险操作自己确认"，这跟 Super-agent 的"自主"是有张力的。

第四，个人能不能落地。原型是"一个仓库一个部署"，要配专用账号和执行环境；对我这种一个人用的情况，收益可能不在"多任务并发"，而在"事件驱动 + 可恢复"这两条。这一点我还没试。

七、这对我的笔记意味着什么

读完这篇，我回头看自己前面写的几篇，有几处需要补一脚：

第 02 篇说"没有核心的运行时"，官方这篇补了另一半：会话本身也不该是核心，它只是实现细节。第 08 篇讲上下文，这篇给了 Inline & Spill 和召回链两个具体做法。第 11 篇讲事件，这篇把 Trigger、Thread、两阶段过滤、订阅直通讲成了完整链路。第 12 篇讲 turn，这篇的异步 ReAct 正好是 turn 的下一种形态。第 18 篇讲多 agent，这篇把 Router 和 Agent Team 的分工讲清楚了。第 24 篇讲押不押，这篇的实验数字和五个开放问题，是我更新判断的新证据。

所以我把这篇放在第 25 篇，作为"延伸"的第一篇：前面 24 篇讲的是"现在这个 DSH 怎么跑"，这一篇讲的是"官方认为它接下来该长成什么样"。

术语小抄

  • Super-agent：把 Agent 从单个会话里解耦出来、能跨会话连续工作的系统形态。
  • Router：长期存在的路由层，接人、分派任务，自己不干活。
  • Worker：隔离的执行会话，干具体任务，不直接对人说话。
  • Trigger：环境里的事件，比如群聊消息、PR 评论、CI 结果。
  • Thread：同一件事的连续事件流，比如一个 PR 下的所有评论。
  • Inline & Spill：把上下文当缓存，常用的放窗口里，不常用的留引用。
  • 召回链：靠对象 ID 一跳一跳把历史上下文找回来。
  • BYOM：Bring Your Own Machine，把你自己的机器接进云端 Agent。

我还没搞懂

  • Router 分片的判据到底是什么，官方有没有内部画好的线。
  • 长期记忆如果不用召回链，还有什么别的做法。
  • 异步 ReAct 默认不开，是工程原因还是产品原因。
  • 个人场景下，Super-agent 的收益能不能大过它的配置成本。
