我能用 DSH 做什么：七种用法，三种我真试过

版本 v1.1 ｜ 2026-11-08 14:20 (Asia/Shanghai) ｜ 依据：本工作区实际使用记录（26 篇生产、知识库、插件、多 agent）+ 官方 Super-agent 文章
系列第 26 篇 ｜ 版本 v1.1 ｜ 2026-11-08 ｜ 依据：本工作区实际使用记录（26 篇生产、知识库、插件、多 agent）+ 官方 Super-agent 文章
学习笔记 ｜ 第 26 站 ｜ 我带着的问题：前面讲了它是什么、怎么跑、为什么这样设计、我能改哪里；那到底我能拿它做什么？
读之前我以为：它就是一个"会写代码的聊天工具"，能用它做的事，和 ChatGPT 差不多。
读完我的一句话答案：它是一个把"读、跑、写、查、发"串成流水线的工作台；价值不在单点最强，在把重复动作串起来。
读完我能答出来的三个问题：1 我真正用它跑通过哪三件事，证据是什么？ 2 哪三件事我试过但不推荐？ 3 哪一类事它现在干不了，别硬上？（答不出就说明我没学会，这篇先不发）

先说人话：如果前面 25 篇是在拆一台机器，这篇是回答"这台机器买回来能干嘛"。我不列"理论上可以"的清单，只写我自己跑过的、以及明确不推荐的。

一、我原来的判断

我原来的判断：它和别的 AI 工具的区别，是"能读文件、能跑命令"，所以用途就是"帮我写代码、改 bug"。

现在的判断：能读能跑只是入场券。真正改变工作方式的是三件事——它能记住一套流程（不用我每次复述）、它能自己检查结果（跑测试、跑质检）、它能被别的 agent 调用（多角色并行）。三件事叠起来，才出现"流水线"这种用法。

所以我按"能不能串成流水线"来分用途，而不是按"能不能干某件事"。

二、七种用法

1. 内容生产：从选题到草稿的一条链

我跑通的：这个系列 26 篇，就是它产的。流程是选题 → 查资料 → 写初稿 → 机械质检 → 配图 → 建发布草稿。中间每一步都是它自己调工具完成的，我只做判断和拍板。

证据：dsh-series/ 下 26 篇、质检脚本 errors=0、配图 21 张、X 草稿链路（只建不发）。这一条我最确定。

边界：判断"这篇值不值得写""这个观点站不站得住"仍然是我；它负责把重复动作做掉。

2. 知识库管理：专题、索引、镜像

我跑通的：Obsidian 里有 5,000 多篇笔记、几十个专题。新增专题、补 00 指引、更新 _索引.md、把工作区成果镜像进 vault，这些它都能按固定规范做完。

证据：03-资源/专题-DeepSeekHarness/ 的 00 指引和索引、10-一切皆插件系列/ 的 95 个文件镜像。

边界：知识怎么分类、哪些该合并，仍然要我定；它擅长"按已有规则执行"，不擅长"发明规则"。

3. 产品调研：抓竞品、拆站、整理判断材料

部分跑通的：抓页面、拉数据、按模板整理成对比材料，这些可以；但"这个词值不值得做"这种判断，我给不出去，也不该让它给。

证据：工作区里的调研目录、拆站方法论；它能把散落的信息整理成可读的结构，但结论要人下。

边界：付费数据源（搜索量、KD）它拿不到；它的强项是"公开信息的整理"，不是"商业判断"。

4. Coding：读仓库、改文件、跑测试

跑通过的：读一个仓库、定位文件、改一处、跑测试、看失败再改。这个系列的生产脚本、质检脚本、HTML 转换器，都是这么改出来的。

证据：tools/dsh_series_html.py 的三次修 bug（缩进围栏死循环、表格竖线、日期兜底），每一步都有命令输出。

边界：大型重构、需要长期架构判断的改动，它容易"改对局部、搞坏全局"，要人 review。

5. Vibe coding：一句需求到能跑的原型

跑通过的：研究台的 v0.2 界面原型、全景信息图、专题总览页，都是"说清要什么 → 它写 → 截图看 → 改"。

证据：04-插件/02-界面原型-v0.2.html、docs/images/00-全景图.png。

边界：原型能跑不等于能上线；它擅长把想法变成可看的东西，不擅长替你处理部署、权限、数据。

6. 多 agent 并行：一晚八个角色

跑通过的：这个系列第一晚就是 8 个 agent 并行：研究、写作、核查、配图、网页版、插件分头做，共享任务板、划写域、我统一收口。一晚出了 24 篇初稿。

证据：任务板、08-迭代 里的失败记录（覆盖写、口径漂移、状态丢失）。

边界：多 agent 的瓶颈不是模型，是写冲突和口径同步；没有写域和统一口径，人越多越乱。

7. 常驻型 Agent：Super-agent 方向（我没试过）

官方在《Super-agent 设计探索》里描述的是另一层：Router 常驻接活、Worker 隔离执行、事件驱动、跨设备持久。它的原型是一个 GitHub 仓库接一个部署。

我没试过，所以只记为"方向"，不写成"用法"。对我这种一个人用的场景，可能先受益的是"事件驱动 + 可恢复"，而不是"多任务并发"。

三、三种我试过但不推荐的用法

第一，让它替我做价值判断。比如"这篇要不要发""这个方向要不要做"。它会给一个很像样的答案，但那是我的判断被它的措辞替代了，代价在后面才出现。

第二，把还在变的流程焊进自动化。我试过把写作流程整个塞进插件，结果规范一天改三次，每改一次就要发一版；后来改成"机制进插件、口径留 Markdown"。

第三，让它碰真钱和真线上。付款、删数据、改生产配置，这类操作的错误代价不对称；它可以准备、可以检查，但最后一下要人按。

四、一个判断：它的价值在"串起来"

单看每一种用法，都有替代品：写作有写作工具，调研有调研工具，写代码有 IDE。DSH 的不同在于，它能把"读资料 → 跑脚本 → 写文件 → 检查 → 发出去"串成一条不需要我搬上下文的链。

所以我现在的用法不是"用它干某件事"，而是"把一件事的重复段交给它，把判断段留给我"。这也是我写这个系列的底气：26 篇不是它替我写的，是我和它一起跑出来的。

五、我还没搞懂

第一，哪些工作该"常驻"（Super-agent 那种），哪些该"一次性"（headless 那种）。我现在全是一次性会话，还没试过常驻。

第二，成本。26 篇 + 调研 + 插件，烧掉的 token 不是小数；哪些环节值得用强模型、哪些用便宜档，我还没有稳定策略。

第三，权限。它能读我的知识库、能跑命令；哪些目录该隔离、哪些操作该二次确认，我现在的做法是"危险操作自己按"，还没有系统化的权限设计。

术语小抄

  • 流水线：把多个步骤串起来、中间不用人搬上下文的工作方式。
  • 一次性会话：跑完就结束的会话，适合明确任务。
  • 常驻 Agent：一直在线的 Agent，适合接事件、长期任务。
  • 写域：多个 agent 并行时，各自只改自己负责的文件。
  • 机制 / 口径：稳定的执行逻辑 / 还在变的判断标准。

我还没搞懂

  • 常驻 Agent 对个人开发者到底值不值。
  • 怎么给不同任务配不同档位的模型。
  • 知识库和 Agent 之间的权限边界怎么划。
